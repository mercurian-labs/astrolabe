# Memory

A project's memory is the durable design truth its threads ground in and amend: atomic, linked notes — one concept per note, plain markdown, wikilinks — in a git repository (or a folder of one) that the [[Teams|project]] designates. Where a [[Threads|thread]] is one effort's conversation, **memory is what stays true after every effort ends.** It productizes the working design-vault practice — this vault's own — which returned under the re-entry condition an early Concepts note set: real use of the product reaching for something above raw files.

Memory is project-scoped standing knowledge, reached from the [[Left Sidebar]] and designated through [[Teams|project settings]]. The navigation decision below retains the original question and records what the later surface designs settled.

## Three layers, all plain text

A memory holds notes — the knowledge, flat markdown with wikilinks, one concept per note — and [[Skill Maps|skill maps]] — arrangement and teaching in one artifact, beside the notes. Everything the product computes over them (links, backlinks, unresolved references, compiled maps) is a derived index it can always recompute. The index may be kept **compiled** — warm to open, searchable, watching the files for change — but compiled means cache, and the law runs one way: files flow into the index, nothing ever flows back; any doubt rebuilds it from disk; and deleting it loses nothing, the same law a skill map obeys. Ground truth is plain text in git; **Mercurian is a lens over the memory, never a silo for it** — a memory stays editable with any tool and portable out of the product entirely. A link to a note that doesn't exist yet is the frontier, not an error: designed as a concept, not yet written up.

## Reading and grounding

The [[Assistant|assistant]] grounds in memory before raw repository files: entry points, links followed deliberately, stopping when the frontier stops being relevant. What it consulted is shown folded away, exactly as repository grounding is. Notes are mentionable as grounding chips in the [[Composer]] alongside files, and a wikilink is navigable wherever it renders — in a note or a reply — opening a transient reader that never leaves the thread's space (an overlay; 2026-09-24: its reason, the right sidebar's fixed set of views, retired with the right sidebar, and whether a link opens its note in a tab instead is open on [[Tabs]]). Notes speak the product's intent, never implementation; the code is consulted live for what's built. Genre is not a property of the memory — it lives in [[Skill Maps|skill maps]], which carry a genre's arrangement and its house rules in one artifact ([[Skills]]). The dividing line is a litmus the substrate never crosses: **if a mechanism must read a note's meaning — a heading convention, a section's structure, a register — it belongs to a skill map; the substrate's own machinery is content-blind**, moving notes, links, diffs, and commits without interpreting a word.

## Amendments

An **amendment** — a new note, an edit, a red link filled — lands through the product's one write path as a commit on the thread's branch of the memory repository, in the design register, at the moments the work earns it: the agent supplies every changed note whole, and the product writes and commits, marked as an amendment and attributed to the turn that made it. One amendment per commit and nothing else in it is what keeps revert surgical — and it is a rule of the register, taught by the base teaching and the skill maps ([[Skills]]), never enforced by the substrate: the product commits what it is handed, and the memory tab shows what landed. A new note arrives _with_ its map placement, one commit. The memory tab shows the thread's amendments with their review state — review and revert are the curation acts, an unreviewed count stands visible, and reverting is one act on one commit. Nothing needs confirmation before landing, because nothing has left the thread: the thread's branch is invisible to every other thread and to main, and the invariant holds where it matters — **an amendment you never merged home never happened to shared truth.** The merge home is the one confirmation, and it walks what you haven't reviewed. _(2026-09-01: "the agent's own commit," the phrase this paragraph carried since 2026-08-31, meant authored by the agent's turn without a person's confirmation — never the agent running git itself; said plainly now, with the branch re-scoped to the line.)_

Direct human edits happen **outside the product**: the memory is a folder, any editor edits it, git records it, and the files are simply current at the next read — editing a note yourself is a standalone act that summons no one, and the next message you send carries what changed. _(Narrowed 2026-09-24: that holds outside a turn. While a turn is running in a thread, an edit to a note in that thread's working state reaches the running turn as a steer — [[Threads]], [[Assistant]]. An editor inside the product is the [[Atlas Editor]] question, open there against this note's one-write-path rule.)_ The product itself carries **exactly one write path, and it is the amendment commit**; even the frontier's write door is a seeded message that starts an amendment, never an editor. Where an amendment is a mechanical transform — a rename, an edge added to a map, a red link filled — a deterministic utility computes the complete diff and the commit carries it ([[Skills]]). _(2026-08-28: narrowed — an earlier reading let the product carry a note editor of its own; the product is a lens, and the lens reads. 2026-08-31: narrowed again — recording a resolution beneath its question left the utility family; it reads a genre, and utilities are content-blind by the litmus above.)_

**Amended (2026-08-31, with the working-state pool on [[Threads]]): confirmation moves from each amendment to the merge home.** As first designed — and as built — the one write path was propose-and-confirm: a rendered diff, landing only on your confirmation, under the rule "an amendment you never confirmed never happened." The unification re-read the gate: the thread's memory branch was already invisible to every other thread and to main, and promotion was already a human merge — so per-amendment confirmation was a second gate in front of a door already gated, and the proposal itself was a diff living outside git in a product whose ground truth is git. Now the agent commits directly to the thread's branch, and "curated, never captured" survives re-scoped: **main is curated** — nothing reaches shared truth but through your merge — while a thread's branch captures its own working truth the way its history captures everything else, rejected paths included. Given up: pre-landing review — the next turn on the line grounds on an unreviewed amendment, and a wrong one misleads its own thread until reverted; accepted because the blast radius is exactly the thread, the same radius as any wrong turn, and the memory tab's review is the net. The discipline survives as teaching, not a gate: amendments land at the moments the work earns them — a resolved decision, a discovery that memory is wrong — never as ambient churn.

Cross-map consequences surface with the landing. Every amendment is checked against every [[Skill Maps|skill map]] as it commits: a change that severs another map's edges **stamps the warning into the affected map's own record** in the same act, and the memory tab's review shows the standing warning beside the amendment — pause there, investigate, and a resolution you make is recorded in the stamp rather than erasing it: the file itself remembers what broke, when, and how it was handled ([[Skill Maps]]). _(2026-08-31: the check formerly ran on a confirmation sheet, before landing; with confirmation moved to the merge home, it rides the commit and surfaces at review.)_

When building teaches that the design was wrong, the lesson continues in the same [[Threads|thread]] — and returns to memory as one more amendment.

## Branches, and the merge home

An amendment lands on a thread's branch of the memory repository, never on its main line. The memory repository is a member of every slot the project holds, so a thread's branch and snapshot chain cover it exactly as they cover code ([[Threads]], "The working state"): what any thread sees of the memory is what its branch carries, a fork reads the memory as its parent left it because its branch starts at the origin checkpoint, parallel threads never stomp one another, and an abandoned thread leaves no residue on anyone's truth. The [[Composer|composer's]] drift guard sharpens under this: an amendment is checked against the thread's own working tree — the slot it runs in — not against a main line other work is moving.

Two kinds of memory change can appear on a thread, and the memory tab tells them apart. A change made through the write path is a **marked** amendment: its own commit on the thread's branch, attributed, reviewable, revertible in one act. A change the agent made by hand in the memory folder — editing a note as a file — reaches the snapshot chain like any other edit but never the branch; the memory tab shows it as **unmarked**, with the same diff and the same revert, and the merge home commits it, labelled as unmarked, before anything crosses. The fence is visibility, not prohibition: the substrate cannot stop an agent from editing a file, and does not try; it makes the bypass plain, and the skill maps teach the register that makes it rare.

A memory designated as a folder inside a code repository is that repository's memory: the same branch, the same snapshots, the same exit. A memory that is its own repository is a member of the slot in its own right. A folder that is its own repository nested inside another member's tree is refused at designation — git would record it as a pointer, not as files — and the refusal names the two shapes the product accepts.

Promotion is a merge, and merges are human. When the work ships — the code merged, the thread published — the product **recommends** bringing the thread's memory home to main: a suggested next message beside the act that shipped, never an automatic act ("forks and transfers are human-driven only," [[DAG]], holding at one more layer). The merge home is where per-amendment confirmation retired to (the 2026-08-31 amendment above): it walks the branch's unreviewed amendments, unmarked changes included, so nothing crosses into shared truth unseen. Its shape follows the repository's own exit ([[Threads]], "Three exits, all human"): a memory inside a code repository ships with the code — the walk sits before the push, and the pull request is the merge; a memory that is its own repository, and typically never leaves the machine, merges home locally on your confirmation. When main has moved and the merge conflicts, the conflict returns to the conversation: the assistant proposes a reconciled amendment against current main, and your confirmation is the merge. Escaping to plain git remains legitimate at every step — it is the memory's own history, after all.

**Amended (2026-09-01): the memory branch belongs to the line, and the write path is the product's.** As first written (2026-08-31), the first amendment in a thread opened a branch of the thread's, every line of the thread committed there, and what a line saw was derived from the memory state each amendment recorded. Two things broke it. Under the snapshot chain on [[Threads]], every repository in a slot already gives each line a branch that forks where its ancestor stood — a thread-scoped memory branch was a second model for one repository, and it could not say what happened when two lines of one thread both amended: the later commit landed on top of an amendment the earlier line never saw. And a memory that lives inside a code repository — a shape the product accepts — shares that repository's branch with the code, so a separate memory branch there was never possible at all. Re-scoping to the line dissolves both: the ancestry reading falls out of the branch, and the code-repository case is simply the ordinary case. Given up: "one amendment per commit" as a property the substrate guarantees — it is a register rule now, taught not enforced, and a hand edit shows as unmarked rather than being impossible; and a merge home of one shape — the exit is the repository's. Kept: the invariant that nothing reaches shared truth but through your merge, and the walk of everything unreviewed before it.

_(2026-09-24: a line is a thread — the thread-as-one-line model on [[Threads]]. The branch belongs to the thread, and the reasoning above stands with that word: a fork is a new thread whose memory branch starts where its parent's stood at the origin checkpoint.)_

## Open Decisions in memory

A note's Open Decisions are standing forks every future effort inherits, surfacing as offers in the [[Composer]] when a conversation touches the note that carries them. Resolutions are recorded, not overwritten, and no fork is ever silently promoted to settled — a convention taught, like every genre convention, by the skill map whose territory carries it.

_(Amended 2026-08-31: genre leaves the substrate.)_ An earlier reading had the product deriving these decisions deterministically — parsing the sections as a known convention, guarding their headings at amendment time, seeding the composer's suggestions from the parse. That baked a genre into shared infrastructure, against this note's own law that the substrate knows notes and links. Now the substrate carries no knowledge of Open Decisions: surfacing them is the teaching's work ([[Composer]]), protecting them is the review's — the memory tab shows the whole diff, and an amendment that rewrites a question is reverted by the human who reads it — and recording resolutions is ordinary amendment prose. Given up: the mechanical heading guard, which validated a register — exactly what the advisory resolution on [[Skill Maps]] says nothing may do — and the parser-derived suggestion source. Kept: the product behavior that open forks surface as offers, now driven by skill maps.

## Staleness

Shown, never auto-reconciled — and detected at two moments. **At read**, every skill map re-validates against the live link graph: an edge whose prose link vanished refuses loudly, and the check runs against the memory state the reading thread's ancestry sees — a branch that never saw the breaking change computes no warning ([[Skill Maps]], [[Threads]]). **At landing**, the amendment pipeline's cross-map check stamps what it severed into the affected map's record, resolution and all (above). External edits bypass the pipeline by design; for those, read-time refusal is the net, and the deterministic forensics on [[Skills]] reconstruct the history on demand — which commit severed the link, which files, which maps' edges. A warning offers a **seeded investigation message** — the frontier-door pattern — on the thread that caused it, never acting on anything itself.

Notes edited outside the product are simply the current files at next read; what a turn was grounded in is part of its record, so a turn that predates a memory change is discoverable — advisory, never re-run. A project with no memory can bootstrap by extraction: the agent walks the product the way a user would and builds a thin-first product map with the frontier red-linked, each slice its own amendment commit.

## What exists today

**Codex workflow (2026-09-10).** The working memory can now be used outside the app through Codex: a task selects an isolated memory branch, discovers its skill maps, reads relevant notes, and lands attributed amendments. Review shows the complete pending branch, including hand-made changes; an authorized local merge promotes the reviewed state. Renames update note links and every map together, and stale relationships remain visible. This workflow is independent of the app’s conversation checkpoints: it does not automatically follow a conversation fork or provide the app’s per-amendment review interface. The dated app snapshot below is historical, not an account of what the Codex workflow supports.

The amendment flow is built in its original propose-and-confirm form (2026-08): proposals as rendered diffs in the conversation, landing only on confirmation. The 2026-08-31 amendment supersedes that gate — the built diff review becomes the memory tab's review, and confirmation retires into the merge home; branches, the memory tab, and the merge home itself are not built, and the 2026-09-01 amendment re-scopes the branch to the line on the snapshot chain, which is built as of 2026-09-02 ([[Threads]]) — the memory repository is not yet a slot member, and every read is still of the designated folder as it sits on disk. The working precursor is this vault and its conventions; designating a vault as a project's memory is the whole migration, one compile step for its containment declarations ([[Skill Maps]]).

## Open Decisions

### Where does memory live in the app?

The [[Left Sidebar]] is a flat thread list with workspace rows in a footer; the [[Thread Tabs]] is thread-scoped by design. Memory is project-scoped standing truth and fits neither cleanly. It needs a designation point, a browsing surface (maps, backlinks, unresolved, search), and an in-thread reader. **Recommendation:** designation joins the project's existing management surface beside its repositories; browsing is a team surface reached from the footer and the [[Search Palette]], scoped by the same project filter as everything else; the in-thread reader is a transient overlay, keeping the right sidebar's thread-only rule intact. Held loosely — this is the part most worth designing on the running product.

**Partially resolved (2026-09-10, reconciling the standing surface designs): designation and project browsing are settled.** [[Teams]] places memory selection in project settings and the new-project flow; [[Left Sidebar]] places Memory in the project-scoped footer. This records those existing decisions rather than choosing a new location. The former plan-only right-sidebar premise was superseded by the adopted thread panel ([[Thread Tabs]]); the original recommendation above must not be read as an unchanged constraint on the in-thread reader. Given up: treating designation and project browsing as still unplaced. The precise in-thread reading interaction is not newly resolved by this reconciliation.

_(2026-09-24: the browsing surface's graph reading is the [[Atlas Graph]]: the whole memory drawn as a web in three dimensions, skill maps as lenses on it, the frontier as nodes. Beside a thread the same graph surfaces the notes the turn reaches.)_

_(2026-09-26: the browsing surface no longer has a graph reading. The [[Atlas Graph]] is a thread tab only, drawing the thread's branch; the Memory page keeps its list, search, and unresolved references.)_

### Does a confirmed amendment land in the thread's history?

The amendment commits to the memory's own history either way. As a checkpoint in the thread's history ([[Threads]]) too, the record stays complete: one history per thread loses its force if some events are invisible. As bookkeeping, the tree stays quieter and only the memory carries the event. **Recommendation:** a commit, cross-referencing the memory commit it landed — deciding to change durable design truth is exactly what a thread's history should explain.

**Resolved (2026-08, during M-181 planning): a commit, cross-referencing the memory commit it landed — as recommended.** Mechanically it is not a new kind of commit but a flavored one: the history says "you amended the memory" and names the amendment, and the record carries the memory commit's identity so the two histories point at each other. Given up: a quieter tree — every confirmed amendment now shows in the thread's history, which is the point. _(2026-08-31: with confirmation moved to the merge home, this holds for every amendment — the turn that landed it is in the thread's history by construction, and the cross-reference rides its checkpoint.)_

### Do notes and decisions get identity beyond their names?

Names are the identity today — the vault's own mechanism — and the convention-first reading matched a decision-identity question the retired plan note once pinned. But [[Skill Maps|skill maps]] reference notes by name from a second layer, so every rename must propagate into every map, and the product owns that propagation. **Recommendation:** convention first; productize navigation over the convention; maps are the surface most likely to eventually justify stable identity — revisit when rename propagation is real.

**Resolved (2026-08-28): convention first, made safe by the rename utility.** Names stay the only identity — the vault's own mechanism, unchanged. What the recommendation was waiting for arrived as the deterministic rename on [[Skills]]: the complete propagation — the file, every wikilink in every note, every edge in every [[Skill Maps|skill map]] — computed as one amendment commit, reviewed like any other. Given up: stable identifiers that would survive a rename no utility saw; accepted because every rename the product performs is a utility rename, and renames made outside the product were always going to be the editor-owner's responsibility, exactly like any other external edit. Revisit only if shared memories surface collisions that names cannot absorb.
