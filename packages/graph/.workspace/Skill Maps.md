# Skill Maps

A skill map is one artifact doing two inseparable jobs: it **arranges** a purpose's corner of the [[Memory|memory]] — a curated subgraph of notes and edges — and it **teaches** the [[Assistant|assistant]] how to use the memory for that purpose. Arrangement is the map half; teaching is the skill half; they share one file because how a view is organized and how it is meant to be used are one piece of knowledge. The **product map** succeeds this vault's containment spine — the same walk-the-product navigation, now one skill map among several — and skill maps as a class are **project-carried [[Skills|skills]]**: they live beside the notes, version with them, and travel with the project (the resolution on [[Skills]]).

Two rules keep the layer honest, unchanged from when maps were arrangement alone:

1. **Notes hold truth; skill maps hold arrangement and teaching.** A skill map never becomes the home of a fact, and deleting any skill map loses zero knowledge — only a lens and its instructions.
2. **A skill map is literally a subgraph.** It may select, arrange, and label edges that exist in the base graph — never mint one. If the product map wants "Threads contains Composer," the prose must actually link them; a missing edge is a question for the note, not a link to invent.

## The graph

Arrangement is **an edge list, not a tree**. Trees are a rendering; the data is adjacency — each edge names its two notes and its type — because every hierarchy is a graph wearing a layout, and the layout is the application's job. What the schema says:

- **A map declares its own edge vocabulary**: each edge type it uses, with a one-line meaning. Edge meaning stays map-scoped — the product map's _contains_ and another map's _depends-on_ can read the same neighborhood differently, and no global link taxonomy ever needs agreeing. A map may declare several types; an edge of an undeclared type is refused.
- **Every edge carries its rationale.** An edge is added by naming its two notes, its type, and _why_ — the reasoning captured at the moment it exists, in the act that creates it, stored beside the edge it justifies. The map's natural-language **reading** is generated on demand from these authored atoms — rationale, type meaning, and the prose sentence that links the pair — never written down as a derived document that could drift from what it describes.
- **File order is curation.** Edges are one per line, and the order a note's outgoing edges appear is the order its neighbors read — a spine's "Composer before Right Sidebar" is a statement the file makes by ordering, with nothing extra to say it.
- **Repeats and cycles are legal.** A note may appear in as many edges as the view needs, and a cycle is a finding about the design, not an error — only the compile step that turns `contains::` declarations into the first product map still refuses cycles, because it is flattening into a spine.
- **Rendering is derived, and the map may insist.** The arrangement's own shape — the union of its edges, every type together, because structure routinely crosses types — picks its reading: a forest renders as an ordered **tree**; an acyclic graph renders as a **flow**, the layered reading where direction ranks; anything with cycles renders as a **web**, the relational reading where a cycle draws as the loop it is instead of being forced through ranking. A map that wants a particular reading declares its view — tree, flow, or web; the map's choice, not the schema's. _(Amended 2026-09-01: the single spatial reading borrowed from the [[Checkpoint Graph]] is corrected — that graph is genuinely acyclic, so the layered reading fits it natively; a skill map's shape is its own, and hierarchy is a property of some edge types, never of maps as such. Given up: one spatial grammar across the product, spent for cycles rendered natively. 2026-09-01: half regained — both spatial readings adopt the [[Checkpoint Graph]]'s camera and minimap, panning and zooming the way its map does; what stays distinct is only the layout each shape earns.)_

The prose-edge rule survives verbatim under the new shape: every edge, of every type, must correspond to a wikilink between the two notes in prose, either direction. The substrate's own links are directed — a note cites another, and the direction carries meaning: backlinks, unresolved references, and which side holds the explaining sentence all depend on it. The edge rule validates against that graph read in either direction, and a map orients its own edges freely within it. A skill map is therefore not a strict subgraph but a **lens**: typed, directed, ordered interpretation laid over relationships the prose already holds. Two maps may read one neighborhood in incompatible ways — disagreeing about what a relationship _means_, never about whether it _exists_, because existence has one source. Notes hold the product's truth; maps hold interpretation for a purpose — deleting a map loses a lens and its readings, never a fact. A skill map may reference an unwritten note deliberately — red-linking the frontier is what a map is for — and off-map notes are healthy, and enumerable: the memory can always list what no skill map has placed.

## The skill

The body of the file is the teaching: when to consult this view, how to walk it, and how notes destined for it are written — the register rule that once lived in a one-line `rule:` field, grown to full prose. The product map's body teaches orientation by containment; a decision map's body teaches "consult these before resolving." A skill map **specializes the protocol and never contradicts it**: the invariants every map inherits — notes hold truth, arrangement never mints, the product's one write path is the amendment commit, curated at review and the merge home — are product-owned and stated once, on [[Skills]]. A body is optional; the product-map generator writes a starter one. Injection is tiered: the base teaching and a **roster** of the skill maps — name and purpose each — are ambient in every turn once a memory is designated, and a map's full body arrives when it is invoked from the [[Composer]] or when the turn works its territory; the base teaching is never omitted, whatever else is, because it carries the rules that hold whichever map is steering. Accepted cost, recorded deliberately: a skill body is repo-authored text entering the assistant's instructions, a wider surface than arrangement alone — the one write path, amendment commits reviewed before anything merges home, is what keeps it curated.

## The file

A skill map is **markdown with structured frontmatter**, extension `.skillmap.md`, living **flat beside the notes** — the extension is the discriminator, so the memory keeps the flat-folder convention the old maps folder quietly broke. Frontmatter carries the structure: name, purpose, the edge-type vocabulary, the edges with their rationales, the optional view — and the map's **staleness record**: warnings stamped by the amendment pipeline when a landed amendment severed an edge, each holding what broke and when, and its resolution once made, recorded in the stamp rather than erasing it ([[Memory]]). The markdown body carries the skill. A malformed skill map fails loudly, never degrades silently, and an edge whose prose link is missing is refused with the note to fix.

The frontmatter is the machine half, and **agents never meet it directly**: every read arrives through a tool that renders it — the derived walk of the arrangement, the generated readings, the standing warnings — and every write goes through a utility that round-trips the validator ([[Skills]]). The file itself stays human-first — any editor opens it, external edits stay external, read-time validation keeps that honest. Tools are the agent's contract, not the file's nature.

## Birth and maintenance

A skill map is born from research, landed by review. A derived lens over the substrate seeds it — the agent surveys the neighborhood from each edge type's perspective, adds edges with their rationales through the utility, and the whole map lands as one amendment commit on the thread's memory branch, reviewed edge by edge in the memory tab ([[Memory]]). Creation reasoning and graph construction inform each other inside one loop, and the rationale parameter is what captures that reasoning at the only moment it exists.

After birth, skill maps are memory, so they change the way memory changes: amendment commits on the thread's branch, curated at review and the merge home ([[Memory]]). Mechanical transforms — renaming a note across every edge that references it, adding an edge — are computed by the deterministic utilities on [[Skills]] and land as ordinary amendment commits: the utility computes the diff, the commit carries it, your review curates it. When a stamp or a read-time refusal marks a map stale, the product offers the investigation as a suggested next step on the line that caused it — the forensics assemble what broke, which commit, which files — and the reconciliation lands as one more ordinary amendment.

## Open Decisions

### What can a map say?

The direction is settled; the schema's expressive range is not. Hierarchy, ordering, groupings, and edge labels are the clear core. Are per-entry annotations allowed, or is that prose leaking back into arrangement? Can a map repeat a note (a walk may revisit; the product map never should)? Can a map include another map? And can a map hold a query ("all notes with open decisions") — which would make its contents unknowable without evaluation? **Recommendation:** start with pure arrangement — no annotation text beyond purpose and rule; repeats forbidden with a per-map allowance; no composition until practice asks; and no queries ever — a map's contents must be readable from its file alone, with derived views (all-unresolved, recently-changed) living as product lenses over the index and as seeds a human curates into a proposed map, never as map content. Let the schema grow primitives the way this vault grew conventions: from practice, recorded as amendments.

**Resolved (2026-08-28, the skill-map reshaping): adjacency with declared edge meanings, speaking markdown.** Repeats dissolved by shape — an edge list has no single-placement rule to except. Per-entry annotations stay refused: prose belongs in the skill body or in a note. Composition still waits for practice to ask. Queries still never — a map's contents must be readable from its file alone. Given up: the "maps are data, so they don't get markdown" file-shape rule — the skill body made prose first-class, so the shape followed the dominant layer to markdown with structured frontmatter; and the tree's free guarantees (single placement, no cycles), which the graph shape trades for expressiveness and the tree rendering recovers where a map happens to be a forest.

### Does a map's rule govern the notes it curates?

A map's rule field states how its genre's notes are written. Enforced, the product would have to judge prose against a register — which it can't do honestly; advisory, the rule governs authoring behavior: when the assistant proposes a note destined for a map, it writes under that map's rule. Two maps' rules meeting on one note is usually the graph saying one note is two concepts. **Recommendation:** advisory — a rule shapes proposals and review, never validation; conflicts prompt a split, not a schema fight.

**Resolved (2026-08-28): dissolved by fusion — the rule field grew into the skill body.** Advisory stands exactly as recommended: the skill shapes proposals and review, never validation, and two skill maps meeting on one note still prompts a split. What changed is only where the rule lives — full prose in the map's own body, rather than one line in its schema.
