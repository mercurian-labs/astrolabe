# Code Graph

The [[Atlas Graph]] drawn over a codebase instead of a [[Memory|memory]]: every symbol a node, every structural relationship an edge, and a thread's checkpoints the turns whose story it tells. _(Designed 2026-09-30, Venkat's idea: the memory's story of notes and links has a twin in code, and code carries richer structure than prose, since programs say what calls, extends, implements, and defines what. A proof of concept is being built the same day.)_ Why it exists and what it may and may not say is [[Design Legibility]]: the tool makes the design legible and never grades it. It is the same surface with a second kind of memory under it, not a second surface: the reading, the storytelling, the labels, the frontier, and the rules that nothing moves at rest and the reader's hand never moves a node all carry over from the Atlas Graph unchanged.

## What it draws

- **Nodes are symbols.** A file is a module; its classes, interfaces, functions, methods, and types are nodes inside it. A node's name is its short name, the way a note's name is its identity ([[Memory]]): `render`, not the path. The path, the kind, and the lines are in the popover. Two symbols may share a name; the map draws the name and keeps the identity underneath.
- **Edges are relationships, typed, in four families.** _(Vocabulary adopted 2026-09-30 from Code-Graph-RAG's graph schema, the mature form of what the first proof of concept improvised.)_ Containment: a folder or package contains files and modules. Definition: a module or class defines its classes, interfaces, enums, types, and functions; a class defines its methods. Polymorphism: inherits, implements, overrides. Use: calls, instantiates, references, imports, exports. The plain graph flattens the use and polymorphism edges into one link per pair, as the Atlas Graph flattens wikilinks; containment and definition are never links, they are where a symbol lives (below). Every use edge carries how it was bound: exact, overload, or heuristic, which are the three tiers of resolution by their proper names. Node kinds: folder, package, file, module, class, interface, enum, type, function, method, and an external module for what is imported from outside the repository.
- **A container is a region, not a node.** _(Ruled 2026-09-30, after the first walk showed a reading of hundreds of symbols spread across the frame.)_ The containment tree, folder, file, class, method, is one tree per language, with a package standing for a folder where the language has packages. At rest a container draws as a faint tinted region with its name at its edge, nested at every level, and a symbol's home is inside its parent's region. Containment is not a force between symbols: a file's forty functions sit inside their file instead of repelling each other across the reading.
- **A node's shape is its kind.** _(Venkat, 2026-10-01: the kind of every node should read at a glance.)_ A label already carries the note's name and, during a checkpoint, its story glyph, and at reading density a node is a few pixels wide, so the kind is told by shape, which reads at any size, and never by a second prefix in the label. Functions and methods are circles, a method being the circle that sits inside its class; classes are rounded squares; interfaces are diamonds; enums are hexagons; types are triangles; constants are small filled squares; a closed container is a circle with a ring. The same symbol stands before the kind's word in the popover ("◇ interface · src/model/view.ts · lines 12–40") and before the name in the play-by-play, and a key in Settings lists them. The memory of notes keeps its plain circles.
- **A reference to a symbol that does not exist is a frontier node**, drawn receded, the way a red link is in the memory. In code that is a name the agent calls before it writes it, or a symbol it removed while something still names it.

## Level of detail follows zoom

_(Ruled 2026-09-30.)_ The one-reading-density rule ([[Atlas Graph]]) says one spacing per frame. A large reading obeys it by collapsing: at reading density the graph shows methods; one step out, each class collapses into one node sized by its members; another step, files; then folders. So a reading of six hundred symbols is a dozen files at the level where it fits the frame, and the density never changes. **The level follows the span of the change.** _(Venkat, 2026-09-30.)_ Take what the turn touched and find its lowest common container; the story is told one level below it. Changes inside one class show its methods; across classes in one file, the classes; across files, the files; across folders, the folders. If that level still holds more nodes than fit one frame at reading density, the story goes up one more. Links aggregate to the level shown, so at file level a bead runs from one file to another for the calls their functions make, and clicking a file drills into what is beneath. Arrivals travel with their container: a new file glides in as one thing and opens. _(Venkat, 2026-10-01, after the first tour stopped at a closed file and said "wrote 3 in reading.test.ts" without showing them.)_ **The cursor goes inside.** When the tour reaches a container whose contents the turn worked, the container opens and the camera moves in to reading density on it; the cursor then visits each worked symbol inside, with its gesture and its own label, and the links made among them run their beads; when it is done the camera steps back out, the container closes with its quiet mark, and the cursor goes on to the next thing at the level the span chose. The landing level is where the story is surveyed; the tour is where it is told, one container at a time. **An open container shows its own structure.** _(Venkat, 2026-10-01.)_ While a file or class is open in the story, the edges among its shown members, the calls and uses that already stood, draw quietly for as long as it is open, so the reader sees the structure the turn is working inside; the links the turn made still carry the full ink and the beads, and edges to things outside the container stay dark unless the turn made them. This is the one place code departs from the memory's rule that nothing but the story is drawn: in a vault of notes a note's links are the story; in code, a file's inner calls are its shape.

**The reading is the worked set.** _(Venkat, 2026-09-30.)_ For code, the reading is what this turn and the earlier turns of the thread touched, and both ends of every link a turn made, which are touched by definition. A caller nobody changed does not belong on screen: it appears when the reader hovers the symbol that calls it, lit, and the camera reaches for it if it lies off frame. The one-link neighbourhood that the memory's reading draws receded ([[Atlas Graph#Surfacing with the turn]]) stays a setting, useful for a small vault of notes, and is off by default for code. Everything drawn is part of the story at its level; prominence separates this turn from earlier ones.

**The camera reaches; the notes never do.** The reader's hand never moves a note ([[Atlas Graph#Storytelling]]). When a hovered symbol's lit neighbour lies outside the frame, the camera pans, or steps out one level, just enough to bring it in, after a short linger so a passing pointer does not jerk the view, and returns when the hover ends. A chosen move does the same for both ends of its link: the follow-the-agent turn, choosing the level.

**The play-by-play is grouped by the tree.** A turn's moves are listed as a short tree: file, then the symbols with their moves, then the links made, under their source. A module's amendment is implied by any change inside it and is never a move; containment never makes a move. Same events underneath, so the graph and the list stay one story.

## Three tiers of resolution

Tree-sitter parses one file at a time and resolves nothing by type, so an edge from a call to a definition carries how sure the map is of it. _(Ruled 2026-09-30.)_

- **By name.** A reference to `render` links to every definition named `render` in the index. Instant, always available, over-connected.
- **By import.** The file's own import statements are visible to the parser. When they bind the name to a module, the candidates narrow to that module's definitions. This closes most of the gap in code that imports what it uses, at no cost.
- **Resolved.** A language server or a SCIP index says exactly which definition. This tier is a **backfill**: it arrives later, may fail, and never delays the story. When it arrives, it mostly prunes: the candidates that were not meant fade out, and nothing moves. When it fails or times out, the edges stay at their tier, say so in the popover, and the next checkpoint retries.

The graph is honest about this by over-connecting rather than omitting: a story told at the name tier may draw a link to a namesake, but never misses a link the turn made.

## Where the precise tier comes from

Both a language server and a SCIP indexer type-check without building, and both need the project's own configuration to exist and be sane; neither runs as part of compilation. They differ in shape, so the design uses both behind one interface, and builds the language server first:

- **A language server** is a long-lived subprocess per language, asked per position. That fits the checkpoint: a turn touches a handful of files, and the graph asks only about the references in those. T3 Code already runs provider CLIs as subprocesses; a language server is the same shape. The TypeScript toolchain the repo runs for typechecking ships a language-server mode, so the first provider costs nothing new.
- **A SCIP index** is one batch run over the whole project, producing one file: minutes on a large repo, nothing incremental. That fits the **base graph**: built once when a project is first opened, refreshed in the background or produced in CI, so checkpoints only ever resolve deltas on top of it.

A repository with neither still gets a coherent, slightly over-connected graph from the first two tiers. That is the floor, and the proof of concept builds only the floor.

## The checkpoint is the delta

A checkpoint is a git ref ([[Checkpoint Graph]]), so a turn's story is the structural difference between two trees: the files the diff names are parsed at both refs, and the symbol and edge sets are compared. Symbols added are written, symbols whose definition text changed are amended, edges added are linked, edges removed are unlinked, in the memory's own vocabulary, so the reading and the play-by-play need no new words. The work is proportional to the files the turn touched, never to the repository. The graph at a checkpoint is the base index plus the deltas up to it, the same replay the memory's reading uses.

## Open Decisions

### What is a symbol's home?

_(Opened 2026-09-30.)_ The memory's notes settle by their links. A codebase has a hierarchy the memory does not: files in directories in packages. Whether symbols settle purely by their edges, or a module's symbols cluster around their file and files around their package, decides whether the map reads as an architecture diagram or as a web. The proof of concept settles by edges with the package as a lens; the question is left open until the map is seen.
