# Providers

A provider is a coding-agent product Mercurian runs work through; a **provider instance** is one connected account of it — work beside personal; a **model** is what an instance runs a turn under. The three-level pattern adapts [[T3code Providers]], documented there as built. Providers power Mercurian's one agent surface — the [[Threads|thread]] — through one picker control and one record: the per-branch choice, carried in the thread's shared history as an abstract provider, model, and depth (the resolutions, as amended through 2026-08-28, on [[Assistant]]). Code turns run under the same record; what they add is a requirement, not a second choice — the machine hosting the repositories. _(Historical: while conversation and coding sessions were separate surfaces, the session chose per session, machine-locally; the unification absorbed that record.)_

## Instances live on machines

Instances are managed in [[Settings]] — plumbing, not first-class, the same temperament as [[Environments]] — and they are **machine-scoped**: an instance lives on the local environment where the provider's agent is installed, because signing in belongs to the provider's agent on that machine, never to Mercurian. Configured once on a machine, an instance is offered to everything that runs there. The t3code instance grammar transfers: a default instance per provider that resets but never disappears, added instances that can be deleted, a label and accent color that follow the instance into every picker, and an identity that never changes once minted ([[T3code Providers]]). Curation transfers too: an instance's model list can be favorited, hidden, and reordered here, shaping what every picker offers ([[T3code Settings]]).

Because instances are machine-bound and a thread's record travels, to your other computers and, once published, to your [[Teams|teams]], **nothing shared ever names an instance**: each thread's own model choice ([[Assistant]]) names a provider and model abstractly, and each machine resolves the pair to its own instance at runtime. A code turn is the bounded case: it must run on the machine hosting the thread's repositories, and what that machine's installed agents can run is what gates it — the same resolution rule, plus physics.

## Switching within a thread

The [[Assistant|assistant]] can change provider or model between turns. The provider label is not treated as a model-family boundary: some provider products offer models from several makers, and custom connections can widen that set, so "same provider" would not promise sameness of model lineage or hidden context. Mercurian gives every effective change one product meaning instead. A reply already in progress finishes under the choice it started with; the next reply starts a fresh assistant session with the thread's recorded history carried into it. Whether a provider could switch models inside its existing session is plumbing and never changes that visible rule.

The choice is per branch, carried by the history rather than held as thread state: each message that opens a turn records the provider and model it ran under, wherever you stand derives its choice from ancestry, and a fork inherits the choice at its fork point (the 2026-08 amendment on [[Assistant]]). Switching on one branch never changes what another branch's next reply runs under.

## New enough, or not yet

Capabilities arrive with the machine's installed agent, and Mercurian inherits t3code's temperament of gating rather than failing ([[T3code Providers]]): models the agent is too old to run don't appear, with an explicit message naming the upgrade that unlocks them; an instance whose agent has a newer version wears an update nudge with a one-click update. An instance's standing — authenticated as whom, not signed in, agent not installed — is status surfaced on the instance, never a login flow of Mercurian's own.

## Signed in, or not yet

Sign-in standing is a **readiness** fact, and readiness is a different question from what a picker offers. A model picker offers what a machine's instances _carry_ — the provider is here, this is its curated list — while readiness asks whether a turn could actually run right now. The two deliberately disagree: a provider you are not signed in to keeps offering its models, because choosing a model you are about to sign in for is a reasonable thing to do, and hiding it would explain nothing. What sign-in governs is sending, not offering (the resolution below, and the states on [[Composer]]).

Resolution reads standing the way [[Environments|plumbing]] should: a machine with several instances of a provider resolves past a signed-out one to a signed-in one rather than failing, and a thread's saved pair is never rewritten by a machine that can't run it — the same rule that holds when no instance exists at all.

## What exists today

Providers, instances, and their curation ship as inherited from [[T3code Providers]] and verified against this design: the instance grammar, model favoriting and hiding, standing surfaced on the instance, capability gating with the upgrade named, and the update nudge. The workspace model default landed with the [[Assistant]]'s first real turns, and has since narrowed to last-used seeding under the per-branch choice. The sign-in gate is closed as resolved (2026-08): a provider explicitly signed out stops sending with the standing named and where to fix it, the picker keeps offering its models, and drafts stay unblocked.

## Open Decisions

### Are provider instances machine-scoped or workspace-scoped?

Machine-scoped is what the agent reality dictates — the provider's CLI and its sign-in live on a machine — but it means workspace-level settings cannot reference an instance that exists everywhere. Workspace-scoped instance _names_, bound per machine, would let settings point at instances directly — at the cost of a sync surface Mercurian otherwise refuses ("refresh, not sync"). **Recommendation:** machine-scoped, with workspace-level choices naming provider and model abstractly, resolved to the machine's instance at runtime.

**Resolved (2026-07): as recommended.** Instances belong to the machine and are managed in [[Settings]]; the abstract provider-and-model form is what workspace settings speak. Given up: a workspace setting can't pin work to a _specific account_ — the machine decides which instance of that provider serves — accepted because pinning accounts workspace-wide was never the point of the setting. _(2026-10-10: "workspace" in this decision meant the set of repositories you worked across, since retired ([[Teams]]). The rule stands for anything shared: a thread's recorded choice and anything a team holds name a provider and model, never an instance.)_

### Does an instance you aren't signed in to stop you sending?

A collision this note half-stated. Standing — "authenticated as whom, not signed in, agent not installed" — is surfaced on the instance, but what governs sending is whether the thread's model _resolves_ on this machine, and resolving asks only whether the provider is here and its agent installed. An installed agent you are signed out of therefore answers yes, the [[Composer]] opens, and every message lands to a reply that can only fail — the message is a commit either way ([[Threads]]), so what fails is the reply, after the fact.

As **not gating**, there is one fewer state to word, and the after-the-fact notice already explains what happened. As **gating**, the composer is honest before you press send rather than after, which is the same courtesy the capability gate already extends to a model the agent is too old to run. **Recommendation:** gate — a signed-out provider is exactly as unable to reply as a missing one, and the surface should say so at the same moment.

**Resolved (2026-08): gate, with three refinements.** Sending stops when the thread's model names a provider that is here but signed out, and the composer names the standing and where to fix it. The refinements are what keep the gate from overreaching: **only an explicit not-signed-in standing gates** — an _unknown_ standing is ignorance rather than a fact, and gating on ignorance would block working setups; **the picker keeps offering a signed-out provider's models**, because offering and readiness are different questions (above); and **drafts stay unblocked** — a thread is still born by its first message whether or not an assistant can answer it ([[Threads]]). Given up: a fourth can't-reply state to word and keep distinct from the other three ([[Composer]]), and the tidy promise that every model a picker lists is one that could run right now — traded for a picker that shows what a machine has rather than only what it can do this second.

### Is a repository's reachability a fact about the session, or about the turn?

_(Raised 2026-09-01, with building across repositories.)_ Some providers reach every repository a [[Threads|thread]] claims and some honestly reach one; the design's promise is that the product _says_ which, before work is attempted. The question is where that statement lives. As **a fact about the session** — stamped once when building starts, from the provider chosen then — it is simple and always present, but the provider can be switched from the composer afterward (resolved on [[Assistant]]), so the stamp can name repositories as out of reach while the current provider reaches them, or the reverse; a notice that can be wrong is worse than none. As **a fact about the turn** — derived from the provider that actually runs it, recorded on the commit that opens the turn beside the provider and model it ran under ([[Assistant]]) — the statement is always true of the turn it describes and follows a picker flip on the next send, at the cost of a per-turn record rather than a standing label. **Recommendation:** a fact about the turn. It is the same shape the recorded choice already has — every turn-opening commit records what it ran under — and reachability is a consequence of that choice, not a property of the conversation. Given up: a standing "this session cannot reach X" label; the history says it per turn instead, which is also where a reader checks what a build actually saw.

**Resolved (2026-09-02): a fact about the turn, as recommended.** Reachability is derived from the provider that actually runs the turn and from where the turn stands — itself derived per turn since the same day's amendment on [[Threads]] — and recorded on the turn-opening commit beside the provider, model, and depth it ran under ([[Assistant]]). What the person sees before sending is the [[Composer|composer]]'s statement of what the next turn will not have, computed from the picker as it stands at that moment, so a flip corrects the statement before it corrects the record. Given up, as recommended: a standing "this session cannot reach X" label on the thread; the history says it per turn, which is also where a reader checks what a build actually saw.

### Which repository's agent configuration does a turn load, and can the product tell?

_(Raised 2026-09-02, with the slot root as a standing.)_ Providers load their own configuration — instruction files, hooks, skills, tool connections — from the directory they stand in and its ancestors, and some walk from the repository root. A turn standing in the home repository loads that repository's; a turn at the slot root, which is no repository, may load none of any member's, and a provider may refuse to stand outside a repository at all. The design promises to say before send what a turn will not have ([[Threads]]), and here the product does not yet know what that is: which providers tolerate a non-repository standing, what each loads from where, and whether any provider reports what it loaded. As **research first**, the product states only what it knows, and the slot root carries a plain "may not load" caveat until the answer is in. As **a generated root**, the product writes an instruction file at the slot root naming every member and its position — read by most providers from where they stand — at the cost of one more file the person never wrote. As **a per-adapter declaration**, each adapter declares what it loads and from where, the way it already declares whether it reaches several roots, and the composer's statement derives from it. **Recommendation:** research first, then the per-adapter declaration, with a generated root where a provider is shown to read one; the caveat stands until then. Given up: nothing yet; the risk carried meanwhile is a person surprised that a repository's own hooks did not fire.
