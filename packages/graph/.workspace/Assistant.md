# Assistant

The assistant is your research partner in every [[Threads|thread]]. It converses, grounds itself in the project's [[Memory|memory]] and repositories, amends memory and changes code when a turn calls for it, and — when you take context from another thread — responds with that thread's delta in hand, compacted (see [[Merges]]). It never structures the history: "forks and merges are human-driven only" — the assistant only ever continues from where things left off. _(2026-09-16: it no longer commits plan or spec revisions; those documents retired with the plan-first ruling on [[Mercurian]].)_

## How it behaves in conversation

- **Responses stream.** You watch the reply being written, and you can stop it mid-response from the [[Composer]].
- **Grounding is visible.** When the assistant consults the project's [[Memory|memory]] notes or repository files to ground a reply — memory first for intent, files for implementation truth — what it looked at is shown, folded away until you expand it, so the record is inspectable without cluttering the conversation.
- **It can ask you questions.** When the work needs your call, the assistant asks a structured question rather than guessing; the thread signals **awaiting your input** until you answer ([[Status Vocabulary]]).
- **It answers messages, not edits — outside a turn.** A note you edit by hand while no turn is running summons no one; the next message you send carries what changed ([[Memory]]). While a turn is running, an edit to a file in the thread's working state is delivered to that turn as a steer saying what changed, because the agent is already working on the same files and silence is the harmful case: an agent that does not know you rewrote the passage under it overwrites it or argues with it ([[Threads]], [[Atlas Editor]]). _(Narrowed 2026-09-24; the rule was written when no turn could be running while you edited.)_

## Open Decisions

### Is a stopped response part of the history?

Everything in the thread is a commit — so what is a response you stopped halfway? As a **commit**, the history stays honest (something did happen) and forking past a bad partial response is exactly what a fork is for ([[DAG]]). As **discarded**, the history stays clean and stopping means "as if never sent," which matches the intuition of cancelling. **Recommendation:** commit it, marked as interrupted. One history per thread loses its force if some events are invisible, and the fork-past-it move is cheap.

**Resolved (2026-07): a commit, marked as interrupted.** Given up: a history that pretends clean cancels — stopping means "this happened and was cut short," and forking past it is the tree's own move.

### Does the user choose the assistant's model?

The shell this design adapts (t3code) exposes a per-thread provider and model picker, with new threads inheriting the last-used choice rather than any configured default (see [[T3code Thread]] and [[T3code Providers]]). For Mercurian, is model choice per-issue, a workspace-level [[Settings|setting]], or invisible? **Recommendation:** a workspace setting. Planning quality shouldn't be a per-issue knob, and the composer stays uncluttered; revisit if users ask to trade depth for speed on individual issues.

**Resolved (2026-07): a workspace setting — reaffirmed when coding sessions existed as a second surface.** The two surfaces deliberately differed: conversation read the workspace setting, a coding session chose per session — the same asymmetry as permission modes, and for the same reason: what varies per task is implementation, not planning. One amendment forced by instance scoping: [[Providers|provider instances]] are machine-bound while the workspace is shared, so the setting names a provider and model abstractly — never an instance — and each machine resolves it to its own ([[Providers]]). Given up: trading depth for speed on individual issues; the original escape hatch stands — revisit if users ask.

_Reopened (2026-08): users asked._ The concrete ask: running one thread under one provider and another under a different one, within the same project — exactly the per-thread variation the escape hatch anticipated.

**Resolved (2026-08): per-thread choice, seeded by a workspace default.** The [[Settings]] setting stays, demoted from the answer to the default: it seeds every new thread, so a user who never cares about models never touches a picker. The [[Composer]] carries the per-thread picker, live from the first draft message — the choice is made at thread initiation without any creation step, preserving "nothing exists until its first commit" ([[Threads]]). A thread either follows the workspace default or carries its own override; returning to the default makes later workspace-default changes apply to that thread again. The effective choice is switchable between turns, across both models and providers, with each assistant commit recording the provider and model that produced it so the history explains itself. A change never retargets a reply already in progress: that reply finishes under the choice it started with, and the next reply begins a fresh assistant session reconstructed from the thread's recorded history. The choice is shared thread state, not personal, which is why it follows or overrides the workspace default rather than inheriting t3code's last-used stickiness ([[T3code Providers]]). It names a provider and model abstractly, never an instance, each machine resolving the pair to its own ([[Providers]]); what a machine's installed agent can't run is gated, not failed ([[Providers]]).

No provider-family lock applies after the first message. A provider names the agent product Mercurian talks to, not a dependable family of underlying models: some providers broker several model makers, and custom connections blur the boundary further. Locking that label would therefore restrict choice without guaranteeing continuity. Mercurian instead gives every effective provider-or-model change the same continuity rule — fresh assistant session, recorded thread history carried forward — regardless of whether the provider could have switched models inside its old session. Given up: preserving provider-private session context across a switch, and the previous resolution's uniformity — all threads in a workspace running under one model. What remained distinct from coding sessions was the seeding (workspace default versus last-used) and what pickers offer (abstract provider-and-model versus the machine's instances).

**Amended (2026-08): the choice is per branch, and it lives in the history.** "Shared thread state" was the wrong wording. The choice is shared, not personal — but it is not a thread-wide knob, and it is not mutable state at all: it is a fact of the record. Each human commit that opens a turn records the provider and model the turn ran under, and whether it was following the workspace default or overriding it; the choice in effect wherever you stand derives from the nearest such ancestor. A fork therefore inherits what was in effect at its fork point, and two branches can run under different models without touching each other. Flipping the picker is draft-local until a message lands — "nothing exists until its first commit" ([[Threads]]), so there is no switch commit: a switch you never messaged under never happened, and the message that lands is what records it. A [[Merges|merge]] records its choice like any commit that opens a turn — seeded from the path you stood on when merging, switchable before you send — and its compaction and reconciliation run under it, so descendants derive through the merge's own record and parents that planned under different models never leave the continuation ambiguous. Each assistant commit additionally records its **reconstruction boundary** — the commit where its session's context stopped being carried verbatim and older history entered as summary — and when a compacted rendition was actually used, the rendition is kept folded on the commit, the same folded honesty as grounding: a compaction is assistant-written and so not re-derivable, and the history should explain what a turn could see. Given up: the thread-wide knob — changing the choice on one branch no longer changes what another branch's next reply runs under — and attribution living only on assistant commits.

**Amended (2026-08, second): last-used seeding; the workspace default retires.** The seeding half of the resolution reverses. A configured default earns its place only if it predicts what threads actually run under better than the record does — and the record is already there: every message that opens a turn records what it ran under. So a new thread now starts under the pair you last ran under — the most recent turn-opening record anywhere in your own threads — and [[Settings]] loses the model row entirely. The only model control left is the picker on the [[Composer]]; with no history yet, the composer asks for a choice there before the assistant can reply, and everything after seeds from use. With no default to follow, the record simplifies to the pair itself: "following the default" is no longer a mode a branch can be in, and the standing choice anywhere is just the nearest ancestor's recorded pair. This adopts exactly the t3code last-used stickiness the original resolution declined ([[T3code Providers]]) — what still separated conversation from coding sessions was the scope of the record, not the seeding: a thread's choice lands in the shared history as an abstract provider and model, never an instance, while a session's choice is machine-local. The picker is one control, offering the machine's instances, each row standing for its provider: choosing any instance of a provider records the same abstract pair. Given up: the workspace-level default and the return-to-default mode — a branch can no longer be told "follow whatever Settings says next"; a stale branch is moved by messaging under a new choice, not by a Settings change — and the seeding distinction between the two agent surfaces.

_(2026-10-10.)_ The records above were written while "workspace" named the set of repositories a person or team worked across. It is retired ([[Teams]]): the last-used pair is read from your own threads, and a thread you continue from a teammate's starts under your own last-used pair, as it does on Astrolabe's `collaboration` branch: their recorded choice describes their turns, not yours.

### Does the assistant need permission modes?

t3code offers supervised / auto-accept / full-access modes because its agents run commands and edit files on your machine. As first designed, Mercurian's assistant read repositories for grounding and wrote only versioned revisions inside the recoverable history. **Recommendation:** no permission modes. Every write stays inside the branching history and remains inspectable and recoverable; if the assistant ever gains write actions beyond the planning space, this reopens.

**Amended (2026-08-28): reopened by the unification exactly as foreseen, and re-closed as an action boundary.** [[Threads]] put building in the same conversation, so the boundary could no longer be a surface; it became a kind of action. The composer carries one **runtime mode** (supervised / auto-accept edits / full access) governing working-tree actions only — a turn that touches no worktree never meets it, and [[Memory|memory]] writes need no mode at all — they land only on the thread's own memory branch, invisible to shared truth until the human merge home (the 2026-08-31 reading; formerly this held because propose-and-confirm was stricter than any mode). The original reasoning survives whole: modes exist exactly where a working tree is edited.

_Reopened for implementation (2026-07):_ coding sessions were exactly such write actions, and carried the three-tier t3code runtime modes while conversation stayed mode-free — the boundary the unification relocated above.

### Does the model choice include how hard the model thinks?

The recorded choice is a pair — a provider and model, named abstractly, never an instance. But many models expose a depth control of their own: reasoning levels that trade speed for depth on the same model. The composer pattern as built already offers them where the model does ([[T3code Thread View]]), so a coding session could choose depth per task — while the thread's pair was the whole vocabulary, so a thread could choose _which_ model thinks but not _how hard_.

Depth is not machine-bound the way instances are: a level names the same behavior wherever the model runs, so it extends the abstract pair without strain. Every rule of the 2026-08 amendments generalizes to a triple: each turn-opening commit records the depth it ran under; the standing choice derives from the nearest ancestor; a fork inherits its fork point; flipping is draft-local until a message lands; and a machine whose installed agent doesn't offer the level gates rather than fails. The asymmetry with coding sessions stayed where it was — the scope of the record, not the shape of the control. _(Dissolved 2026-08-28 — the paragraph below.)_

Against: the recorded choice just got simpler — the second amendment retired the workspace default — and every dimension added to it is picker surface and record surface forever. Depth vocabularies also differ by provider and model, so the record would hold each provider's own words for depth rather than one scale.

**Recommendation:** extend the choice — the pair becomes provider, model, and the model's own depth where it offers one, under all of the pair's existing rules. This honors the depth-for-speed escape hatch a second time: the 2026-07 resolution gave up "trading depth for speed on individual issues" but kept "revisit if users ask" — users asked once and got the per-branch picker, and asking for depth on a branch is the same request, finer-grained.

**Resolved (2026-08): as recommended — the pair becomes a triple.** The recorded choice extends with the model's own reasoning depth where the model offers one, under every rule the pair already follows: recorded by each turn-opening commit, derived from the nearest ancestor, inherited at fork points, draft-local until a message lands, and gated rather than failed on a machine whose installed agent doesn't offer the recorded level. A model that offers no depth simply records none, and a history from before depth existed runs at the model's default until a message records one. Accepted: depth speaks each provider's own vocabulary rather than one scale — the record holds the words the turn actually ran under. Given up: the two-field simplicity of the recorded choice, freshly won by the second amendment.

**Amended (2026-08-28): one record governs every turn — the session-side choice is absorbed.** With [[Threads|threads]] unified, the per-branch triple governs code turns exactly as it governs replies; there is no per-session picker and no machine-local second record. What the session's per-task freedom bought — a retry beside a failed attempt under a stronger model — the per-branch record buys natively: fork, flip the picker, and both attempts stand in history with their recorded choices. A code turn additionally requires the machine hosting the repositories; when this machine can't run one, the [[Composer]] says so in its existing can't-reply grammar. Given up: the deliberate asymmetry recorded above and on [[Providers]]; what remains asymmetric is only physics — where a turn can run, not what records it.
