# Durable checkpoint history

`CheckpointRecordStore` owns one record per existing Mercurian history act. A turn's opening query commit remains the owner when its response arrives. Imports, refreshes, and merges can attach their own delta with `attach`, without an orchestration turn. `get(planId, ownerCommitId)` and `getByTurn(threadId, turnId)` expose durable identities for historical readers. Callers must retain their normal plan authorization.

The immutable query payload records its request thread and line root before dispatch. A raw recorded send is unanswered; only the persisted accepted-start event marks preparation. The response payload records `checkpointOwnerCommitId`, independently of its M-137 `reconstructionId`. The response owner has a unique index; a repeated append returns the immutable recorded reply. Exact response attachment can therefore be repaired after an append/attachment crash. Reconstruction submission acknowledgment and summary storage are unchanged.

`CheckpointRecordReactor` subscribes before replay and consumes persisted orchestration events in sequence. Its cursor and each event's record updates commit in one Mercurian transaction. New terminal capture events retain `requestMessageId` from `ProjectionTurnRepository.pendingMessageId` and `captureTerminal`; no PlanTurnId conversion is involved. Legacy captures without exact association remain unresolved for known Mercurian threads. Legacy queries without a recorded line root retain an unknown line identity and do not enter line-scoped document projection. Other orchestration threads do not acquire Mercurian records. Replay never selects a latest message or triggers another capture.

Pre-provider cancellation needs no turn ID or capture event. Its request becomes cancelled. Captured partial turns instead retain a concrete turn link and their partial capture facts. On restart, unfinished requests with no exact running projected turn become unknown rather than indefinitely saving. A later exact capture can still complete them. Runtime deletion preserves records and terminates unresolved live status; plan deletion removes its records with the owning history. There is no record-only deletion API, so no tombstone protocol is needed.

Repository groups are authoritative when present. Successful snapshots and partial facts survive weaker placeholders. Capture and summary availability are separate: a missing member snapshot blocks a coherent historical fork, while failed summary enumeration alone does not invalidate recorded snapshots. Metadata does not retain Git objects; existing hidden refs and snapshot chains still own reachability. Historical diff and restoration resolve these recorded objects without a mutable HEAD fallback.

`PlanDetail.checkpoints` and `checkpointSequence` are read atomically. `subscribePlan` acquires the checkpoint feed before snapshot reads. `afterCheckpointSequence` is independent of `afterSequence`; catch-up queries `(plan_id, update_sequence)` in pages of at most 128 current rows. Updates use `checkpoint-update`, snapshots use `checkpoint-snapshot`, and `checkpoint-synchronized` advances the independent high-water. Overall `synchronized` follows both opening catch-ups. A transient `in-flight-turns` frame refreshes active reply text and questions when the commit stream resumes; replayed start frames cannot reset an already-snapshotted turn. Clients reject stale per-record revisions and retain the checkpoint cursor only after the corresponding high-water marker. Older clients without a checkpoint cursor receive a fresh checkpoint snapshot. No patches, file contents, or reconstruction summaries ride these frames.

The pure client-runtime checkpoint helpers derive effects from recorded roles and report lifecycle/availability separately. Document history follows the selected carrying ancestry through its selected checkpoint, excluding the line's inherited prefix and non-carrying merge parents. A merge contributes its saved delta. M-214 remains responsible for populating capture-time document roles; these readers do not infer locations or a permanent document registry.

`mercurian.readCheckpointDiff` accepts `{ planId, ownerCommitId, repositoryId, checkpointRevision, ignoreWhitespace? }`. It resolves the repository from the saved capture and the registered repository path, then delegates the exact before/after OIDs to `CheckpointDiffQuery` and `CheckpointStore`. It never needs an orchestration thread, a surviving runtime, or the current slot. A successful member of a partial multi-repository capture remains diffable. Missing records, unavailable snapshots, unrecorded repositories, and stale revisions return explicit unavailable results. Legacy records without exact snapshot pairs cannot provide this historical diff. Full patches remain lazy and retain the Git driver's existing output limits.

The client-runtime `recordedCheckpointDiffTarget` helper supplies an environment-scoped target for `createMercurianPlanningAtoms(...).checkpointDiff`. Environment, plan, owning act, repository, whitespace choice, and record revision participate in the query cache identity. Rebuild the target from each checkpoint update; a newly available record or stronger capture creates a new cache entry. Revision zero is available to readers attempting an identity before its record arrives. Physical repository recovery can be retried by refreshing the query or reopening it after its short stale interval. The existing thread/range diff interface remains available to its existing consumers.

For code continuation, pass `recordedCheckpointForkInput(record)` to the existing `forkLine` command. This form names the owning act and revision; the server selects its exact recorded terminal reply when available, otherwise the owning act itself. A terminal capture with every required repository snapshot remains continuable after interruption or a crash even when no reply was appended. The first new query is parented through the selected checkpoint, so restored files and M-137 reconstruction both include A and exclude later B. Owner lookup survives later response attachment: an already-pending fork keeps its originally selected owner boundary and saved files, without inserting a reply into its reconstruction. New selections can navigate through the attached response. Nonterminal captures and incomplete repository snapshots remain unavailable. The `{ planId, parentCommitId }` form retains exact-parent query-edit semantics; a caller editing the prior query must not use its after-snapshot continuation action. The web Checkpoints surface joins records by `ownerCommitId` and recomputes its projection when records change. Recorded file effects determine turn glyphs in code, memory, plan, spec order; lifecycle status appears separately. Legacy turns without records retain their artifact-revision reading. Open changes selects a repository in the Diff panel using the current record revision, with explicit unavailable states and no HEAD fallback. Continue from checkpoint uses the recorded fork command without seeding the prior query into the composer. The shared document-history projection retains owner effects when a later attached response is outside the selected carrying path, while excluding future owners, inherited prefixes, and other line roots.

`LineBranchReactor` consults the nearest record on carrying ancestry before legacy runtime/session inheritance. Recorded snapshots require every saved and linked repository to agree and every required branch-tip/after-snapshot object to exist. Incomplete captures fail coherently instead of creating some repositories from HEAD. Summary enumeration failure alone does not block restoration. Initial branches start at each saved deliberate branch tip, and existing `SlotService` overlays the saved hidden snapshot, preserving uncommitted files. Recorded line-root identities supplement graph-inferred legacy roots and survive runtime cleanup; an explicit fork remains a distinct line even when its first query is the terminal reply's first child. M-137's first-fork detection recognizes that rooted query after pending runtime metadata has been cleared; in-place native resume keeps its existing reconstruction provenance.

`AttachCheckpointInput` exports the existing `CheckpointRecordStore.attach` operation's input for import, refresh, and merge integrations: `{ ownerCommitId, lineRootCommitId, capture }`. The owner and line root must already belong to the same plan history. Capture facts come from the existing snapshot path, without fabricated provider identities or a second capture engine. This interface does not implement import/refresh/merge product interactions. Runtime cleanup removes neither these records nor the existing retained snapshot chain/refs. No additional pinning mechanism is introduced.
