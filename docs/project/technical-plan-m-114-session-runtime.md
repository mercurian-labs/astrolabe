# Technical Plan — M-114: Coding session runtime: turns, approvals, modes, compaction

_Generated from the Goal/AC on Linear issue M-114 (2026-08-19). Grounded against `main` at `d5baedf1e`, after M-110 landed session birth. Product sources consulted in the almagest vault as of `bd4a698` (2026-08-19): **Coding Sessions** (resolved: modes, compaction), **Assistant** (resolved: mode asymmetry), **T3code Thread**, **Issue Status**, **Coding Session View**, **Composer**, **Merges**, **Search Palette**. Governing ADRs: 001 (`docs/architecture/local-first-runtime.md`), 002 (`docs/architecture/event-streaming-model.md`), 004 (`docs/architecture/fork-baseline.md`)._

**Goal, in one sentence:** govern the coding sessions M-110 births with the fork's own thread runtime — three runtime modes switchable from the session's composer, kind-scoped approvals with exactly four responses, one interruptible turn at a time, the context meter and automatic compaction — by reactivating the fork's thread surface at a session route, stripping the plan/default interaction mode, and projecting awaiting-your-input/working onto the project tree, while no session compaction ever reaches plan history.

**Scope fences:** M-110 built birth and owns the draft (including the draft's runtime-mode choice, already restricted to the three product tiers). 063/064 (M-117/M-118) own the real session screen — timeline reshaping, checkpoint/revert surfacing, right panel, diff review; this issue's surface is deliberately the fork's existing thread view reactivated at a route, not a redesign, per the issue's non-goal ("a minimal turn surface suffices to exercise the runtime"). 065 owns git actions and PRs (`CodingSessionStore.attachPullRequest` stays unwired); M-115/066 owns teardown (`CodingSessionStore.end` stays unwired). M-99 built the status ladder this issue feeds; M-104 built planning's mode-free composer, which this issue does not touch.

**Vocabulary:** the product tier is worded **Supervised**; the wire value is `approval-required`. Upstream's fourth tier `auto` never reaches a Mercurian surface. "Interaction mode" / plan mode is the fork concept this issue strips; "runtime mode" is the one it keeps.

## Discovery Summary

**Most of the AC is already mechanically true in this repository, unmounted.** Strictly-one-turn is the composer's send-becomes-Stop gate (`ComposerPrimaryActions.tsx:150`, phase from `session-logic.ts` `derivePhase`); interrupt is a full chain from the Stop control through `thread.turn.interrupt` (`decider.ts:1027`) to `ProviderCommandReactor.processTurnInterruptRequested` and the adapters' `interruptTurn`. Approvals pause the turn per kind (`ProviderRequestKind`: `command` / `file-read` / `file-change`, classified in `ClaudeAdapter.ts` `classifyRequestType` and remapped by `ProviderRuntimeIngestion.ts` `requestKindFromCanonicalRequestType`), surface in the composer (`ComposerPendingApprovalPanel.tsx`), and offer exactly the four product responses. Decline is wordless and non-terminal by construction — the panel has no text field, and the Claude adapter maps it to a tool deny while the turn continues (`ClaudeAdapter.ts:4044`). Allow-for-the-session is delegated to the provider's own session-rule vocabulary (Claude: `updatedPermissions` from the SDK's suggestions, `ClaudeAdapter.ts:4032`; ACP: `allow-always`; OpenCode: `always`) — there is deliberately no T3-side grant store. Structured questions are a separate channel end to end (`user-input.requested/resolved` activities, `thread.user-input.respond`, `ComposerPendingUserInputPanel.tsx`), and both pause kinds are already derived server-side onto the thread shell as `hasPendingApprovals` / `hasPendingUserInput` (`ProjectionPipeline.ts` `refreshThreadShellSummary`, `ProjectionSnapshotQuery.ts`). The meter is `ContextWindowMeter.tsx` in the composer footer, fed by `context-window.updated` activities; compaction is provider-automatic (Claude `compact_boundary`, Codex `thread/compacted`) and lands as an ordinary `context-compaction` timeline activity (`ProviderRuntimeIngestion.ts:741`) — there is no user trigger and none is added, matching the resolution ("the user neither triggers nor prevents it").

**One mechanical gap, found by tracing the whole chain: Cancel turn does not end the turn.** The vault is explicit — "Cancel the turn — the turn ends" — but upstream's `cancel` decision is a plain tool deny with a "User cancelled tool execution." message. Neither `onRespondToApproval` (`ChatView.tsx:5251`), nor the decider's approval-respond case, nor `ProviderCommandReactor.processApprovalResponseRequested` (`:1210`), nor `ProviderService.respondToRequest`, nor `ClaudeAdapter.respondToRequest` (`:4494`) interrupts the turn; whether the agent stops is left to the model's discretion. Section 3 closes this at the decider.

**The interaction mode is dormant, and this issue is its recorded strip point.** Every entry point is gated behind `settings.planModeEnabled` (default false, Settings → Beta "legacy-plan-mode"): the Build/Plan pill and compact-menu "Mode" group render only when it is on, the Shift+Tab intercept bails first (`ChatComposer.tsx:1871` `if (!planModeUiEnabled) return false;`), the `/plan` / `/default` dispatch checks it (`ChatView.tsx:4898`), and `ChatView.tsx:1494` coerces the effective mode to `"default"` when off — so the Settings row is the one reachable affordance, and the rest is dead code one flag away from returning. ADR 004 §2 assigns the strip to backlog 062 (this issue). The strip is taken at the surface: the Settings row _and_ the flag-gated dead code behind it all go, so the concept's absence is structural rather than dependent on a flag default upstream owns; the wire plumbing (`ProviderInteractionMode`, the `thread.interaction-mode.set` command and event, `projection_threads.interaction_mode`, the adapters' plan-mode branches, mobile) stays dormant, always `"default"`, because tree-wide contract removal poisons every weekly upstream merge and belongs to cut-over (ADR 004 §3). M-110 already hardcodes `interactionMode: "default"` at birth.

**The fork has four runtime tiers; the product has three.** `RuntimeMode` (`orchestration.ts:119`) carries `auto` between auto-accept-edits and full-access; the vault names exactly three tiers, and M-110's draft already offers only three (`CODING_SESSION_RUNTIME_MODES`). The session composer must offer the same three. The contract keeps `auto` (upstream-owned).

**The tree seam was reserved by M-110 and is exactly ADR 002 §4's prescription.** `composePlanRowStatus` currently passes `hasPendingInput` through untouched and derives `isWorking` from `endedAt === null` — a deliberate placeholder ("M-114 owns pending approvals/questions and will compose those thread-derived flags at the already-reserved read-layer seam"). The composition source is the thread shell (`hasPendingApprovals`, `hasPendingUserInput`, `latestTurn.state`); the invalidation source is "upstream's domain-event stream filtered to referenced thread ids" (ADR 002 §4, verbatim), with `CodingSessionRecordReactor.ts` as the in-tree precedent for consuming `streamDomainEvents`.

**One fidelity risk, named honestly:** the vault says allow-for-the-session silences "that kind" of action; Claude's `acceptForSession` applies the SDK's _suggested_ permission rules, which may be narrower than the whole kind (e.g. one command pattern rather than all commands). The issue's own framing treats the built t3code machinery as the referent ("All of that machinery is built in this repository"), so provider-delegated granularity is the shipped semantics; the integrated walk verifies the observable behavior, and if a second command of the same kind still asks after allow-for-session, the fallback is a one-function widening at the Claude decision-mapping seam (`ClaudeAdapter.ts:4032`) — not a new grant store.

## Design

### 1. The session route reactivates the fork's thread view — the minimal turn surface

Add `apps/web/src/routes/_chat.sessions.$threadId.tsx` **(new)**, a lightly adapted copy of the deleted thread route (`git show 2da3c58b1^:apps/web/src/routes/_chat.$environmentId.$threadId.tsx` is the donor). It resolves the machine's environment with `usePrimaryEnvironmentId()` (the `PlanningSpace.tsx:179` precedent — sessions are local-first, single-environment; 063 re-addresses if that changes), mounts `ChatView` with `routeKind: "server"` and the sync phase from `resolveThreadSyncPhase`, and drops the donor's draft-thread halves entirely: sessions are born already started (M-110), so there is no draft promotion, no `draftId` variant, no `finalizePromotedDraftThreadByRef`. A missing or deleted thread renders a quiet empty state with a link back to the plan, in the `IndexPlaceholder` temperament — not a redirect loop.

Reusing `ChatView` whole is the architecture guardrail applied literally: the surface brings the composer (send-becomes-Stop, so one-turn/no-queueing and interrupt arrive built), the approval and structured-question panels, the runtime-mode select, the provider/model pickers, the context meter, and the timeline that already renders `context-compaction` as an ordinary work-log entry (`session-logic.ts:745`, its test at `session-logic.test.ts:1596`). Everything else it drags in — header actions, checkpoints, terminal/diff panes — is upstream behavior on a deliberately minimal surface; 063/064 reshape it into the designed screen, and 066 owns teardown, so no header affordance is hidden here. That includes the header's thread archive/delete menu (`useThreadActionMenu`, `ChatHeader.tsx:179`): deleting a session's thread outside the designed teardown leaves a dangling `coding_sessions` record, an accepted interim exposure (Decision Log D1) — the status projection (§5) tolerates it, reading a missing shell as idle.

Entry point: enable the deferred **Open session** action on the plan timeline's session card (`PlanTimeline.tsx:214`, disabled since M-110) to navigate to the route by the record's `threadId`. The sidebar popover rows and DAG explorer keep their current, non-navigating rendering — the timeline card is the designed entry, and 063 owns richer navigation.

`navigateToParkedThreadRoute` stays an inert no-op: `ChatView`'s internal thread-to-thread navigations still go nowhere, which is correct while plans are the navigation spine. The `chat.*` keybindings in `_chat.tsx` stay inert for the same reason.

### 2. The session composer carries exactly the three tiers

In `ChatComposer.tsx`, restrict `runtimeModeOptions` (`:256`) to `approval-required`, `auto-accept-edits`, and `full-access` — upstream's `auto` tier leaves the select. The existing labels already match the product wording (Supervised / Auto-accept edits / Full access). If a pre-existing thread carries `auto` (legacy, pre-fork threads only — Mercurian births never produce it, since `MercurianStartCodingSessionInput.runtimeMode` admits only the three), append the current value to the options so the select stays truthful; it disappears the first time the user picks a product tier. The `RuntimeMode` contract itself is untouched.

Mode switching is upstream's semantics, transferred whole: the select stages the change in the composer draft (`handleRuntimeModeChange`), the next send persists it via `thread.runtime-mode.set` (`persistThreadSettingsForNextTurn`), and the provider session restarts with resume (`ProviderCommandReactor.ts:666`). The draft's initial mode (AC 1's first half) is already M-110's `runtimeMode` on `thread.create`; the default stays `full-access`, matching `DEFAULT_RUNTIME_MODE` and t3code's non-sticky default — the vault names no Mercurian default, so upstream's is kept deliberately rather than silently.

### 3. Cancel ends the turn — closed at the decider

Extend the decider's `thread.approval.respond` case (`apps/server/src/orchestration/decider.ts`) so a `cancel` decision emits `thread.turn-interrupt-requested` alongside `thread.approval-response-requested`, guarded on the thread actually having a running turn — the same event the interrupt command emits (`decider.ts:1027`), so the reactor path (`processTurnInterruptRequested` → `ProviderService.interruptTurn`) is reused unchanged and the deny lands before the interrupt (the engine processes serially). This is the one Mercurian-semantics change inside upstream orchestration, and the decider is the right seam: it holds for every client and every replay, where a client-side double-dispatch would hold only for the window that clicked. The other three decisions are untouched — approve-once and allow-for-session resolve and continue, decline denies and the turn continues wordlessly (the vault's "declining carries no words" is already structural: the panel has no text field, and the deny message is fixed, never user-authored).

### 4. The interaction mode is stripped from every reachable surface; the wire stays dormant until cut-over

Remove, on the web app only:

- the Settings → Beta "legacy-plan-mode" row (`SettingsPanels.tsx:1592, 1635-1642`) and its search entry (`settingsSearch.ts:158`) — with the row gone, `planModeEnabled` is unreachable and permanently false;
- the Build/Plan pill in `ComposerFooterModeControls` and the compact menu's "Mode" group (`ChatComposer.tsx:311-342`, `CompactComposerControlsMenu.tsx:43-58`), collapsing the split prop bundle (`showInteractionModeToggle`, `interactionMode`, `onToggleInteractionMode`) out of those components;
- the hardcoded Shift+Tab intercept (`ChatComposer.tsx:1870-1874`) and the `/plan` / `/default` slash commands (parse in `composer-logic.ts:265-275`, dispatch in `ChatView.tsx:4895-4911`, menu entry `ChatComposer.tsx:1691`).

`ChatView`'s effective-mode coercion to `"default"` stays as belt-and-suspenders. Everything below the surface stays, dormant and always-`"default"`: `ProviderInteractionMode` and its fields on threads/shells/commands, the `thread.interaction-mode.set` command and event, migration 012's column, the per-provider plan branches, the proposed-plan machinery, `Sidebar.logic`'s "Plan Ready" (the old sidebar is itself parked), and all of `apps/mobile` (parked by ADR 004). Deleting those now would poison every weekly upstream merge for zero user-visible gain; their removal is cut-over scope. Amend ADR 004 §2's disposition row to record exactly this: surface strip landed at M-114, contract/wire removal deferred to cut-over.

This also closes AC 2's planning half by inspection: planning surfaces never mounted mode UI (M-104, mode-free by construction), and the settings row was the last mode affordance reachable anywhere.

### 5. Awaiting-your-input and working are composed at the tree's read layer from thread shells

Two changes at the seam M-110 reserved, both pure ADR 002 §4:

**Composition.** Rework `composePlanRowStatus` (`apps/server/src/mercurian/planning/wire.ts`) to take per-session live facts rather than inferring "working" from `endedAt`:

```ts
interface SessionLiveStatus {
  readonly isWorking: boolean;       // shell.latestTurn?.state === "running"
  readonly hasPendingInput: boolean; // shell.hasPendingApprovals || shell.hasPendingUserInput
}
composePlanRowStatus(status, sessions: ReadonlyArray<SessionLiveStatus | null>)
```

In `ws.ts`'s `loadPlanningTreeSnapshot`, look up each live session's shell by `ProjectionSnapshotQuery.getThreadShellById(session.threadId)` (sessions with `endedAt !== null`, and sessions whose thread no longer exists, contribute `null` → idle). The plan row's `hasPendingInput` becomes assistant-or-any-session; `isWorking` becomes assistant-or-any-session-turn-running. This deliberately _retires_ M-110's `endedAt === null ⇒ working` placeholder: a session idle between turns shows no signal, and a session paused on an approval shows awaiting-input — the client ladder (`resolvePlanRowStatus`) already ranks pending-input above working, so a paused session's row flips from Working to Awaiting your input with no client change. The palette's needing-you ranking and the project-row rollup ride the same fields for free.

**Invalidation.** Add a fourth stream to the tree subscription's merge (`ws.ts`, the `subscribeTree` handler): `OrchestrationEngineService.streamDomainEvents` filtered to the event types that change a session thread's shell-status facts — `thread.activity-appended`, `thread.session-set`, `thread.turn-start-requested`, `thread.turn-interrupt-requested`, `thread.approval-response-requested`, `thread.user-input-response-requested` — and to threadIds that belong to coding sessions (checked via `CodingSessionStore.getByThreadId`, a unique-indexed lookup; the in-tree precedent for consuming this stream is `CodingSessionRecordReactor.ts`). `thread.message-sent` is explicitly excluded so token deltas never churn the tree; the existing 50 ms debounce coalesces activity bursts, and the tree re-emits whole small snapshots per ADR 002 §7. `ProjectionSnapshotQuery` and the engine's event stream join the ws layer's Mercurian scope if not already present — and per this repo's known failure mode, every new method the handler calls must appear on `server.test.ts`'s mocks in the same commit.

No per-session status rides the wire records themselves: `PlanCodingSessionRecord` stays pure store facts, the sidebar popover keeps its current labels, and per-session live status display belongs to 063's screen (which will have the thread stream open anyway). The signal the AC names — the session rolling up its plan's row — is exactly what the row flags carry.

### 6. Compaction stays inside the session — verified structurally, not re-implemented

Nothing needs building for AC 6's mechanics: the meter is already in the composer footer (`ContextWindowMeter.tsx`, fed by `context-window.updated` activities), compaction is provider-automatic with no T3-side trigger (none is added — the resolution's rejected alternative was a manual compact action), and each compaction is already an ordinary timeline entry (`kind: "context-compaction"`, `ProviderRuntimeIngestion.ts:741-761`).

The plan-history firewall is structural, and this issue locks it with guards rather than code: session activity lives in `state.sqlite`'s orchestration store; plan history is the Mercurian commit DAG whose only writers are `PlanningStore`'s guarded methods; no reactor writes commits (`CodingSessionRecordReactor` writes `coding_sessions` rows only). M-114 adds **no** new `PlanningStore` append path, no new `CommitKind`, and no session-activity mirror into any Mercurian table or `PlanStreamItem` member — the checklist states this as a negative constraint, and tests pin the enumerations. The glossary gains the two-compactions note: session compaction is bookkeeping inside the leaf; the Merges sense ("how context is assembled going forward", human-driven) never meets it on any surface.

## Decision Log

_Reviewed 2026-08-19 (`technical-plan-decision-review`; evaluations in `decision-review-m-114-session-runtime.md`). All six resolutions confirmed the plan's original choices._

- **D1 (architectural) — Minimal turn surface: reactivate `ChatView` whole.** Guardrail-conformant reuse over a header-trimmed variant or a new Mercurian surface; the header's thread-delete path (dangling session record) is an accepted interim exposure until 066's teardown.
- **D2 (architectural) — Strip depth: full reachable-surface strip.** Corrected grounding showed everything is already `planModeEnabled`-gated, making a settings-row-only strip functionally sufficient — rejected because the toggle's code would sit one upstream-owned flag default away from returning; deleting it makes the absence structural. Contract removal stays cut-over scope.
- **D3 (architectural) — Cancel-ends-the-turn lives in the decider.** One command → two events has precedent (`thread.turn.start`); reactor-side coupling would end the turn without the log recording an interrupt request (violates ADR 002's typed-events rule), and client double-dispatch leaves other clients without the invariant.
- **D4 (local) — Rollup: pull-at-read with per-connection filtered invalidation.** ADR 002 §4's mechanism verbatim; a shared invalidation layer is the named fallback if per-connection filtering measurably costs (the ADR's own revisit trigger).
- **D5 (local) — Route addresses the thread id** (`/sessions/$threadId`), not the leaf commit: zero translation at the mount; 063/064 may re-address the real screen.
- **D6 (local) — Allow-for-session ships provider-delegated granularity**, verified in the walk, with the `ClaudeAdapter.ts:4032` kind-widening as the named fallback — a wider-than-suggested grant deserves the walk's evidence first.
