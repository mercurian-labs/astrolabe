# Technical Plan — M-93: Settings becomes a place you go

_Generated from the Goal/AC of Linear issue M-93 (see the issue for the full AC). Implements backlog 023 (Phase 2 — App shell) on the t3code-fork base, under [ADR 004](../architecture/fork-baseline.md) (bounded tracking: Mercurian code additive, minimal edits in upstream-owned files). Design sources are the almagest vault notes the issue cites: Settings, T3code Settings (documented-as-built, describing this repository's own code), Environments (resolved: plumbing), Left Sidebar._

**Goal, in one sentence:** reshape the fork's settings surface into Mercurian's — the section list and page scaffolding — so trackers (050), providers (041), preferences/confirm-gates (071), and the Archived page's contents (070) each land a page instead of first reworking the shell, while the already-built "settings as a place you go" behavior (main screen replaced, sidebar yields its panel) is verified as kept.

**Scope, stated plainly (the issue's exclusions):** no page content — every section this plan adds is an empty state that names what will live there. The fork's inherited t3code sections (appearance, keybindings, git glue) are 071's open decision and stay untouched. Environments surface as at most a static statement of the local environment, which this plan defers to 040 (nothing would be stated that the app doesn't already say elsewhere; the section list stays honest without it).

## What discovery found: two of three ACs are already built

The M-95 project-tree work landed most of this issue's surface before it was picked up. Verified in code:

- **AC 1 (settings replaces the main screen; the sidebar yields).** The `/settings` layout route ([settings.tsx](../../apps/web/src/routes/settings.tsx)) renders a full-height `SidebarInset` over the main content, and `ProjectTreeSidebar` swaps its panel for settings navigation whenever the route is under `/settings` ([ProjectTreeSidebar.tsx:77–86](../../apps/web/src/components/mercurian/ProjectTreeSidebar.tsx) — "Settings takes the panel over while you are in it, and the tree returns when you leave"). Selection is a prefix match (`resolveTreeSelection` in [ProjectTreeSidebar.logic.ts](../../apps/web/src/components/mercurian/ProjectTreeSidebar.logic.ts)), so pages added later inherit the yield without touching it. Exit paths exist: Escape (handler in `settings.tsx`) and a Back row in the settings nav footer.
- **AC 3 (reachable from the Workspace group and the palette).** The sidebar's Workspace group has the Settings row ([ProjectTreeSidebar.tsx:308–320](../../apps/web/src/components/mercurian/ProjectTreeSidebar.tsx)); the palette has an "Open settings" action navigating to `/settings` ([CommandPalette.tsx:1467](../../apps/web/src/components/CommandPalette.tsx), search terms already include "preferences"); the desktop menu's `open-settings` action does the same ([AppSidebarLayout.tsx:188](../../apps/web/src/components/AppSidebarLayout.tsx)).
- **AC 2 is the gap.** The settings navigation is still the fork's flat eight-section list — General, Appearance, Keybindings, Providers, Source Control, Connections, Beta, Archive — rendered by the upstream-owned [SettingsSidebarNav.tsx](../../apps/web/src/components/settings/SettingsSidebarNav.tsx) from the `SETTINGS_SECTION_LABELS` record in [settingsSearch.ts](../../apps/web/src/components/settings/settingsSearch.ts), which `ProjectTreeSidebar` currently imports wholesale.

So this plan is one move: replace the nav panel `ProjectTreeSidebar` mounts in settings mode with a Mercurian-owned one carrying Mercurian's section list, plus the two routes that don't exist yet.

## Design

### The section list: two groups, one panel

The Mercurian settings nav shows two groups:

1. **Workspace** — Mercurian's sections, in the issue's order: **Trackers**, **Providers**, **Preferences**, **Archived**. This is the vault's Settings note made navigable: connections and preferences configured once and rarely revisited, plus the Archived page.
2. **Application** — the fork's inherited sections, untouched and still reachable: **General**, **Appearance**, **Keybindings**, **Source Control**, **Connections**, **Beta**. Their fate is 071's open decision (recorded in ADR 004's "Deferred" list); this plan neither redesigns nor hides them. The group label "Application" is a naming call this plan makes (the vault's phrasing — these "belong to surfaces Mercurian hasn't designed" and "accrete here" — names no group); it reads truthfully for theme, keybindings, and git glue without borrowing dead branding.

Where each Workspace section points:

- **Trackers → `/settings/trackers` (new)** — empty state. Copy close to the vault: connections to external issue trackers are made and managed here; issues never arrive through Settings — they enter as the starting points of plans, through import. Content is 050's.
- **Providers → `/settings/providers` (existing page, unchanged)** — the fork's provider-instances page is precisely what the vault records as a _transfer_ ("provider instances with model curation"), so Mercurian's Providers entry points at it as-is; 041 owns reworking its contents. Giving Providers a fresh empty state while a functional transferred page exists would regress live behavior (provider config powers real coding agents today) and duplicate the section.
- **Preferences → `/settings/preferences` (new)** — empty state naming 071's contents: whether a new coding-session worktree starts from origin or your local branch, the background fetch interval, and the confirm-gates on archive and delete. (Today those settings live scattered on the fork's General page; moving them is exactly the content work 071 owns.)
- **Archived → `/settings/archived` (existing page, unchanged)** — the Archive page is likewise a recorded transfer ("the Archived page as the reversibility surface"); it lists archived threads today, and 070 brings the plan-shaped contents.

Reading of the AC this encodes: "empty-state pages that name what will live there" is satisfied literally by the two sections that have no page (Trackers, Preferences) and in substance by the two whose transferred pages already _are_ what lives there pending their content issues. The alternative — empty-stating all four — was rejected as a functional regression dressed as scaffolding.

The `/settings` index redirect moves from `/settings/general` to `/settings/trackers`, so opening Settings lands on Mercurian's first section rather than the fork's. One-token edit inside the upstream-owned `settings.tsx` `beforeLoad` — within ADR 004's "minimal edits" budget. (The palette, menu, and Workspace row all navigate to `/settings` and inherit the new landing for free.)

### A Mercurian-owned nav, beside the fork's, not instead of it

New component pair in `components/mercurian/`:

- **`SettingsNav.logic.ts` (new)** — the pure section model: the two groups as data (`{ label, sections: [{ to, label }] }`), plus the active-row resolution (path equality, as the fork nav does). This is the single source the component renders from, and the thing the tests pin.
- **`SettingsNav.tsx` (new)** — renders the groups on the `ui/sidebar` primitives (`SidebarGroup`/`SidebarGroupLabel`/`SidebarMenu`/`SidebarMenuButton`, icons mapped in the component per house pattern), closes the mobile sheet on section pick, and carries the footer's **Back** row (same `canGoBack → history.back(), else navigate "/"` behavior as the Escape handler). It does **not** carry the fork footer's T3 Connect sign-in/avatar — Connect is parked by M-122 and clients build without it, so nothing user-visible is lost.

`ProjectTreeSidebar` swaps its settings-mode panel from `SettingsSidebarNav` to `SettingsNav` — a one-import edit in a Mercurian-owned file. [SettingsSidebarNav.tsx](../../apps/web/src/components/settings/SettingsSidebarNav.tsx) itself is not touched: it stays live for the dormant upstream `Sidebar.tsx`, keeping upstream merges clean per ADR 004. This is the same posture M-106 took toward `RightPanelTabs`.

**One deliberate regression, flagged:** the fork nav's per-setting search box (the `/`-focused combobox over `settingsSearch.ts`) does not come along. Its catalog is 100% fork-page settings, reproducing it means hand-copying ~130 lines of upstream UI into `mercurian/` (a reverse fork-tracking liability), and every target remains one click away under Application. Whether Mercurian's settings get their own search belongs with 071's decision about the sections that search indexes. If review disagrees, the fallback is importing the pure `searchSettings` function and re-rendering the combobox in `SettingsNav.tsx` — no upstream edit either way.

### The two empty-state pages

- **`components/mercurian/SettingsEmptyPage.tsx` (new)** — one small presentational component (icon, title, description on the `ui/empty` primitives, centered in the settings outlet), shaped like the Repositories precedent minus the `SidebarInset`/header the settings layout already provides. Shared rather than inlined because later sections (an Environments statement at 040, and any 071 outcome) start life the same way.
- **`routes/settings.trackers.tsx` (new)** and **`routes/settings.preferences.tsx` (new)** — thin file routes rendering `SettingsEmptyPage` with the copy above. `routeTree.gen.ts` regenerates via the vite plugin.

No data, wire, or server surface is touched anywhere in this plan.

### Gaps where the AC outran the repo

Only the two new routes and the section model — both introduced above. Everything else the AC names already exists and is kept, not rebuilt.

## Findings carried out of implementation

- Settings' landing page changes (General → Trackers). Anyone muscle-memorying into General is one click away; the redirect is the only behavior change to existing entry points.
- The per-setting search (and its `/` hotkey) is absent from the live settings nav after the swap — deliberate, recorded above, revisit with 071.
- The dormant `Sidebar.tsx` keeps `SettingsSidebarNav` referenced; neither is dead code to a linter nor deletable before cut-over (ADR 004).
- An Environments "static statement of the local environment" was considered and deferred to 040, per the issue's own deferral — the section list gains it when there is something true to state.
- `apps/mobile` has its own settings screens; it is parked (ADR 004 §2) and this plan does not touch it.
