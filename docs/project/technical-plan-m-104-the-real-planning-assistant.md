# Technical Plan — M-104: The real planning assistant

_Generated from the Goal/AC of Linear issue M-104 (see the issue for the full AC). Implements backlog 042 (Phase 4 — Assistant and providers) on the t3code-fork base as it stands after M-96/M-97/M-99/M-100/M-102/M-106/M-108, under [ADR 001](../architecture/local-first-runtime.md) (local-first storage seam), [ADR 002](../architecture/event-streaming-model.md) (event and streaming model — §2/§3 explicitly delegate the planning turn's frame shapes to this issue), and [ADR 004](../architecture/fork-baseline.md) (bounded tracking: Mercurian code additive, minimal edits in upstream-owned files). Design sources are the almagest vault notes the issue cites — Assistant (three resolved decisions), Plans, Commit Tree, Environments, Providers, T3code Thread (the runtime being reused) — plus the 2026-08-04 issue comment on the multi-repo grounding × single-cwd collision, which this plan resolves (Design §4)._

**Goal, in one sentence:** stand planning turns on the fork's existing provider-session runtime — a reply in a planning space is generated by the workspace planning model, grounded read-only in the project's repositories, streamed as transient frames over `mercurian.subscribePlan`, and landed as a commit (interrupted when stopped), with structured questions pausing on you and assistant plan revisions committing at equal standing — while planning stays mode-free.

**Scope fences, restated from the issue:** merge compaction responses (M-111), issue-revision proposals (M-109), technical-plan derivation (M-107), and Open-Decisions-as-suggested-messages (M-112) each cite this issue and are not built here. Coding sessions (M-114's side) are untouched; nothing in this plan writes to a working tree.

## What discovery found: the runtime exists whole; the planning side built to exactly this seam

- **The provider-session runtime is complete and provider-neutral.** `ProviderService` (`apps/server/src/provider/Layers/ProviderService.ts`) exposes `startSession` / `sendTurn` / `interruptTurn` / `respondToRequest` / `respondToUserInput` / `stopSession` / `getCapabilities`, and `streamEvents` — a PubSub whose every access is an independent subscription. Adapters exist for Claude, Codex, Cursor, Grok, and OpenCode behind one SPI (`provider/Services/ProviderAdapter.ts`).
- **The canonical event vocabulary already carries the whole behavioral contract.** `contracts/src/providerRuntime.ts`: `content.delta` with `streamKind: "assistant_text"` (streaming), `turn.completed`/`turn.aborted` with `RuntimeTurnState` including `"interrupted"` (stop), `user-input.requested` carrying `UserInputQuestion` (structured questions), `request.opened`/`request.resolved` (the enforcement channel, Design §3), and `item.*`/`tool.progress` lifecycle events (the grounding-visibility source, Design §6).
- **The planning side stopped at exactly this issue's doorstep.** `mercurian.subscribePlan` streams snapshot → commit events → synchronized over the commit store's sequence (ADR 002 §2); the pure client fold is `packages/client-runtime/src/state/planReducer.ts`; `authorKind: "assistant"` was representable but unwritten; and `mercurian/planning/wire.ts` hardcoded `hasPendingInput: false, isWorking: false` with a comment naming this issue as their producer.
- **M-97 landed the planning-model setting and predicted this consumer.** `PlanningModelSelection` (provider + model, structurally instance-free) and the pure `resolvePlanningModel` helper live in `contracts/src/mercurianWorkspace.ts`; the turn start calls the same helper against the server registry's own `getProviders` output. The client hook `usePlanningModel()` with its resolution states is the composer gate's input, already built.
- **The commit model enforces the structural invariants this issue must keep.** `CommitStore` refuses assistant forks and merges as typed errors (`AssistantForkError`/`AssistantMergeError`) — the M-94 "guarantee" resolution, landed. `ancestors` walks every parent path in append order — the transcript-assembly read a fork-resume needs.
- **The MCP door exists per session.** `prepareMcpSession` mints a per-thread `t3-code` MCP endpoint injected into provider sessions; toolkits register via `McpServer.toolkit` with the precedent at `apps/server/src/mcp/toolkits/preview/`. This is the sanctioned write path for assistant plan revisions (Design §5).
- **The multi-repo collision is confirmed as the comment described.** `ProviderSessionStartInput` had one `cwd`; the Claude adapter plumbs `additionalDirectories` end to end but echoed the cwd; Codex maps runtime mode `"approval-required"` to a `read-only` sandbox with `untrusted` approvals. Single-directory was the session shape, not a provider limit.
- **AC 6's surface half is true by construction.** The planning space is Mercurian-owned end to end and mounts no runtime-mode or interaction-mode picker; the fork's pickers live in thread components this surface never imports. ADR 004 schedules stripping the fork's own plan/default toggle at backlog 062 — out of scope here; this plan's job is the enforcement half (Design §3).

## Design

### 1. Shape: a Mercurian assistant runtime beside the store — not the orchestration bus

ADR 002 §2 already fenced this: `dispatchCommand`, the decider, and the projector remain t3code-only machinery; planning mutations are plain RPCs and the commit DAG is the durable log. So the assistant lands as a new Mercurian area, `apps/server/src/mercurian/assistant/`:

- `assistant/PlanningAssistant.ts` — canonical single-file Effect service, tag `"t3/mercurian/assistant/PlanningAssistant"`. It owns the per-plan turn lifecycle: at most one active turn per plan (a server fact, not a UI habit), the live-turn state, the fold from canonical runtime events to planning turn state, and the settle path that writes the commit. Its API: `startTurn` (called by the ws layer after a human message commits), `stopTurn`, `answerQuestion`, `frames(planId)` (fresh PubSub subscription per access), `inFlight(planId)` (snapshot composition — join-mid-turn, ADR 002 §3), `status` + `changes` (the tree's two new inputs), `teardownPlan`, and the MCP door's two thread-scoped calls.
- `assistant/PlanningPrompt.ts` — pure prompt assembly: the planning system appendix (identity, the one write door, repository roots by name and path, narrowed-grounding statement) and the transcript preamble for fork-resume. Pure functions, co-located tests.
- `assistant/GroundingFold.ts` — pure fold from `item.*`/`tool.progress`/`request.opened` runtime events to `PlanGroundingItem`s, deduplicated by key. Separate file because it is the one piece with per-provider vocabulary drift; table-driven tests pin it.
- `planning/PlanTurnRegistry.ts` — the structural facts of running turns (plan, turn, thread, tip), as its own leaf service so the dependency arrows stay acyclic: `PlanningStore` reads it for the human-write guard, `PlanningAssistant` claims and advances it, neither depends on the other for it.

### 2. Sessions: continue at the tip, rebuild on fork

A provider session is linear; the plan's history is a DAG. The reconciliation follows the vault's own line — "the assistant only ever continues from where things left off":

- Per plan, the assistant keeps the live session's `threadId` (a fresh branded `ThreadId` minted per session), the instance it resolved to, and the commit the session's context stands at (the tip it last settled on).
- **Continuation** (the common case): the new human message hangs from the session's tip, the same instance and model still resolve → `sendTurn` on the existing session. The provider's own context carries the conversation; nothing is re-sent. A continuation whose session turns out dead falls back to a rebuild, moving the turn to the new thread before the old session is torn down.
- **Fork, first turn, model change, or dead session**: stop the old session, `startSession` fresh, and open the turn with a transcript preamble assembled from `CommitStore.ancestors(parentCommitId)` projected through the planning payload schemas — messages as dialogue, plan revisions as markers, the current plan text last, budgeted against the provider input cap with oldest-first elision. Today every path is single-parent (merges are M-111); recorded in Gaps.
- The registry claim happens **before** anything reaches the provider, so the MCP door resolves the thread to the turn even for a tool call racing the first delta.
- Nothing about sessions is persisted in `mercurian.sqlite`. The record is the commit; the session is runtime state (ADR 002 §3).

### 3. Read-only and mode-free, enforced at the runtime — not asserted in a prompt

- **Sessions open at the most restrictive tier the contract has:** `runtimeMode: "approval-required"`. For Codex that is a `read-only` sandbox — filesystem-enforced. For Claude it is the default permission base, which routes every consequential tool through `canUseTool` → `request.opened`.
- **The runtime auto-answers every approval request; no approval ever surfaces.** `file-read` → approve for the session; `command`, `file-change`, and everything else → decline (`auth_tokens_refresh` is adapter plumbing and is left alone). Planning therefore never shows an approval, never waits on one, and never lets a write through — the read-only invariant holds even if a provider tries.
- `interactionMode` is never passed. Claude's plan permission mode was considered for the read-only half and declined: its preset biases the conversation toward propose-then-implement and ends turns through `ExitPlanMode` capture — the inverted plan-mode model the vault explicitly rejects for planning.

### 4. Multi-repo grounding: native multi-root, visibly narrowed where a provider can't

Resolving the 2026-08-04 comment, adopting its option 1:

- `ProviderSessionStartInput` grows `additionalDirectories` — an additive edit in an upstream-owned contract file, within ADR 004's minimal-edits budget.
- **Claude adapter, one-line edit:** extra roots ride the SDK's `additionalDirectories` beside the cwd. **Codex needs no session-shape change:** the planning tier's `read-only` sandbox does not confine reads to the cwd. The prompt preamble names every root for both — `additionalDirectories` grants access, the preamble grants awareness.
- **Capability gate, not failure:** `ProviderAdapterCapabilities` grows `groundingRoots: "multi" | "cwd-only"`. Claude and Codex declare `"multi"`; Cursor, Grok, and OpenCode declare `"cwd-only"` until someone verifies otherwise (Gaps).
- The plan's cwd is the project's first repository in the project-set order, the rest ride `additionalDirectories`. A project with no repositories grounds nothing and says so in the preamble — planning without grounding is legal.
- **When the provider is `"cwd-only"` and the project has more than one repository, grounding proceeds — narrowed, and visibly so.** The turn opens on the first repository alone, and the turn frames plus the settled commit carry a `groundingScope` fact naming the repositories that were out of reach; the timeline renders it as a quiet notice above the grounding fold. The decisive call: narrowed-but-visible over a gated composer — blocking all planning because one repository of three is unreachable serves nobody, while _silent_ narrowing is exactly what "grounding is visible" forbids. Candidate Open Decision for the vault; flagged in Gaps with this behavior as the working resolution.

### 5. The write door: a planning MCP toolkit, backed by the commit guarantee

- `apps/server/src/mcp/toolkits/planning/` (`tools.ts`, `handlers.ts`, tests) — the preview-toolkit shape. Two tools: `save_plan_revision({ text })` (the artifact's whole text — snapshot semantics) and `read_plan({})`. The handlers map the calling session's `threadId` to its live planning turn — a thread that is not an active planning turn is refused, so coding sessions never see plan-revision powers — and write through `PlanningStore` with `authorKind: "assistant"`, parented on the turn's current tip. The revision emits on `subscribePlan` as an ordinary `commit` event carrying `planText`: equal standing, live in every window, mid-turn.
- The system-prompt appendix names `save_plan_revision` as the one way to change the plan and forbids claiming an edit without calling it.
- **The structural invariant is the store's, not the prompt's.** Assistant writes pass `authorKind: "assistant"` through to `CommitStore.append`, where `AssistantForkError`/`AssistantMergeError` refuse any assistant commit that would fork or merge. With no issue-revision write existing anywhere yet, "never revises the issue unilaterally" is vacuously true until M-109 (Gaps).
- The cross-window race — a human committing onto the turn's line mid-turn — is closed at the store boundary: while a plan has an active turn, human `appendMessage`/`savePlanRevision` refuse with `PlanTurnActiveError` ("the assistant is replying — stop it to act").

### 6. Grounding visibility: folded from item lifecycle, persisted on the commit

- `GroundingFold.ts` folds runtime events into `PlanGroundingItem = { kind: "file-read" | "search" | "listing" | "other", label, detail? }`, per-provider labels normalized. Command-shaped and file-change-shaped items cannot occur (declined at §3's policy) — the fold drops them defensively.
- Each item emits live as a `turn-grounding` frame and accumulates on the in-flight turn (bounded, with an explicit "…and more" marker at the cap); at settle, the list lands in the assistant message's payload. The timeline renders one collapsed row per reply ("Consulted N items"), expandable per item — for the streaming turn and the settled commit alike.

### 7. The store grows assistant writes; the message payload grows the turn's facts

- `appendAssistantMessage` and `saveAssistantPlanRevision` — the existing writes' shapes with `authorKind: "assistant"` and the new payload facts. Assistant writes always name their parent explicitly.
- `MessageCommitPayload` grows optional fields (the `attachments` precedent — every existing commit keeps decoding): `interrupted?`, `grounding?`, `groundingScope?`, and `question?: { questions, answers? }` — a question stopped-past stays recorded, unanswered.
- The wire `PlanMessage` mirrors the same optional fields; `wire.ts` maps them straight through. `PlanQuestion` is a Mercurian wire schema structurally matching `UserInputQuestion` — copied, not imported, so the planning surface's contract does not couple to the provider-runtime contract's evolution.
- Settle writes exactly one message commit: full text on `turn.completed`; partial text plus `interrupted: true` on `turn.aborted`, on stop, and on any abnormal session end. After the commit lands, the turn leaves the registry and its `turn-settled` frame closes the client's in-flight state; the commit event itself is the record arriving.

### 8. The wire: transient turn frames on `subscribePlan`, in-flight state on the snapshot

Executing ADR 002 §3's delegation. `PlanStreamItem` grows transient members — commits stay the only durable events:

```
| { kind: "turn-started";  turnId, parentCommitId, groundingScope? }
| { kind: "turn-delta";    turnId, textDelta, offset? }
| { kind: "turn-grounding"; turnId, item: PlanGroundingItem }
| { kind: "turn-question"; turnId, questions: PlanQuestion[] }
| { kind: "turn-question-answered"; turnId }
| { kind: "turn-settled";  turnId }          // the commit event follows; the commit is the record
| { kind: "turn-refused";  reason: "unset" | "no-instance" | "model-unavailable" | "turn-active" }
```

- `PlanDetail` gains `inFlightTurn?` so a window opened (or reconnected) mid-turn joins coherently from the snapshot — which **resolves ADR 002's open question on reconnect-mid-turn buffers: no bounded replay is built.** The ws handler attaches its frame feed before the snapshot read, and each delta carries the offset of the reply before it, so a frame replayed across the join folds away idempotently on the client.
- Frames carry no sequence and are never resumable — they are transport (ADR 002 §3). The `synchronized` marker's meaning is unchanged (caught up on _commits_).
- `turn-refused` is the honest backstop behind the composer gate: the append succeeded, and the stream says why nothing is streaming.

New methods on `MERCURIAN_WS_METHODS`: `stopPlanningTurn` and `answerPlanningQuestion` — plain RPCs through the full convention chain. No `startPlanningTurn` RPC exists: turns start server-side when a human message commits (`appendPlanMessage` and `createPlan` handlers call `startTurn` in a detached fiber) — the assistant responds; it is never invoked.

### 9. Status signals: the tree's two constants become real

- The ws `subscribeTree` handler composes `PlanningAssistant.status` into the rows — `isWorking` while a turn streams, `hasPendingInput` while a structured question waits — read-layer composition per ADR 002 §4, never a cross-store transaction.
- The tree's re-emit trigger merges `PlanningAssistant.changes` alongside `PlanningStore.changes`.
- "Unseen updates" needs nothing new: assistant commits bump `updatedAt` through the store writes (M-99).

### 10. Client: the reducer folds turns; the composer streams, stops, gates

- `planReducer.ts`: `inFlightTurn` folds from the new frames; the settled commit and `turn-settled` converge in either order (an assistant message commit closes the in-flight turn; a mid-turn revision closes nothing); `turn-refused` surfaces as a transient notice. Pure, co-located tests — web and mobile share it unchanged.
- `PlanTimeline.tsx`: the streaming reply below the last commit on its own path (live text, grounding fold, narrowed-grounding notice), the question card (submit → `useAnswerPlanningQuestion`; no free-text lane — the composer is right there), settled assistant messages with the persisted grounding fold, the question-and-answers record, and an **Interrupted** badge — which forking past needs nothing new (M-108's act-from-anywhere already forks from any commit).
- `PlanComposer.tsx` + `PlanComposer.logic.ts`: while a turn is live the send action becomes **Stop** and send stays unavailable (no queueing); the gate (AC 7) renders an explicit inline notice when `usePlanningModel()` resolves to `unset` or `unresolved` — typing is not blocked, sending is, with the reason stated. The draft space shows the same notice informationally without blocking: a plan can be born without an assistant.
- `apps/web/src/state/mercurian.ts`: `useStopPlanningTurn()`, `useAnswerPlanningQuestion()` via the existing command factories on the shared write scheduler.

- `docs/internals/glossary.md`: **Planning turn** and **Grounding** join the Projects-and-plans section; the planning-space, composer, and issue-status entries updated to the now-real producers.

## Gaps and findings carried out of discovery

- **Candidate Open Decision for the vault (predicted by the issue comment):** what the user sees when a provider cannot ground across all of a project's repositories. This plan ships narrowed-but-visible grounding (§4) as the working behavior; the vault's Assistant note should record the decision (or overturn it).
- `groundingRoots` capability declarations for Cursor, Grok, and OpenCode are conservative defaults (`cwd-only`), not verified limits — each adapter deserves a look as follow-up, and the gate-don't-fail behavior makes upgrading a one-word change per adapter.
- **AC 5's "never revises the issue unilaterally" is vacuously true in this codebase**: no issue-revision write path exists anywhere yet. M-109 builds issue revisions; the MCP toolkit deliberately exposes no issue-shaped tool.
- **Transcript assembly assumes single-parent ancestor paths** — true today. When merges land, `PlanningPrompt`'s fork-resume needs the compaction semantics M-111 owns; recorded so M-111 knows this seam exists.
- **ADR 002 is still Proposed** (acceptance tracked on M-91). This plan implements its §2–§4 concretely; if M-91 review amends §3 the frame design here moves with it.
- **The fork's own plan/default interaction-mode UI remains in t3code surfaces** until backlog 062 strips it (ADR 004 §2) — out of scope here and invisible from any planning space.
- **Upstream tracking risk is concentrated in two files**: the `ProviderSessionStartInput` widening and the one-line `ClaudeAdapter` edit ride upstream-owned code that merges weekly; both are additive and small, per ADR 004.
- **No per-session system-prompt seam exists on the provider contract**, so the planning appendix rides as the head of a fresh session's first turn input rather than as a system prompt. If the contract ever grows one, `PlanningPrompt.planningSystemAppendix` is the one producer to re-point.
