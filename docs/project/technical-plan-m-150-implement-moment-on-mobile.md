**Goal, in one sentence:** put the whole implement moment on the phone — try-to-implement from any checkpoint, the advisory stale-plan warning, the readiness gate with its analyzing state, the per-repository confirmation sheet that lands sibling branches, the recorded-readiness badging — entirely as a client rendering of the machinery the desktop gate already runs server-side, ending at a configured coding-session draft that hands off to M-151.

**Scope fences:**

- **Zero server, contract, or shared-reducer work.** The gate evaluation, verdict recording, short-circuits, split landing, and session birth are all server-owned (`apps/server/src/mercurian/assistant/PlanningAssistant.ts:1194` `tryImplement`, `PlanningStore.saveSplits`, `recordImplementVerdict`) and already cross the wire typed (`packages/contracts/src/rpc.ts:989–1027`, `mercurian.ts:374–457, 697–745`). The shared reducer already folds every implement stream item and the `readyCommits` map (`packages/client-runtime/src/state/planReducer.ts`). Mobile re-evaluates nothing.
- **The session view is M-151's.** This issue ends when `startCodingSession` succeeds; where the user lands afterwards is an interim seam (§5).
- **Start-all is deferred to M-151** (judgment call, rationale in §4).
- **Columns view, graph arrangement/drawing settings, plan-artifact editing** — out, per the M-147/M-149 fences.
- **No new native modules, no new dependencies.**

## Design

### 1. What is already built end-to-end, and what mobile actually adds

Everything behavioral about the gate exists and is client-agnostic:

- `tryImplement {planId, parentCommitId?}` refuses synchronously (`PlanTurnActiveError`, `ImplementBlockedError`), **short-circuits recorded verdicts server-side** — a `ready` verdict publishes an `atomic` proposal with no agent session and no model requirement; a fully-covered `needs-split` publishes `already-covered` (`PlanningAssistant.ts:1194–1248`) — and otherwise runs the analysis turn, streaming `implement-started` / `turn-grounding` / `implement-analyzed` / `implement-failed`.
- `confirmSplits` lands sibling plan-revision commits transactionally, each born with a `ready` verdict; cancel/failed lands nothing. `cancelImplementProposal` clears the server-held proposal. `startCodingSession` validates readiness server-side (`CodingSessionBlockedError: not-ready | repository-mismatch | …`) and answers `{commitId, threadId}`.
- The shared reducer already gives any subscribed client `detail.implementProposal`, `detail.inFlightImplement`, `readyCommits` (keyed map), and `implementFailure` — mobile's plan atom (M-146 bridge) carries all of it with **no reducer change**.

So M-150 is: hoist three small pure-logic modules, one flow controller, two sheet routes, one native confirm, badges, and copy parity. The AC's hardest-sounding clause — "confirming lands them as sibling branches, cancelling lands nothing" — is a server truth this plan merely renders.

### 2. Hoist the implement-moment logic to `packages/client-runtime`

Mobile needs the same pure functions web uses, and copying them is the drift the scoping assessment warned against. Move — don't fork — into `packages/client-runtime/src/state/` (subpath-export each, matching `./state/mercurian-planning`):

- **`planSplits.ts`** (+ test) ← `apps/web/src/components/mercurian/splits.logic.ts` whole: `existingSplitsAt`, `partitionProposal`, `confirmPayload`, `implementDisabledReason`, `ImplementFlowEvent`/`implementFlowAction`. Depends only on contracts + `PlanGraph` types.
- **`planFreshness.ts`** (+ test) ← the staleness half of `SpecArtifact.logic.ts` (`planMayBeStaleAt`, `stalePlanLeafIds`, `staleSpecLeafIds`) **and** the two copy constants from `PlanFreshness.ts` (`PLAN_MAY_BE_STALE_LABEL`, `PLAN_MAY_BE_STALE_DESCRIPTION`) — one source for the warning's words on every client. The rest of `SpecArtifact.logic.ts` (editor state, labels) stays web-local.
- **`codingSessionDraft.ts`** (+ test) ← the portable core of `apps/web/src/components/mercurian/codingSessionDraft.logic.ts`: `CODING_SESSION_RUNTIME_MODES`, `localBranchOptions`, `seedBaseRef`, the `CodingSessionDraft` shape and `startCodingSessionPayload`. The web-only pieces (`codingSessionModelGroups`, `seedCodingSessionModelSelection`) depend on web's provider-instance helpers (`apps/web/src/providerInstances.ts` et al.) and stay behind in the web file — mobile has its own model machinery (§5).

Web keeps working through updated imports (no behavior change; the moved tests move with their modules). If M-148/149 land first and chose a different shared home for plan-graph logic, these three follow the same home — the decision that matters here is _shared, not copied_.

`implementFailureNotice` (web `PlanComposer.logic.ts:105`) is deliberately **not** hoisted: notice presentation is per-surface; mobile writes its own two-line mapping with the same wording (§6) rather than importing web's composer-notice type.

### 3. One flow controller, three entry points (AC 1, AC 2)

**`useImplementFlow`** — `apps/mobile/src/features/mercurian/useImplementFlow.ts` (+ co-located test for its pure transition core, which is mostly `implementFlowAction` already). Mirrors `PlanningSpace.tsx:508–544` exactly:

```
beginImplementFrom(commitId | null):
  resolved = resolveImplementFrom(graph, commitId ?? position head)   // session leaves act from their parent
  implementFlowAction({kind:"invoke", planMayBeStale: planMayBeStaleAt(graph, resolved)})
    → "show-warning"      → native confirm (below)
    → "evaluate-readiness" → tryImplement({environmentId, input:{planId, parentCommitId: resolved}})
  on confirm-"Review plan"  → implementFlowAction({kind:"review-plan"}) → open the plan artifact view (M-147's toggle; callback prop)
  on confirm-"Continue"     → implementFlowAction({kind:"continue-anyway"}) → tryImplement(...)
```

**The stale-plan warning is the native confirm**, not a sheet: title `PLAN_MAY_BE_STALE_LABEL`, message `` `${PLAN_MAY_BE_STALE_DESCRIPTION} — the plan may be stale.` ``, buttons **Review plan** / **Continue anyway** — `Alert.alert` on iOS, `showConfirmDialog` on Android (the established split; `ConfirmDialogHost` is already mounted). Desktop uses an `AlertDialog` for exactly this two-choice advisory shape; the native alert is the phone's version of that shape, and a formSheet route would be ceremony. Dismissing the alert (outside-tap/back) does nothing — advisory, nothing landed, matching web's dismissable `AlertDialog`.

The three entry points, each calling the same `beginImplementFrom`:

1. **The planning space's own act** (desktop: the composer-rail Implement button) — an Implement action in whatever action affordance M-147's composer established, acting from the current position, disabled with the reason from `implementDisabledReason({turnActive, planTextEmpty, isDraft:false})` (`turnActive` covers `inFlightTurn` _and_ `inFlightImplement`; mobile has no client-local draft plan spaces — M-146 excludes plan creation — so `isDraft` is constantly false, noted in code).
2. **History Thread rows** (M-148) — per M-149's touch-grammar ruling, acts live in the node sheet: a row's disclosure summons the same node sheet the map uses, and the act there is entry point 3. No per-row implement button (desktop thread rows don't have one either — the act is in the popover).
3. **The node sheet's "Implement from here"** (M-149's stub) — wire the stubbed act to `beginImplementFrom(node.commitId)`. Same label as desktop (`PlanNodePopover.tsx:480`). The act is offered per the shared `offeredActs` (every non-session node; session leaves resolve to their parent via `resolveImplementFrom`), so mobile offers it exactly where desktop does.

**Proposal arrival opens the sheet.** The planning-space screen watches `detail.implementProposal` (undefined → defined, guarded by `turnId` ref so re-renders don't re-present) and navigates to the implement sheet route — the mobile mirror of `PlanningSpace.tsx:399–403`. This also means a proposal produced by a desktop window while the phone watches the same plan presents on the phone, which is the web behavior today; accepted for parity.

### 4. The implement sheet (AC 3, 4, 5)

**`PlanImplementSheet`** — `apps/mobile/src/features/mercurian/PlanImplementSheet.tsx`, registered in `Stack.tsx` as a `formSheet` route (Android per the Git-sheet precedent), params `{environmentId, planId}` only — the sheet reads the live proposal from the plan atom itself (serializable-params rule; the plan subscription is already the source of truth on every client). Pure presentation state derives through the hoisted `partitionProposal`/`existingSplitsAt`/`confirmPayload`; card edit state (`SplitCard.removed`, edited text) is component state, exactly like web's `SplitSheetPanel`.

States, mirroring `SplitSheet.tsx` string-for-string (the copy _is_ the AC-5 deliverable — every string below already passed the 2026-08-12 vocabulary resolution on desktop):

- **Ready (`verdict.kind === "atomic"`)** — "This plan is ready to implement." / "A coding session will run in _{repositoryName}_." Primary action **Start a coding session** → opens the draft sheet (§5) for `{commitId: proposal.parentCommitId, repositoryId, repositoryName}` and dismisses this sheet. Nothing lands in history — the server never wrote anything for a ready verdict (AC 3's "nothing lands" is already true; the client just must not call `confirmSplits`).
- **Needs split (`"needs-split"`)** — header "This plan covers work in more than one repository. A coding session works in one repository at a time.", then the agent's rationale; **already-split rows** ("This repository already has its own plan" + Go to plan → jump, §below) for repositories with landed projections at this commit; one **card** per fresh proposal: repository name, the projected plan in a multiline `TextInput` (editable in place — the sheet is the overrule), a remove action. Footer: **Cancel** and — only while `confirmPayload(cards) !== null` — **Add a plan for each repository**. (`confirmPayload === null` renders _no_ confirm action: the zero-to-create defect guard.)
- **Already covered (`"already-covered"`)** — jump rows only, no confirm action.
- **Post-confirm (landed jump list)** — on `confirmSplits` success the server clears its proposal, so the sheet holds the landed rows in local state (zip returned commit ids with confirmed cards, web `PlanningSpace.tsx:826–838`) and re-renders as: "You added a plan for _{repositoryName}_" per row, with **Go to plan** and **Start a coding session** (draft sheet for that landed commit). Footer becomes **Done**. Confirming also **pins the position** at the commit tried from, `{_tag:"at", commitId: proposal.parentCommitId, live:false}` — the 2026-08-12 stay-put resolution — through M-148's position store (fallback if the stack kept position in screen state: lift it into a small `planPositionStore.ts` module in the feature, `use-thread-selection.ts` precedent, as part of this issue). Going somewhere is only ever a jump the user taps (`positionAfterPick`).
- **Dismissal** (Cancel, swipe-down, Android back) while a proposal is live → `cancelImplementProposal` — "cancelling lands nothing" is the server clearing a proposal that never touched history. Wire it once in the route's remove/unmount path (`beforeRemove`), so gesture-dismiss and Cancel are the same act. Dismissal from the landed state cancels nothing (there is no proposal left) — it just closes.

**Start-all is deferred to M-151** (judgment call): desktop's Start all exists, but it drags in per-repository base-ref preloading (`CodingSessionBaseRefLoader` per landed row) purely to skip N draft sheets, M-150's AC never asks for it, and it is session-lifecycle sugar squarely in M-151's territory. The landed rows' per-repository **Start a coding session** covers the flow; recorded here so the omission is a decision, not drift.

**Analysis in flight** is _not_ a sheet state — it renders in the conversation (§6), as on desktop. If the sheet is somehow open with neither proposal nor landed rows (races), it closes itself.

### 5. The session draft sheet, and the M-151 boundary (AC 3)

**Boundary decision, stated:** M-150 **owns the draft sheet** — AC 3 says "a session draft opens directly", and the sheet is small, sheet-shaped, and built from parts mobile already has. M-151 owns everything after `startCodingSession` succeeds: the session screen, following/steering, editing a _drafted_ session's configuration from inside the session surface, draft persistence/re-entry, and start-all. The handoff seam is one navigation: on Start success, navigate to the session's thread. **Interim destination: the existing `Thread` route** (`{environmentId, threadId}` — the session runs as a real orchestration thread, and mobile's thread screen renders those today; `GitConfirmSheet` already navigates exactly this way). M-151 re-points this one `navigate` call at its session view. This is the cheapest honest seam: it works the day M-150 lands, and it is one line to move.

**`CodingSessionDraftSheet`** — `apps/mobile/src/features/mercurian/CodingSessionDraftSheet.tsx`, `formSheet` route, params `{environmentId, planId, parentCommitId, repositoryId, repositoryName}` (all strings — a draft is client-local until Start, so the params _are_ the draft's identity; web's `PlanningSpace.tsx:214` materializes the same five facts into its store). Fields, mirroring web's sheet on mobile's own machinery:

- **Repository header** — name + "Implements commit {parentCommitId.slice(0,8)}".
- **Base branch** — refs for the repository's path from mobile's `vcsEnvironment` (`apps/mobile/src/state/vcs.ts`; loading pattern per `new-task-flow-provider.loadBranches`), repository path resolved from the repositories snapshot — bridge `createMercurianRepositoryAtoms` in `apps/mobile/src/state/mercurian.ts` if M-146 didn't already (`@t3tools/client-runtime/state/mercurian-repositories`, the one-liner convention). Seed via hoisted `seedBaseRef` (default, else current); filter via `localBranchOptions`.
- **Start from origin when available** — a switch, seeded from the environment's settings snapshot like web seeds `newWorktreesStartFromOrigin`.
- **Runtime mode** — the hoisted `CODING_SESSION_RUNTIME_MODES` (Supervised / Auto-accept edits / Full access — deliberately desktop's Mercurian label set, _not_ the T3 thread-settings label set, so the same feature speaks the same words on both clients), default `full-access` as on web.
- **Agent and model** — mobile's own `lib/modelOptions.ts` machinery (`ProviderGroup`/`ModelOption`, the `NewTaskDraftScreen` picker pattern); the payload needs only `ModelSelection {instanceId, model}`. Sticky **last-used session model** persists through mobile preferences (the one persisted fact; web's `lastModelSelection` analog). No available model → Start disabled with "Install and enable an agent before starting a coding session."
- **Start** — `startCodingSession({environmentId, input: startCodingSessionPayload(draft)})`; disabled until base ref + valid model (web's `canStart`); on success navigate per the seam above; on refusal (`CodingSessionBlockedError` etc.) surface the error inline and stay open.

**No persisted draft store on mobile** (judgment call): web's zustand/localStorage store exists so desktop can re-offer abandoned drafts; on the phone a dismissed configuration sheet is simply gone — "a draft you never start never existed" — and M-151 can introduce persistence when its draft-editing AC needs it. Recorded as a deliberate divergence.

### 6. The analyzing state, composer gating, and failure notice (AC 1's wait, AC 4's cancel-nothing)

In the M-147 conversation timeline, while `inFlightImplement` is visible on the rendered path (same ancestor-closure filter the stack uses for `inFlightTurn`):

- An **analyzing card**: spinner + "Checking whether this plan is ready to implement. A coding session works in one repository at a time." + **Stop** → `stopPlanningTurn` (the wait explains itself — the vault's narration rule; exact desktop copy, `PlanTimeline.tsx:274`). Grounding lines fold in if M-147 built a grounding fold; otherwise the card ships without them (noted as a stack-follow-up, not a blocker — the narration is the AC-bearing part).
- The composer treats `inFlightImplement` as `turnActive` (send gated, one live thing per plan), and the Implement action disables via `implementDisabledReason`.
- `implementFailure` (from the shared reducer) surfaces through M-147's composer notice slot: `no-proposal`/`invalid-proposal` → "The assistant couldn't produce a usable analysis; nothing landed.", `provider-error` → same tail, `stopped` → quiet (the user did it). Wording mirrors web's `implementFailureNotice`; mapping lives mobile-side (§2 rationale).

A short-circuited try (recorded verdict) publishes `implement-analyzed` with **no** `implement-started`, so the proposal arrives with no analyzing card and no wait — the badge-to-sheet path costs nothing, which is AC 6's badge earning its keep. Nothing to build: the reducer already folds proposal-without-in-flight (M-107 §A4), and §3's watcher only cares about the proposal landing.

### 7. Readiness and staleness badging parity (AC 6, AC 2's visibility)

`readyCommits` is already in the mobile plan state (shared reducer). This issue supplies the rendering and guarantees the predicate matches desktop:

- **`MercurianBadges.tsx`** (feature-local): `ReadyBadge` — "Ready to implement", emerald pill (`StatusPill`-style, `bg-emerald-500/15` tone per web); `StalePlanBadge` — `PLAN_MAY_BE_STALE_LABEL`; `StaleSpecBadge` — "Spec stale", amber. One component set so every surface renders the same chip.
- **Where:** M-148 thread rows (badge slot beside effects — fill the stub if M-148 left one, add the slot if not), M-149 node sheet's readiness/staleness indicator block, and M-149 map nodes' corner status dots if the stack wired readiness into them (the sheet is the authoritative text carrier per the map's zoom-fade division — dots are M-149's own AC and not re-litigated here).
- **Predicates:** ready = `readyCommits.get(commitId)`; stale plan/spec = the hoisted `stalePlanLeafIds`/`staleSpecLeafIds` — the _same_ functions desktop calls, which is what makes "matches what desktop shows for the same history" structural rather than aspirational.

## Gaps and findings carried out of discovery

- **The entire mobile Mercurian layer is unbuilt today** — `grep -r mercurian apps/mobile/src` is empty and all five stack branches point at main `d1731ae88`. This plan's file-level integration points into M-146–M-149 surfaces are therefore expectations from their ACs, not read code; the Stack-seams table and per-section fallbacks bound the risk. Re-verify each seam against the actual stack code at implementation time, and prefer the stack's real shapes over this plan's guesses about them.
- **Web-local logic mobile needs is not yet shared** — §2 is the fix; `PlanGraph.logic`/`PlanPosition.logic`/`PlanNodePopover.logic` hoists belong to M-148/149 and are prerequisites here only if this issue reaches implementation first.
- **Mobile has no provider-instance model-group helpers** matching web's `codingSessionModelGroups`; §5 deliberately uses mobile's `lib/modelOptions.ts` instead of porting web's. The two derive from the same server catalog, so parity holds at the data level.
- **`ImplementBlockedError` reasons** (`plan-empty`, `model-unset`, `no-instance`, `not-signed-in`, `model-unavailable`) surface on the `tryImplement` promise, not the stream. The flow controller must render these as a composer notice/toast rather than swallowing `null` — web leans on its composer gate to make them rare; mobile (M-147's gate covers the send path, not the implement path) should show the reason plainly.
- **One-turn-per-plan races** (`PlanTurnActiveError` when a desktop turn is live) — same rendering path as blocked reasons; nothing special.
