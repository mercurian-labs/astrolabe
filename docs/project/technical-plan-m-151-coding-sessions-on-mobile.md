# Technical Plan — M-151: Coding sessions on mobile

_Generated from the Goal/AC on Linear issue M-151 (2026-08-20). Grounded against `main` at `d1731ae88`, after M-110/M-114/M-117/M-118 landed coding sessions end to end on web. **Stack note:** the branch `venk/m-151-coding-sessions-on-mobile` stacks on `venk/m-150-implement-moment-on-mobile`; below it sit `venk/m-149` (Checkpoint Graph map on touch), `venk/m-148` (history Thread view), `venk/m-147` (mobile planning space), and `venk/m-146` (mobile plan list). Those branches exist but currently sit at `main`'s tip — their plans are being authored in the same wave — so this plan treats their designed capabilities as present, cites their issues rather than files for anything they own, and names every seam where the two plans must meet. Product sources consulted in the almagest vault: **Mobile App** (the focused subset, touch divergences), **Coding Sessions** (runtime modes, four approval responses, checkpoints/revert, born-as-a-draft), **Coding Session View** (timeline, header git acts, composer, review loop), **Issue Status**. Governing ADRs: 001, 002, 004 (`docs/architecture/fork-baseline.md`)._

**Goal, in one sentence:** give the phone a window onto a coding session — its own screen with the streaming turn timeline, the four-response approval flow, per-turn diffs with line comments that ride the next message, revert, mode/provider/model visibility, and the finishing git acts — plus the session draft the implement moment hands off to, by re-addressing the mobile client's existing thread machinery at a Mercurian session route rather than rebuilding any of it.

**Scope fences:** M-150 owns the implement gate on mobile — readiness, the stale-plan warning, split confirmation — and ends at the session-draft handoff; this plan owns the draft surface itself and everything after (its own AC covers "editable until its first turn starts"). M-152 owns push notifications; this plan builds no delivery and only keeps the signals and deep-link address it will need. The plan list, planning space, history views, and graph map are the stack below (M-146–M-149); this plan adds **Open session** acts to the surfaces they land, not the surfaces themselves. No server change of any kind is made here — discovery confirmed every server-side semantic the AC needs already holds client-agnostically. Desktop/web are untouched. Teardown, browser preview, terminal-output-as-context chips, and the session's standing Plan tab stay out (see §6).

**Vocabulary:** "Session" on a mobile surface always means a Mercurian coding session; the t3code thread it references never surfaces by that name. "The shell" is the adapted upstream mobile app, per the Mobile App vault note.

## Discovery Summary

**The key question — how much of mobile's thread machinery re-points at coding sessions — has a precise answer: nearly all of it.** A coding session is a t3code thread (`coding_sessions` rows carry `threadId`; the web session screen is `ChatView` mounted at `/sessions/$threadId` behind a Mercurian header). Mobile's whole thread surface is addressed the same way: `ThreadRouteScreen` and its satellite screens — review, review-comment composer, terminal, files, and the four git sheets — all key off `threads/:environmentId/:threadId` route params, and `useThreadSelection` derives everything from those params on _any_ route that carries them (`use-thread-selection.ts:141-144`). So a Mercurian session route that renders `ThreadRouteScreen` with the session thread's ids inherits, with zero new wire work: the streaming turn feed with folded/expandable work-log rows and settled-turn folds (`ThreadFeed.tsx`, `thread-work-log.tsx`, turn folds at `threadActivity.ts:1242-1259`) — AC 1; the approval and structured-question cards with responses dispatched through the shared contract (`PendingApprovalCard.tsx`, `PendingUserInputCard.tsx`, wired at `ThreadRouteScreen.tsx:762-812`) — most of AC 2; send, the Stop pill driving `threadEnvironment.interruptTurn` (`ThreadRouteScreen.tsx:216,481-498`) — AC 5; the staged model/runtime-mode editing and the provider-grouped settings sheet (`ThreadComposer.tsx:286-297,619-623,837`, `ThreadSettingsSheet.tsx`) — most of AC 6; per-turn checkpoint diffs, line-range selection, and comments that append to the next message as `<review_comment>` blocks (`useReviewSections.ts`, `ReviewCommentComposerSheet.tsx` → `appendReviewCommentToDraft`) — most of AC 4; and commit with per-file inclusion and auto-generated messages, push, and create-PR through the stacked git actions (`GitCommitSheet.tsx:41,205`, `GitOverviewSheet.tsx:114-168`) — AC 8.

**AC 3 needs no code at all.** M-114 composes `hasPendingInput`/`isWorking` onto `PlanTreeRow` at the server's tree read layer from the session thread's shell (pending approvals, pending user input, running turn), and the tree subscription rides `createMercurianPlanningAtoms` in client-runtime. The plan list M-146 lands renders those rows; a paused session flips its plan's row to awaiting-input on the phone with nothing added here. The walk demonstrates it.

**Five honest gaps, all client-side and all narrow.** (1) Mobile's approval card offers three responses — Allow once / Allow session / Decline (`PendingApprovalCard.tsx:32-56`) — but not **Cancel turn**; the contract and decider already handle `cancel` for every client, so this is one button. (2) Mobile has **no revert affordance anywhere**; the entire chain below the button is shared (`revertCheckpoint` command, decider guard, reactor, reducer), so this is UI plus one pure mapping — web computes the target as "next assistant message's checkpoint `turnCount − 1` per user message" (`ChatView.tsx:2518-2547`). (3) The feed renders no per-turn **changed-files** affordance (the raw "Checkpoint captured" activity is deliberately skipped, `threadActivity.ts:309`), although checkpoint summaries with per-file +/− counts sit on thread detail and the Review screen already builds a per-turn section for each one (`getReviewSectionIdForCheckpoint`). (4) The mobile settings sheet offers upstream's **four** runtime tiers including `auto` (`ThreadSettingsSheet.tsx:52-59`); the product names three (M-114 §2). (5) The composer **queues** messages while a turn runs ("Queue" label and queued-count footer, `ThreadComposer.tsx:317-322,826-833`), against the Coding Session View's "one turn at a time, no queueing; send and stop are one control."

**The draft has a complete precedent on each side.** Web's `CodingSessionDraftSheet` edits a local draft — immutable repository context from the recorded ready verdict, base-branch select seeded default-then-current, start-from-origin, three-tier mode, provider+model — and dispatches `startCodingSession` (client-runtime) for a `{commitId, threadId}` result, with `CodingSessionBlockedError` reasons for refusals. Mobile independently has every ingredient: cwd-addressed branch listing (`useBranches`, `new-task-flow-provider.tsx:524-543`), availability-gated model options from an environment's `ServerConfig` (`buildModelOptions`, `lib/modelOptions.ts:107-130` — enabled ∧ installed ∧ authenticated), an origin-base toggle and mode/model pickers in the `NewTaskDraftScreen` form-sheet pattern, and the repositories snapshot via `createMercurianRepositoryAtoms`.

**Two integration facts shape the design.** First, the adaptive workspace layout and hardware-keyboard scoping recognize the active thread by parsing `/threads/…` paths (`parseActiveThreadPath`, `hardwareKeyboardCommands.ts`; consumed at `AdaptiveWorkspaceLayout.tsx:291,373`) — a session route needs one regex alternation to inherit tablet split view and keyboard commands. Second, no Mercurian atom family is instantiated in `apps/mobile` today (zero grep hits); the stack below is expected to land `apps/mobile/src/state/mercurian*.ts` mirroring web's one-liners, and this plan names that as a seam rather than assuming file shapes.

**Accepted interim, recorded:** session threads live in a t3 project keyed by the repository's workspace root (`CodingSessionService.ts:323-343`), so they also appear in the shell's Home thread list under that project. Hiding them is shell-navigation work this issue does not own; the session screen is reachable through Mercurian surfaces regardless, and opening the same thread through the shell's Thread route keeps plain-thread behavior — harmless, since every session semantic that matters (cancel, revert guard, status) is server-enforced.

## Design

### 1. The session screen is the thread screen, re-addressed — one route, one context, byte-identical upstream defaults

Add a `Session` route to the root stack (`apps/mobile/src/Stack.tsx`), linking `sessions/:environmentId/:threadId` — the mobile mirror of web's `/sessions/$threadId`, and the stable deep-link address M-152's notifications will open. It renders `CodingSessionScreen` **(new** — `apps/mobile/src/features/mercurian/CodingSessionScreen.tsx`; this plan establishes `features/mercurian/` as the mobile analog of `apps/web/src/components/mercurian/`, coordinating with whatever directory the stack below lands first**)**. The screen:

- resolves the owning plan and session record by scanning the environment's Mercurian tree snapshot for a `codingSessions` entry with the route's `threadId` — exactly the web route's lookup — tolerating a missing record (a dangling thread renders with a bare "Sessions" context, the web route's temperament);
- provides `SessionScreenContext` **(new** — `features/mercurian/SessionScreenContext.tsx`**)** carrying `{planId, planTitle, sessionRecord}`;
- renders `ThreadRouteScreen` with the route's params passed through unchanged — `useThreadSelection` picks them up as it does on the Thread route.

The context is the whole seam: it defaults to `null`, every upstream consumer reads it with a hook and falls back to current behavior, so the shell's own thread screens are **byte-identical** when it is absent. This is M-117's one-prop `headerContent` move translated to a component tree four layers deep — threading session props through `ThreadRouteScreen → ThreadDetailScreen → ThreadComposer → ThreadSettingsSheet` would put a Mercurian-shaped prop bundle in four upstream signatures; the context puts one narrow read at each decision point instead (Decision D2).

Chrome differences under the context, all inside `ThreadRouteScreen`'s existing option-building code: the native header subtitle becomes _plan title · environment label_ (replacing _project · environment_, `ThreadRouteScreen.tsx:301-306`) — the session title itself is already right, since M-110 seeds thread titles from the plan and renames stick; the split-view **New task** header item (`:671-677`) is suppressed — it starts a shell thread, an act with no session meaning; everything else — git controls, terminal, files, inspector panes on tablet — stays exactly as mounted, because those are the session's own affordances (AC 8, and the vault's right-panel-as-screens reading below). Extend `parseActiveThreadPath` (`features/keyboard/hardwareKeyboardCommands.ts`) to match `/(threads|sessions)/…`, with its existing test file pinning both forms — tablet split view and keyboard commands then treat the session as the active thread with no further edits. On tablets the workspace's primary sidebar remains the shell's thread list for now — the Mercurian navigation shell is the stack below's concern; recorded, not hidden.

### 2. The four gated divergences — session-only, upstream behavior untouched

Each of the four gaps from discovery closes behind the context, so plain shell threads keep upstream behavior verbatim (Decision D3):

- **Cancel turn** (AC 2). `PendingApprovalCard` gains a fourth action rendered when the session context is present: **Cancel turn**, dispatching the existing `onRespondToApproval(requestId, "cancel")` — the decider already turns `cancel` into a turn interrupt for every client (M-114 D3), so no new wiring exists below the button.
- **Three tiers** (AC 6). Under the context, the runtime-mode rows offered by `ThreadSettingsSheet` are filtered to `approval-required` / `auto-accept-edits` / `full-access` (labels already match the product wording); a legacy `auto` value, were one ever present, stays visible as the current selection until changed — M-114 §2's rule, transferred. The composer's settings summary label additionally carries the provider display name (`ModelOption.providerLabel` is already derived) so mode, provider, and model are all visible without opening the sheet.
- **No queueing while a turn runs** (composer temperament). Under the context, when `activeThreadBusy` the composer's primary send action is unavailable and the Stop pill is the one control — the "Queue" label and the queued-count footer never render. The durable outbox itself is untouched as transport: a message composed while _disconnected_ still queues and drains on reconnect, a phone-reality divergence from the vault's "no queueing" this plan records deliberately (Decision D5) rather than smuggles.
- **Revert** (AC 7). User-message rows in the session feed carry a **Revert to this message** action (long-press menu entry plus the row affordance the feed's presentation logic yields). The target comes from `sessionFeed.logic.ts` **(new**, pure, tested**)**: mirror web's mapping — for each user message, the next assistant message bearing a turn-diff checkpoint gives `turnCount − 1` (`ChatView.tsx:2518-2547` is the reference implementation; mobile's feed entries already carry `turnId`, and thread detail carries the checkpoint summaries). The handler refuses with the existing toast pattern while a turn runs ("Interrupt the current turn before reverting checkpoints." — the decider refuses too, since M-117; the client guard is the friendly path), then confirm-gates with a destructive native alert using web's permanence copy ("This will discard newer messages and turn diffs… cannot be undone"), then dispatches `threadEnvironment.revertCheckpoint({environmentId, input: {threadId, turnCount}})`. Everything below — worktree restore, conversation rollback, later-diff discard, reducer rewrite (`threads.ts:354`), leaf-never-destroyed — is shared machinery this plan verifies in the walk and does not touch.

### 3. Each settled turn shows its changed files; the Review screen is the phone's diff panel

The vault's changed-files card ends each turn and "opens that turn's diff in the right panel"; on the phone the right panel's tabs are already screens (Review, Terminal, Files — the shell's own adaptation, blessed by the Mobile App note's subset). So, under the session context, the feed appends a **changed-files row** to each settled turn: files touched with per-file +/− counts, straight from the turn's `OrchestrationCheckpointSummary.files`. Derivation is pure in `sessionFeed.logic.ts` (join settled turn groups to ready checkpoints by `turnId`); rendering is a compact card in `ThreadFeed`'s row vocabulary. Tapping it pre-selects that turn's review section — `setReviewSelectedSectionId(threadKey, getReviewSectionIdForCheckpoint(checkpoint))`, the exported review-state seam — and navigates to the existing `ThreadReview` route, landing on that turn's diff with line-comment selection live (AC 4's read-and-comment half, already built). Comments continue to travel exactly as they do today: staged into the thread draft as removable `<review_comment>` blocks and sent with the next message — the same wire format web's loop produces, so the agent sees one convention regardless of which client commented.

### 4. The draft sheet — M-150's handoff destination, editable until the first turn

Add a `SessionDraft` form-sheet route (linking `session-draft/:environmentId/:planId/:parentCommitId` — prefix distinct from `sessions/:environmentId/:threadId` so linking never mis-matches; added to `WORKSPACE_OVERLAY_ROUTES` like the git sheets), rendering `CodingSessionDraftSheet` **(new** — `features/mercurian/CodingSessionDraftSheet.tsx`, the `NewTaskDraftRouteScreen` presentation pattern**)**. **The M-150 boundary, stated as this plan reads it from M-150's AC:** the gate — try-implement, stale-plan warning, split confirmation — is M-150's; its success path for a single-repository plan ends by navigating to this route with the ready commit's identifiers, and this plan owns everything from that navigation onward. The two plans are being authored in the same wave; if M-150's plan draws the line differently (e.g. ships a placeholder destination), reconcile at implementation time — the route name and params here are the offered contract.

The sheet resolves its facts from subscriptions rather than trusting params beyond identity: the ready verdict's `repositoryId`/`repositoryName` from the plan detail's `readyCommits` at `parentCommitId`, the repository's path from the repositories snapshot. Fields mirror web's draft exactly — immutable repository context; base branch (local branches via `useBranches({environmentId, cwd: repositoryPath})`, seeded default-then-current per `seedBaseRef`'s rule); start-from-origin toggle; the three runtime modes defaulting `full-access`; provider+model from `buildModelOptions(serverConfig)` with its availability gating, seeded sticky-last-used. Draft state lives in `codingSessionDraft.ts` **(new**, module store keyed `(planId, parentCommitId)` so reopening the implement moment resumes the shaped draft — M-110's keying — with `lastModelSelection` persisted through `mobile-preferences`; drafts themselves are in-memory only, a deliberate divergence from web's localStorage persistence recorded in Decision D6**)**. Logic (seeding, payload assembly, canStart) is pure and shared-shaped: lift `CODING_SESSION_RUNTIME_MODES`, `seedBaseRef`, `localBranchOptions`, and the payload builder from `apps/web/src/components/mercurian/codingSessionDraft.logic.ts` into `packages/client-runtime` (Mercurian-owned file, safe to move; web's imports re-point) rather than duplicating them.

**Start** dispatches `mercurianPlanning.startCodingSession` (client-runtime), on success clears the draft and navigates to the `Session` route with the result's `threadId` — on the phone you land in the newborn session, the natural flow (web deferred this as polish; nothing forbids it here). A `CodingSessionBlockedError` surfaces its contract message in a native alert with the draft intact. Until Start, nothing exists anywhere — closing the sheet abandons only local state, and "a session you shaped and never started never existed" holds by construction.

If the stack below has not already instantiated the Mercurian atom families on mobile when implementation starts, add `apps/mobile/src/state/mercurian.ts` and `state/mercurianRepositories.ts` as web-mirroring one-liners against `connectionAtomRuntime` — the factories are environment-scoped already, so multi-environment pairing needs nothing extra.

### 5. Entry points and the signals M-152 will ride

- **From the draft:** Start lands in the session (§4).
- **From the stack below's surfaces:** wherever those plans render a session — the history Thread view's session leaf (M-148), the graph map's node-detail sheet, whose acts are how touch navigates (M-149, per the Mobile App note's tap-inspects divergence), the plan list's session detail (M-146) — the act is **Open session**, navigating to `Session` with the record's `threadId` and the surface's `environmentId`. The record already carries everything needed; this plan contributes the destination and a shared `navigateToCodingSession` helper in `features/mercurian/`, and wires the acts into whichever of those surfaces exist on the stack at implementation time (a checklist item, deliberately elastic — the leaf's "full session inspectable from it" resolution says at least the map's sheet must offer it).
- **Awaiting-input** (AC 3): nothing built — server-composed row flags through the shared tree subscription, rendered by M-146's list, demonstrated in the walk.
- **For M-152:** the deep-link address (`sessions/:environmentId/:threadId`), the plan-row flag transitions, and the turn/approval events on the session thread's shell are the complete signal surface push needs; this plan verifies in the walk that an approval request flips the plan row promptly (M-114's invalidation stream) and adds nothing else. The shell's existing `agent-awareness` notification navigation is the seam M-152 re-points.

### 6. What this plan deliberately does not build

No server change (the one candidate — a decider guard — landed with M-117; none remained in discovery). No session Plan tab — the plan stands one navigation away and phone-width editing is outside the vault's subset; revisit with the stack's polish. No browser preview (vault: absent on mobile), no terminal-output-attach chips (web right-panel affordance; not in the AC), no **Start all** for splits (M-110's web affordance; the phone starts sessions one at a time), no hiding of session threads from the shell's Home list (recorded interim, §Discovery), no notification delivery (M-152), no changes to plain-thread UX anywhere (every divergence is context-gated), and no `apps/web` change beyond the draft-logic move's import re-point.

## Decision Log

- **D1 (architectural) — The session screen reuses `ThreadRouteScreen` whole behind a Mercurian route.** A purpose-built session screen recomposing `ThreadDetailScreen` was rejected: `ThreadRouteScreen` is ~870 lines of header/inspector/terminal/git glue that would be duplicated wholesale, violating the reuse guardrail M-114/M-117 set on web. Cost accepted: session chrome is expressed as gated deltas rather than owned layout.
- **D2 (architectural) — Session chrome flows through a default-null React context, not props.** Prop-threading would add Mercurian-shaped parameters to four upstream component signatures; the context touches each decision point with one hook read and leaves the shell byte-identical when absent, keeping weekly upstream merges cheap (ADR 004 §1).
- **D3 (design-conformant) — Every behavioral divergence is session-gated; plain threads keep upstream behavior.** Cancel-turn, revert, changed-files rows, and the three-tier filter are arguably good for all threads, but this issue owns Mercurian sessions, and un-gated changes to shell UX both creep scope and invite upstream-merge collisions. Revisit at cut-over.
- **D4 (local) — The route is `sessions/:environmentId/:threadId`.** Mirrors web's `/sessions/$threadId` (thread id is the session's runtime identity), gives M-152 a stable deep link, and one regex alternation buys split-view and keyboard parity.
- **D5 (design-conformant, flagged) — No queueing while a turn runs; the disconnected outbox stays.** The vault's "no queueing" is applied to the running-turn case (send-becomes-unavailable, Stop the one control — web's built semantics). The offline outbox is kept as transport because a phone without it cannot send reliably at all; this is a genuine divergence from a literal reading, recorded here for a Mobile App vault-note divergence entry rather than decided silently.
- **D6 (local) — Mobile drafts are in-memory with sticky model preference, not cold-persisted.** Web persists drafts in localStorage; on the phone the draft reopens seeded from the same gate in two taps, and durable draft storage would need the mobile persistence layer for marginal value. The `(planId, parentCommitId)` resume key — the semantic part of M-110's design — is kept.
- **D7 (design-conformant) — The changed-files card opens the Review screen at that turn.** The vault's right panel is already screens on the phone (the shell's own adaptation, inside the Mobile App subset); pre-selecting the turn's review section is the faithful translation of "opens that turn's diff in the right panel."
- **D8 (stack boundary) — M-150 ends at the draft-open navigation; M-151 owns the draft and beyond.** Read directly from M-150's AC ("a session draft opens directly and nothing lands in the history") and M-151's ("configuration is editable until its first turn starts"). The `SessionDraft` route and params are the offered contract; reconcile with M-150's authored plan at implementation time.
