# Technical Plan — M-196: The gate retires: threads implement across repositories

_Generated from M-196's Goal/AC and the almagest vault (Splits "Superseded 2026-08-28", Threads as amended 2026-08-31). Plan authored 2026-09-01 against main @ `585513fae` (M-195 merged). The implement gate — readiness analysis, verdicts, badges, split sheet — is deleted end to end; a coding session becomes project-scoped and its turns may edit every repository the project links; each repository's changes land as runtime commits on the line's branch for that repository; the turn record and git actions become per-repository. The stale-plan condition survives only as the already-built dot + popover._

**Goal, in one sentence:** starting to build from any checkpoint opens the session draft directly — no analysis, no sheet — and the session that starts spans every linked repository, with per-repository checkpoint commits, changed-files, and git actions.

**Scope fences.** The thread unification (M-197) is not this issue: the coding-session screen, the session leaf in the DAG, and the two-surface product all remain — this issue makes the session multi-repository and deletes the gate in the product as it stands. Code-turns-as-interior-commits is M-198; teardown/pool-shrink is M-115; the memory repository is M-194. Provider _capability_ is M-184's (landed): this plan only consumes its seam — `additionalDirectories` + `writableRoots` + the narrowing record — never grows the capability vocabulary. Upstream t3code threads, desktop, and mobile are untouched (`apps/mobile` has no Mercurian surface).

## Conventions Detected

- **Event-sourced core; Mercurian domain under `apps/server/src/mercurian/**`with its own additive migration sequence** (high):`Migrations.ts:29-43`is a static list of 13 entries, append-only per its own docstring and ADR 004 §1 — so retiring the verdicts table is a new`DROP TABLE`migration, never a removed entry (the Effect migrator skips ids ≤`MAX(migration_id)`, so removal would orphan the table with live FKs on every existing install).
- **Contracts change first, and `server.test.ts` partially mocks services** (high, hazard): signature changes must reach the mock in the same commit or the wire suite fails CI-only.
- **Store shape** (high): `<Feature>Store.ts` as `Context.Service` + SqlSchema, `schema.ts` types, `wire.ts` mappers, RPC in `ws.ts` with `RPC_REQUIRED_SCOPES` coverage-tested in `auth/RpcAuthorization.test.ts:16` (key set must exactly equal the RPC group).
- **Additive-optional wire evolution** (high): `OrchestrationCheckpointSummary.partial?`, `PlanRevision.split?` — optional fields are the extension mechanism; old rows decode unchanged.
- **Grounding assembly precedent** (high): `PlanningAssistant.buildRebuildMaterials` (`PlanningAssistant.ts:1096-1174`) — roots in project-link order, `reachable = multi ? all : slice(0,1)`, `cwd = reachable[0].path`, `additionalDirectories = rest`, `groundingScope` recorded and rendered as `NarrowedGroundingNotice`. Coding sessions copy this shape.
- **Tests beside sources; targeted runs only** (high): `vp test run <files>`, `tsgo --noEmit` per package; no repo-wide checks.
- **Plans in `docs/project/technical-plan-m-NNN-*.md`; conventional commits with plain-language titles** (high).

- **Stale-plan already renders as status**: orange corner dot (`data-status="stale-plan"`, `DagExplorer.tsx:1772-1781`), node-popover warning (`PlanNodePopover.tsx:331-345`, wording from `PlanFreshness.ts`), header alert popover (`DagExplorer.tsx:462-521`). No server component.
- **Checkpointing is single-tree**: `CheckpointReactor` settles with one `add -A`/`commit`/`update-ref` in one cwd (`:415-479`), marks `built` for the session's repository only (`:462-467`), and `OrchestrationCheckpointSummary.files` has no repository dimension (`contracts/orchestration.ts:323-344`). Changes in sibling members are today left dirty and swept into a partial on the next slot switch.
- **Provider start is single-root**: `ProviderCommandReactor.ts:650-669` passes `cwd` only — no `additionalDirectories`, no capability gate — while M-184's write seam (`writableRoots` on `workspaceWrite` turns, `CodexSessionRuntime.buildTurnStartParams`) sits unconsumed, its plan naming M-196 as the caller.
- **The session record is singular throughout**: `coding_sessions` (one `repository_id/branch/worktree_path/base_ref/pr_url/settled_commit_oid`), `PlanCodingSessionRecord` (`mercurian.ts:111-125`), leaf payload `PlanCodingSession {repositoryId, repositoryName, ...}` (`:363-370`), header/route (`_chat.sessions.$threadId.tsx:151-152`, `CodingSessionHeader.tsx:49-58`), PR attach by branch (`ws.ts:424-441,3722-3728` → one `pr_url`). - **The draft's `baseRef` is already mostly inert**: `LineBranchReactor` pre-mints every line branch with base OIDs honoring `newWorktreesStartFromOrigin`; the create-if-missing in `CodingSessionService.ts:303-324` is dead in practice.

## Design

### 1. The gate deletes; implement opens the draft

Every Bucket-1 item from the census goes: the three RPCs and their auth entries; `PlanningAssistant`'s implement flavor, proposals map, `settleImplement`, `tryImplement`, and the flavor branches (`PlanTurnRegistry.flavor` collapses to reply-only — drop the field); `implementTurnInput`; MCP `save_implement_proposal` (tool, handler, approved-tools entry, `GroundingFold` filter); `PlanningStore`'s verdict types, rows, methods, `saveSplits`, `getImplementContext`, and the snapshot's `readyCommits`; the five `implement-*` stream items, `PlanImplementVerdict/Proposal/Ready`, `ImplementBlockedError`, `ConfirmSplitsBlockedError`; `planReducer`'s implement state and folds; web `SplitSheet.tsx`, `splits.logic.ts` (whole file — `existingSplitsAt` has no surviving consumer), ready badges, the emerald dot, `PlanNodePopover`'s `ready` facts and act plumbing, `implementFailureNotice`, the analyzing card, fixtures and catalog entries.

What replaces the flow: `beginImplementFrom(commitId)` resolves the acting head as today and **directly** calls `materializeSessionDraft({commitId})` — no verdict, no repository. The composer hammer and the popover's "Implement from here" (label unchanged) both do this. `implementDisabledReason` survives in spirit as a small local helper (turn active / draft space / empty plan text — client courtesy; the server refuses authoritatively).

**Readiness re-checks come out**: `CodingSessionService.ts:246-252` and `PlanningStore.ts:2191-2201`. `CodingSessionBlockedReason` loses `"not-ready"`, `"repository-mismatch"`, `"repository-not-in-project"`, and `"base-ref-missing"` (the input that justified it is gone, §3); keeps `"repository-not-git"` — re-aimed at "a linked repository is not a git checkout", named in the message — plus the provider/model/pool reasons.

**Migration `014_DropPlanImplementVerdicts`** (new): `DROP TABLE IF EXISTS plan_implement_verdicts`. Entry 9 stays in the list (append-only history); `migrationEntries.length` pins move 13→14; the `at(-1)` guard moves from `013_WorktreeSlots.test.ts:15` to 014's test; `009_PlanImplementVerdicts.test.ts` is deleted (014's test asserts the table exists at `toMigrationInclusive: 13` and is gone after full `runMigrations()`); the raw-SQL trigger test at `PlanningStore.test.ts:2859-2912` goes with it.

### 2. The stale-plan condition keeps its dot and loses its dialog

Delete `StalePlanWarning.tsx` (+ test, catalog entry, `catalog.test.ts:38` assertion, `STALE_PLAN_WARNING_CATALOG_ENTRIES`), `implementFlowAction` and its event kinds, and `PlanningSpace`'s `stalePlanWarningOpen`/warning wiring. **Keep** `PlanFreshness.ts` (label + description feed the popover, the header alert, and the aria-labels), `planMayBeStaleAt` and both stale predicates, the amber/orange corner dots, the node-popover warnings, and the graph-header `GraphWarningsPopover`. `planNodeStatusDots` drops its `ready` input and the emerald dot; stale-spec and stale-plan dots keep their order and fills (`DagExplorer.test.tsx:460-473` updates from three dots to two).

### 3. The session becomes project-scoped

`MercurianStartCodingSessionInput` slims to `{planId, parentCommitId, runtimeMode, modelSelection}`. `repositoryId` goes (the session spans the project); `baseRef`/`startFromOrigin` go with it — base resolution is already `LineBranchReactor`'s, per repository, honoring `ServerSettings.newWorktreesStartFromOrigin`; the per-session override retires (vault: base "defaults per repository from Settings"). The dead create-if-missing block (`CodingSessionService.ts:291-324`) is deleted; start instead **requires** the line-branch rows the reactor minted (a missing row is the existing `SlotServiceError("claim:lineBranch")` path, surfaced as a typed refusal).

`CodingSessionService.start` after the change: guards → provider gate (unchanged) → resolve the project's linked repositories in link order → orchestration project + `thread.create` keyed by the **primary repository** (first link — the same `reachable[0]` convention planning uses) → `slotService.claim` (unchanged) → **no narrowing**: dispatch `thread.meta.update { branch, worktreePath: <primary member path>, workspaceMembers }` where `workspaceMembers = [{repositoryId, worktreePath: slotMemberWorktreePath(...)}]` for every member. Setup scripts run once per member that declares one, each in its own member cwd. `appendCodingSession` records the leaf with no repository stamp (§5).

**`workspaceMembers` is the one new wire fact**, additive-optional on `thread.meta.update`, the thread row, and the thread shell (`contracts/orchestration.ts:408-409,486,795-812`) — `ReadonlyArray<{repositoryId, worktreePath}> | null`, re-dispatched on every re-claim exactly as `worktreePath` already is (`ws.ts acquireCodingSessionSlot :713-768`, which also stops narrowing). Three consumers: the provider start (§4), the checkpoint reactor (§5), and the web header (§6). Upstream threads never set it; every existing `worktreePath !== null` gate keeps working because the primary path still lands there.

### 4. Provider sessions claim every root, honestly

`ProviderCommandReactor.ts:650-669` gains what planning has: for a thread with `workspaceMembers`, `cwd` = primary member, `additionalDirectories` = the rest — **gated on `capabilities.groundingRoots`**, the `buildRebuildMaterials` split reproduced (a small shared helper is fine, but do not entangle planning's memory-root logic). A `cwd-only` provider gets `cwd` only, and the narrowing is recorded: the session record gains optional `unreachableRepositories: readonly string[]` (names, in link order), written at start and rendered in the session view with the existing `NarrowedGroundingNotice` component — M-184's "or say they can't", now stated where building happens. Codex/Claude (`multi`) reach every root; M-184's `writableRoots` seam fires for coding sessions because their turns run `workspaceWrite` — no adapter change needed here.

### 5. The runtime commits per repository; the record shows files per repository

`CheckpointReactor`'s slot-backed settled path (`:415-479`) iterates **every slot member** instead of one cwd. Per member, per settled turn: `git add -A`; commit **only if dirty** (the vault: real commits "in each repository the turn touched" — no empty commits on untouched branches); then `update-ref <checkpointRefForThreadTurn> HEAD` **always** (an untouched member's ref points at its existing HEAD, so per-turn diffs stay well-defined for every repository at every turn without empty commits). `markBuilt` fires per member that actually committed. `recordSettledCommit` moves to per-repository rows (below). Pre-turn baselines (`:589-637,:736-795`) write their ref in every member. The partial path captures an orphan snapshot per **dirty** member (the shape `SlotService.switchSlot` already uses per member). The lease-release member loop (`:498-523`) is already right.

**Wire:** `OrchestrationCheckpointSummary` gains optional `repositories: ReadonlyArray<{repositoryId, repositoryName, files: OrchestrationCheckpointFile[]}>`; `files` stays as-is and remains the single-repo/legacy shape (for multi-repo turns it carries the primary member's files, keeping old consumers sane). `ChangedFilesCard`/`MessagesTimeline` render grouped per-repository sections when `repositories` is present — repository name as the group header, the existing tree per group. Diff reads (`CheckpointDiffQuery.ts`) gain an optional `repositoryId`: the server resolves that repository's cwd (current slot member if held, else `repository.path` — checkpoint refs live in the shared git dir, so any worktree of the repository reads them) and the web passes the group's `repositoryId` on file clicks.

**Record:** new table `coding_session_repositories (thread_id, repository_id, settled_commit_oid, pr_url)` in the same migration 014 (one migration, one issue), PK `(thread_id, repository_id)` + `CodingSessionStore` methods (`recordSettledCommit(threadId, repositoryId, oid)`, `attachPullRequest(threadId, repositoryId, prUrl)`, `listRepositories(threadId)`). The `coding_sessions` legacy columns stay for existing rows; new sessions write `repository_id = NULL` there and rows here. `PlanCodingSessionRecord` gains optional `repositories: ReadonlyArray<{repositoryId, repositoryName, settledCommitOid, prUrl}>`; the leaf payload `PlanCodingSession`'s `repositoryId/repositoryName` become optional (absent on new sessions; old leaves render exactly as today, AC 4's sibling: old _sessions_ keep their repository name on the card).

**Amended (2026-09-02): the chain, not commits, per repository.** Section 5 was written against M-195's settle-time runtime commit. M-206 (merged the same day) replaced it with the per-line snapshot chain — the runtime never commits; every turn end captures a whole-tree snapshot on hidden refs with the previous snapshot and `HEAD` as parents, and "built" is decided inside `SnapshotChain.capture` from the tree against the recorded base — so this issue now widens the _chain_ to every member instead of committing in each. As rebased onto main @ `11bda523d2`:

- **The reactor snapshots per member.** `CheckpointReactor.captureCheckpointForTurn` resolves every slot member (`sessionMembers`: slot order, names from the session's rows or the registry, the member the provider stands in marked as _home_) and runs `captureMemberSnapshot` for each: `adoptStanding` → `snapshotChain.capture(kind, turn ref)` → `branchMovement` → branch tip → `recordRepositorySnapshot`. The turn ref carries the same name in every member's git dir; `built` marks only where a tree changed or a branch moved (the chain's rule, per repository). Partial turns take the same path with kind `partial` — every member snapshots, which is the vault's "same record as a settled turn, plus the mark". The opening capture (`captureExternalSnapshot`) and the `turn/0` baseline run per member too, through one `ensurePreTurnBaseline`.
- **The session row follows the home member; rows follow every member.** `coding_sessions` keeps the home member's snapshot facts (so every existing reader — Departed badge, popover Branch line, `inheritedCommitOid` for legacy sessions — is unchanged), with `departedRef` set when _any_ member departed. `coding_session_repositories` carries `snapshot_oid`, `snapshot_kind`, `branch_tip_oid`, `departed_ref`, `branch_movement`, and `pr_url` per repository; `settled_commit_oid` is gone from it (the branch tip is what the chain records). `PlanCodingSessionRepository` on the wire mirrors the row; `OrchestrationCheckpointRepository` gains optional `departedRef`/`branchMovement` per group.
- **A rename is adopted where it happened.** `adoptStanding` takes the member: the chain-owned records move for that repository alone; only the home member's rename also moves thread meta and the session's branch. The activity line names the repository for a non-home rename.
- **Forks inherit per repository.** `LineBranchReactor` reads the ancestor session's row for each repository (`branchTipOid` for the base, `snapshotOid` to seed the new line's chain head), falling back to the legacy singular facts for sessions recorded before this issue. M-206's re-point guards and holds replace this plan's checked-out guard.
- **Recreating a missing branch is per line.** The session starts project-scoped, so the Implement door cannot name which repository lost its branch; `mercurian.recreateLineBranch`'s `{ planId, commitId }` form recreates every missing branch of the line across the project's repositories (`repositoryId` narrows it), and the `{ threadId }` form covers the session's repositories.
- **The home repository is recorded, not derived.** Found on the two-repo walk: birth took the first project link, the slot re-claim took the first session row, and the slot store listed members by path — three orders, and the provider's cwd flipped between turns (restarting the provider session). `coding_sessions.repository_id` now records the home for every session (the first linked repository at birth, per the vault's project-order default); the slot re-claim, the reactor's home member, and the header's default selection all read it, and `workspaceMembers` lists the home first.
- **Migration 016** (renumbered past M-206's 014/015) drops the verdicts table, rebuilds `coding_sessions` with `repository_id` nullable and M-206's columns carried, and creates the repository rows table above.

### 6. Git actions, scripts, and open-in go per-repository

`_chat.sessions.$threadId.tsx` passes the thread shell's `workspaceMembers` (plus the legacy singular fallback for old sessions) into `CodingSessionHeader`. The header gains a **repository switcher** — a small select rendered only when more than one member exists, defaulting to the primary; the selected member's `worktreePath` and repository feed the existing `GitActionsControl` (`gitCwd`), `SessionScriptsControl` (whose `terminalId` becomes `script-<repositoryId>-<script.id>` to avoid the cross-repo collision), and `OpenInPicker` unchanged — they are already single-cwd machines, and per-repository means _switching which cwd_, N calls not a new RPC shape (`GitRunStackedActionInput` keeps one `cwd`). `changeRequestsAllowed` follows the selected repository's status for free.

**PR attach keys on branch + repository.** `ws.ts:3717-3752` already captures the acting `cwd`; resolve which repository it belongs to (match against the session thread's `workspaceMembers`, falling back to `repositories.path` prefix) and write `coding_session_repositories.pr_url` for that pair; `getByBranch` still finds the session (one branch name per line across repositories). **PR links render per repository**: the session card (`PlanTimeline.tsx:211-247`) and the node popover session facts (`PlanNodePopover.logic.ts:29-36,143-161`, `.tsx:305-329`) list each repository row — name, settled state, PR link when present — so "a thread that touched three repositories can open three pull requests, each linked from the thread" is literally the card. Old records render their singular facts unchanged.

### 7. The draft sheet slims

`CodingSessionDraft` drops `repositoryId/repositoryName/baseRef/startFromOrigin` (localStorage key bumps to `:v2`; v1 drafts are discarded — they were pre-gate-retirement shapes). `CodingSessionDraftSheet` shows the project's linked repositories as a read-only list ("Works across: repo-a, repo-b, …", from `useRepositories()` + the plan's `projectId`), runtime mode, and the agent/model pickers; the base-branch select and origin checkbox go. `createCodingSessionDraft` takes `{commitId}`; `materializeSessionDraft` follows. The start-all cluster (`startAllLandedPlans`, `landedPlans`, `sessionBaseRefs`, `CodingSessionBaseRefLoader`) deletes — one session now covers what N per-repo sessions did.

### 8. Split revisions keep rendering (Bucket 2, untouched)

`PlanSplitStamp`, `PlanRevision.split`, the payload schema, `toTimelineEvent`'s no-`planText` rule, `getPlanTextAt`'s projection walk, `PlanArtifact.logic`'s skip-splits invariant, and the three labels ("Plan for {repo}" / "You added a plan for {repo}") all stay, as does `planMovedPastSplit` and its popover warning. The one gate-side read of `item.split` (`planReducer.ts:203`, proposal-closing) goes with the proposal. A test asserts a split-stamped revision from a seeded history still renders its label and contributes no snapshot text.

### 9. Docs

`docs/user/projects-and-plans.md`: the "Implementing a plan" section (:192-212) rewrites — implement opens the session draft directly; the session works across every linked repository; per-repository changed files and git actions; the split/confirmation paragraphs move to past-tense "histories may contain per-repository plans from the former flow"; dots copy at :220-222 loses readiness; :352/:359 lose "ready". `docs/internals/glossary.md`: delete **Atomic plan**, **Readiness verdict**, **Implement gate**; reword **Split** as a historical commit shape (fix the cross-anchors). `docs/internals/overview.md:149-156`: the gate paragraph becomes the direct-draft + multi-repository-session clause.
