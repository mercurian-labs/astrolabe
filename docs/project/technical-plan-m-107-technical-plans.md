# Technical Plan — M-107: Technical Plans

_Generated from the Goal/AC of Linear issue M-107 (see the issue for the full AC). Implements backlog 060 (Phase 6 — Technical plans and coding sessions) on the base as it stands after M-96/M-100/M-104 (its three blockers, all landed) plus M-101/M-102/M-105/M-106/M-108/M-123/M-124, under [ADR 001](../architecture/local-first-runtime.md) (Mercurian storage seam), [ADR 002](../architecture/event-streaming-model.md) (commit DAG as the durable log; transient frames as transport), and [ADR 004](../architecture/fork-baseline.md) (Mercurian code additive; minimal edits in upstream-owned files — this plan needs zero). Design sources are the almagest vault notes the issue cites — Technical Plans (both resolved decisions), Plans, Repository Filter ("derived, never assigned"), Issue Planning Flow step 8 — plus Coding Sessions, Commit Tree, Assistant, Repositories, and Projects for the invariants this feature sits inside._

**Goal, in one sentence:** make derivation real — from a plan, a user derives a technical plan for one repository the plan grounds in, produced by the planning runtime grounded in that repository alone, landing **as a commit** in the plan's one history, **stamped with the source plan revision** so staleness is shown (never auto-reconciled), never editable except by re-deriving — the layering that keeps one plan per planning space true while implementation stays single-repository.

**Scope fences, restated from the issue:** the Coding Session View tab that displays a technical plan beside work is not built here (neither are coding sessions — M-110 cites this issue as a blocker). Nothing here writes to a working tree; derivation turns inherit planning's read-only enforcement whole.

## Design

### 1. A fifth commit kind: `technical-plan` — and the one migration this needs

The vault resolved "is a derivation a commit?" as **a commit** — "one history per plan loses its force if some events are invisible." M-94 pre-seeded `commits.kind` with four kinds so later features would land "without schema surgery," but `technical-plan` was not among them (the Commit Tree note's own kind list predates the Technical Plans resolution — a vault gap, recorded below). So this issue carries the sequence's first real schema surgery:

- `commitTree/schema.ts`: `CommitKind` gains `"technical-plan"`. The kind is **interior-capable** — planning continues past a derivation, and M-110's coding-session leaf will hang off one — so no new structural refusal accompanies it; the existing laws (assistant fork/merge refusals, coding-session leaf rule) apply unchanged.
- `mercurian/persistence/Migrations/009_TechnicalPlanCommitKind.ts` **(new)**: SQLite cannot alter a CHECK constraint, and the migrator's single wrapping transaction means `PRAGMA foreign_keys=OFF` is unavailable (it is a no-op inside a transaction), so the rebuild is ordered to stay FK-consistent throughout: create `commits_new` with the widened CHECK (same columns, `sequence INTEGER PRIMARY KEY AUTOINCREMENT`); copy `commits` including `sequence`; create `commit_parents_new` referencing `commits_new`; copy `commit_parents`; drop `commit_parents` (child first), drop `commits`; rename `commits_new → commits` and `commit_parents_new → commit_parents` (SQLite ≥3.25 rewrites the FK references on rename); recreate `idx_commits_history` and `idx_commit_parents_parent`. Copying explicit `sequence` values keeps the append order and advances `sqlite_sequence`, so the cursor semantics of ADR 002 §2 survive byte-for-byte. `Migrations.ts` registers `[9, "TechnicalPlanCommitKind", …]`.
- A co-located `009_TechnicalPlanCommitKind.test.ts` proves the rebuild is faithful (§Test Plan).

### 2. The derivation commit: human-authored, snapshot payload, stamped with its source

**Author.** The commit lands `authorKind: "human"` (significant choice): "deriving is a decision about what to build" — the resolution's own wording makes it the human's act, and the import precedent already encodes exactly this (machinery produced the issue-revision root; the human's act authored it). This is also what makes derivation compose with the tree's law rather than fight it: deriving from an interior commit _is_ a fork — "implementation can start from any point the planning reached" — and forks are human acts; an assistant-authored derivation commit would be refused by `AssistantForkError` everywhere but at a tip. The store's assistant refusals stay untouched.

**Payload** (in `PlanningStore.ts`, beside its three siblings — payload schemas live with the feature that writes them):

```ts
/**
 * What a technical-plan commit carries: the plan projected onto one
 * repository, whole. Repository name is captured as record, not link —
 * grounding references in histories survive repository removal.
 */
export const TechnicalPlanCommitPayload = Schema.Struct({
  text: Schema.String,
  repositoryId: MercurianRepositoryId,
  repositoryName: TrimmedNonEmptyString,
  /** The plan revision this derives from — the staleness stamp. */
  sourceRevisionCommitId: CommitId,
  /** What the derivation consulted, the message-commit precedent. */
  grounding: Schema.optional(Schema.Array(PlanGroundingItem)),
});
```

A snapshot, not a reference: the technical plan _is_ this text, frozen at derivation. "Cannot be edited independently of derivation" (AC 4) is then true by construction — no write path to this payload exists anywhere except derivation itself, and re-deriving lands a _new_ commit rather than touching an old one, exactly as plan revisions never rewrite their predecessors.

**The stamp and staleness.** `sourceRevisionCommitId` is the last `plan-revision` commit at or above the derivation point on its path — the same walk `getPlanTextAt` already does. Staleness is a _derived comparison_, never stored and never reconciled: a technical plan is stale wherever the current path's latest plan revision is no longer the stamped one. Server stores facts; the client compares them (ADR 002 §4's temperament — ranking, not originating), in a pure logic module (§6).

**One per repository per derivation point** (AC 5) is enforced at start, path-scoped: deriving for repository R at commit P refuses when the ancestors of P already carry a technical plan for R stamped with P's current source revision — there is nothing new to derive from. Re-derivation becomes available exactly when the plan has moved (or on a sibling branch, whose path is its own). Given up, deliberately: regenerating at an unchanged revision to get a different generation; the escape is any plan edit, and a _failed_ derivation lands nothing so retry-after-failure always works (significant choice, flagged for review).

### 3. Derivation runs as a flavored planning turn — one runtime, not a second one

Derivation is generation grounded in a repository — exactly what `PlanningAssistant` already operates. It becomes a second turn flavor on the same service rather than a sibling service (significant choice: the alternative duplicates session lifecycle, read-only enforcement, registry claims, and frame plumbing for no boundary that exists):

- **`startDerivation({planId, repositoryId, parentCommitId?, createdAt})`** on `PlanningAssistant`. Unlike `startTurn` (which never fails — the message already landed), derivation starts nothing until it is known to be startable, so this **refuses synchronously**: `PlanNotFoundError`, `PlanTurnActiveError` (registry claim), and a new `TechnicalPlanDerivationBlockedError { reason }` with reasons `"plan-empty"` (no plan text at the derivation point — there is nothing to project), `"repository-not-in-project"` (the derive surface offers the project's set; the server checks the same membership), `"up-to-date"` (§2's per-point rule), `"model-unset" | "no-instance" | "model-unavailable"` (the planning-model resolution, M-97/M-104's helper — a derivation that cannot generate should say so in the dialog, not as a frame after an ack). One error class, reasons enumerated, mirroring `PlanTurnRefusalReason`'s vocabulary where it overlaps.
- `parentCommitId` carries the `appendPlanMessage` meaning — where the sender stood, absent means tip — so deriving while standing at an earlier commit derives the plan _as of that point_ and forks there, which is the composer's own act-from-anywhere semantics applied to the implement moment.
- **The registry claim is the same claim.** `ActivePlanTurn` gains a `flavor: "reply" | "derivation"` field; one turn per plan holds across both flavors, and the store's existing human-write guard (`PlanTurnActiveError` on `appendMessage`/`savePlanRevision`) now also protects a running derivation from a mid-flight fork racing its settle. `stopPlanningTurn` stops whichever flavor is live — no new stop verb.
- **The session is planning's session, narrowed to one root.** Fresh provider session per derivation: `cwd` = the one repository's path, no `additionalDirectories` — single-root by design, so the multi-repo narrowing machinery (`groundingScope`) never applies and even a `cwd-only` provider grounds fully. Workspace planning model, most-restrictive runtime mode, approvals auto-answered, `interactionMode` never passed — the M-104 enforcement rides unchanged. The session is torn down at settle; a derivation never becomes the plan's conversational session.
- **Prompt** in `PlanningPrompt.ts` (pure, tested, beside its siblings): `derivationTurnInput({repositoryName, planText})` — the plan text as of the derivation point, the instruction to project it onto _this_ repository as a self-contained implementation plan grounded in the code actually present, to call `save_technical_plan` with the complete document as the one way to produce output, not to edit the plan, and not to ask questions — make reasonable assumptions and record them in the document. A `user-input.requested` that arrives anyway is auto-answered empty (`respondToUserInput({})`) so a derivation never pauses on a person; `hasPendingInput` stays reply-turn-only (significant choice — the alternative, surfacing the question card, buys interactivity the compilation framing doesn't want; flagged).
- **The write door widens by one tool.** `mcp/toolkits/planning/` gains `save_technical_plan({ text })`: the handler routes thread→turn as today and refuses unless the calling turn's flavor is `derivation`; symmetrically, `save_plan_revision` now refuses for derivation turns (a derivation must not workshop the plan). `read_plan` stays available to both — it reads at the turn's registry tip, which for a derivation is the derivation point, so it reads the right text for free. The tool stores the text as the turn's _pending_ document (last call wins), not a commit.
- **Settle is all-or-nothing.** On `turn.completed` with a pending document: one commit lands via a new internal store write (§4), then `derivation-settled` and the commit event. On completion _without_ the tool ever called, on stop, and on any abnormal end: `derivation-failed` (reasons `"no-technical-plan"`, `"stopped"`, `"provider-error"`), the claim closes, and **nothing lands** — a partial technical plan is not a technical plan. This deliberately diverges from message turns' interrupted-partial commit (significant choice): a reply cut short is a record of conversation that happened; a derivation is a compile, and a failed compile leaves no artifact — the first-commit temperament ("nothing exists until its first commit") applied to the derived layer. `teardownPlan` discards a running derivation the same way for both archive and delete.

### 4. `PlanningStore`: one internal write, one derivation-context read, one on-demand text read

- **`saveTechnicalPlan({planId, parentCommitId, repositoryId, repositoryName, sourceRevisionCommitId, text, grounding?, createdAt}) → PlanTechnicalPlan`** — the derivation settle's write, called only by `PlanningAssistant`. `authorKind: "human"` hardcoded (§2), parent named explicitly (the derivation point — a parent with children makes this the fork, the store's one way to make one), in one `sql.withTransaction` with `touchPlanRow`, then `announceChange`. Like the assistant writes and unlike the human RPCs, it does **not** consult the turn-registry guard — it _is_ the active turn's write.
- **`getDerivationContext({planId, atCommitId?}) → { atCommitId, planText, sourceRevisionCommitId?, latestTechnicalPlans: ReadonlyMap<repositoryId, {commitId, sourceRevisionCommitId}> }`** — one ancestor walk (via `CommitStore.ancestors`, path at-or-above the point) answering everything `startDerivation` refuses on and stamps with: the text and last plan revision at the point (`undefined` when the path has none — issue-revision roots deliberately don't count, matching `toTimelineEvent`'s "an issue is what you plan _from_"), and each repository's newest technical plan on that path.
- **`getTechnicalPlanAt({planId, commitId}) → {text, grounding?}`** — the on-demand text read, the `getPlanTextAt` shape exactly: verify history membership, require kind `technical-plan`, decode the payload. History above a commit never changes, so the answer never goes stale and the client may cache per commit.
- **Timeline projection**: `toTimelineEvent` gains the `technical-plan` case, projecting `{_tag: "technical-plan", …commitFields, repositoryId, repositoryName, sourceRevisionCommitId}` — **no text** (the constant-size wire rule; the document is read on demand like historical plan text) and **no `planText`** on the event (a derivation never changes the artifact). `PlanTechnicalPlan` joins the store's projected types beside `PlanRevision`.

### 5. The wire: two methods, one timeline member, three frames

`packages/contracts/src/mercurian.ts` (all additive):

- `MERCURIAN_WS_METHODS` += `deriveTechnicalPlan`, `getTechnicalPlanAt`.
- `PlanTechnicalPlan` = commit fields + `repositoryId: MercurianRepositoryId`, `repositoryName`, `sourceRevisionCommitId: MercurianCommitId`; `PlanTimelineItem` union gains `{_tag: "technical-plan"}`.
- `MercurianDeriveTechnicalPlanInput { planId, repositoryId, parentCommitId? }` → success `MercurianPlanAcknowledged` (the stream carries everything after); error union adds `TechnicalPlanDerivationBlockedError` (new refusal class here, reasons per §3) beside `PlanNotFoundError`/`PlanTurnActiveError`.
- `MercurianGetTechnicalPlanAtInput { planId, commitId }` → `TechnicalPlanAt { text, grounding? }`.
- `PlanInFlightDerivation { turnId, parentCommitId, repositoryId, repositoryName, grounding: Array<PlanGroundingItem> }`; `PlanDetail` gains `inFlightDerivation?` (snapshot join for a window opening mid-derivation — the `inFlightTurn` precedent exactly).
- `PlanStreamItem` gains `{kind:"derivation-started", derivation: PlanInFlightDerivation}`, `{kind:"derivation-settled", turnId}`, `{kind:"derivation-failed", turnId, reason: Literals(["no-technical-plan","stopped","provider-error"])}`. Grounding streams on the existing `turn-grounding` frame — turnId-keyed, and the reducer routes by which in-flight thing owns the turnId. **No `turn-delta` is emitted during derivation** (significant choice): the provider's narration is not conversation and the document arrives whole through the tool; the deriving card shows liveness through grounding instead. Frames stay transport (ADR 002 §3); only the settling commit is durable.
- `MercurianPlanningError.operation` += `"deriveTechnicalPlan"`, `"getTechnicalPlanAt"`.

Then the standard touchpoints: `rpc.ts` — `WsMercurianDeriveTechnicalPlanRpc`, `WsMercurianGetTechnicalPlanAtRpc`, `WsRpcGroup` membership; `RpcAuthorization.ts` — `deriveTechnicalPlan` → Operate, `getTechnicalPlanAt` → Read (the coverage test forces both); `ws.ts` Mercurian block — two handlers on the established shape (`DateTime.now`, refusals pass through, the rest wraps with the new operation names); `mercurian/planning/wire.ts` — `toWirePlanTechnicalPlan`, the timeline-item and stream-item mappings, `toWirePlanDetail` gaining `inFlightDerivation`.

### 6. Client: reducer folds the frames; staleness is a pure comparison; three surfaces show it

- `packages/client-runtime/src/state/planReducer.ts`: fold `derivation-started` into `inFlightDerivation`, route `turn-grounding` by turnId to whichever of `inFlightTurn`/`inFlightDerivation` owns it, clear on `derivation-settled`/`derivation-failed` (surfacing the failure reason as the transient notice, the `turn-refused` precedent), append `technical-plan` commits like any other (never touching `planText`). Pure, co-located tests.
- `mercurianPlanning.ts` atoms + `apps/web/src/state/mercurian.ts` hooks: `useDeriveTechnicalPlan()` (shared write scheduler, the serial-per-plan key), `useGetTechnicalPlanAt()` (the `useGetPlanTextAt` query shape, cacheable per commit).
- **`apps/web/src/components/mercurian/technicalPlans.logic.ts` (new, pure, tested)** — the staleness and menu brain, beside `PlanGraph.logic.ts` where path math already lives: `latestTechnicalPlansOnPath(path)` (per-repository newest), `sourceRevisionOnPath(path)` (last plan-revision id), `isStale(item, path)` (stamp ≠ current source), and `deriveMenuItems(projectRepositories, path, planText)` → per-repository `"never-derived" | "up-to-date" | "stale"` plus the disabled reasons (empty plan, turn active). Position-aware by construction: callers pass the path through the current position, so looking at an earlier commit shows that point's truth.
- **The derive entry point** lives on the `PlanArtifact` header (the artifact is the thing being projected, and the header is where its actions already sit): a **Derive** menu on the `ui/menu` primitives listing the project's repositories (`useProjectRepositories`) with each row's state — up-to-date rows disabled ("Derived from the current plan"), stale rows offering re-derive, never-derived rows plain. Disabled entirely while a turn or derivation is live or the plan text at the position is empty. Acting from an earlier position derives there (the fork), so the menu stays available while viewing the past — read-only applies to _editing_, and deriving is not an edit of the plan.
- **Timeline row**: `technical-plan` items render as a compact interleaved row in the same `<ol>` at the same standing (the plan-revision row precedent): "You derived a technical plan for _{repositoryName}_", relative time, plus a **stale badge** when `isStale` against the rendered path — staleness visible wherever the technical plan is shown (AC 2), and this row is where it is shown in the timeline. The row opens the viewer.
- **`TechnicalPlanDialog.tsx` (new)** — the viewer: repository name, the derived-from stamp ("Derived from the plan as of ‹relative time›", attribution from commit facts), a staleness banner when stale ("The plan has moved past this derivation — re-derive to update it"), the grounding fold, and the document rendered with the planning surface's markdown treatment. Deliberately **no edit affordance and no editor state** — AC 4 at the surface, matching its structural truth below. Content via `useGetTechnicalPlanAt`.
- **The deriving card**: while `inFlightDerivation` is set (and its parent is on the rendered path — the `visibleInFlight` closure check the in-flight turn already does), the timeline shows a quiet working card — "Deriving technical plan for _{repositoryName}_…", live grounding fold, Stop — and the composer treats it exactly like a live turn (send unavailable, stop available): the `turnActive` prop generalizes to either in-flight kind.
- **DAG explorer**: the kind-glyph map gains `technical-plan` (a code-file icon, distinct from the plan revision's `FileTextIcon`); `buildPlanGraph`/navigator handle the new `_tag` structurally already, and any kind-label helpers gain the case (the typecheck finds them).
- **Tree status**: `isWorking` during a derivation comes free — `PlanningAssistant.status` reports the plan's live turn either flavor; `hasPendingInput` never fires for derivations (§3).

## Gaps and findings carried out of discovery

- **Vault gap, for the vault's author:** the Commit Tree note enumerates commit kinds as "message, plan revision, issue revision, or a coding session" — the Technical Plans resolution ("a commit") implies a fifth kind the note never gained. Technical Plans' "What exists today" ("Not built — neither is the plan artifact") is also two phases stale. Both worth an authoring pass when this lands.
- **The schema-surgery debt existed before this issue:** M-94's kind CHECK pre-seeded four kinds "so features land without schema surgery" but missed this one; migration 009 pays it. The rebuild recipe here (FK-consistent ordering inside the migrator's single transaction) is precedent for any future kind.
- The issue stub's `backlog/060-technical-plans.md` lives outside this repository (the M-100/M-104 plans hit the same); noted so nobody hunts for it.
- **Deriving with no plan text refuses** (`"plan-empty"`): the vault never says what projecting an empty plan means; refusing is the conservative reading ("the plan projected onto one repository" needs a plan). If born-from-issue plans should derive from issue content before any revision exists, that is a design change for the vault, not this plan.
- Repository identity in payloads is **record, not link** (name captured at derivation), per Repositories' removal rule; a removed repository's derivations keep rendering by recorded name. The timeline shows the recorded name even for live repositories — consistent, and honest about what the commit says.
- `PlanQuestion` machinery and derivations: questions are suppressed by prompt and auto-answered empty at the runtime (§3). If real derivations turn out to genuinely need a human call mid-compile, the question-card plumbing exists to reopen this.
- M-110 (coding sessions) will scope a session to a technical plan — i.e., to a `technical-plan` commit — and hang its leaf in the history; `getTechnicalPlanAt` and the interior-capable kind are the seams built here for it, and the Coding Session View's stamped tab (excluded here) reads the same payload facts.
