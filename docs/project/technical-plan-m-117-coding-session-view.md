# Technical Plan — M-117: Coding Session View: timeline, checkpoints, revert

_Generated from the Goal/AC on Linear issue M-117 (2026-08-19). Grounded against `main` at `4bc12aa23`, after M-114 reactivated the thread surface at the session route and M-133/M-129 landed the Checkpoint Graph rename and node popover. Product sources consulted in the almagest vault as of `65a03ae` (2026-08-19): **Coding Session View**, **Coding Sessions** (checkpoints/revert, leaf-record resolution), **T3code Thread**, **T3code Thread View**, **Plans** (rewind refusal), **Checkpoint Graph** (node popover, map-clicks-pick), **Left Sidebar** (popover as the session-detail home). Governing ADRs: 001 (`docs/architecture/local-first-runtime.md`), 002 (`docs/architecture/event-streaming-model.md`), 004 (`docs/architecture/fork-baseline.md`)._

**Goal, in one sentence:** make the session's screen its own screen — reachable from its sidebar row and its Checkpoint Graph leaf, headed as a session rather than a t3code thread — while the timeline, checkpoints, turn diffs, changed-files cards, revert, and composer it re-houses stay the fork's existing machinery, and revert becomes server-refused (not merely client-disabled) while a turn runs.

**Scope fences:** M-110 owns birth and the draft; M-114 owns the runtime (turns, approvals, three-tier modes, compaction) and already mounted `ChatView` at `/sessions/$threadId`. 064 (M-118) owns the right panel and the diff-review loop — the terminal/files/diff/preview tabs stay upstream-interim here, as M-114 left them, and the changed-files card keeps opening upstream's diff panel. 065 (M-119) owns the header's git actions, open-in picker, and repository scripts — this plan removes the t3code header from the session screen and deliberately does **not** re-add those three controls; they return with 065's design. M-115/066 owns teardown; two findings from this discovery (checkpoint-ref accumulation, thread-delete dangling records) are recorded for it below. Mobile stays parked (ADR 004).

**Vocabulary:** "Checkpoint Graph" is the product name; the files are still `DagExplorer.*` (M-133's rename was user-facing text only — this plan follows the file names as they stand). "Session" on a surface always means a coding session; the t3code thread it references never surfaces by that name.

## Discovery Summary

**Three of the five ACs are already mechanically true on the mounted surface.** The timeline reads turn by turn with each activity entry folded to a line and expandable (`PlainWorkEntryRow`, `MessagesTimeline.tsx:2226-2378`); long turns collapse twice over — work-log groups keep only the newest entry visible (`MAX_VISIBLE_WORK_LOG_ENTRIES = 1`, `MessagesTimeline.logic.ts:13`; `WorkGroupToggleTimelineRow`) and settled turns fold to a "Worked for …" line (`deriveTurnFolds`, `MessagesTimeline.logic.ts:318-443`); the LegendList virtualizer pins to the end while streaming (`maintainScrollAtEnd`, `MessagesTimeline.tsx:589-593`) with the jump-to-bottom pill at `ChatView.tsx:6080-6099` (AC 2). Each turn ends with `ChangedFilesCard` — files touched with `DiffStatLabel` +/− counts (`ChangedFilesTree.tsx:30-203`), fed by `useTurnDiffSummaries` from `thread.checkpoints` (AC 3). The composer stages removable chips (images inline at `ChatComposer.tsx:2841-2914`, file `@`-mention chips via `FileTagChip`, terminal-output and review-comment chips already wired for 064's sources) and carries the `ProviderModelPicker`, M-114's three-tier runtime-mode select, and the combined send/stop control (`ComposerPrimaryActions.tsx:56-245`) (AC 5). Checkpoints are live for Mercurian sessions: `CodingSessionService` dispatches `thread.meta.update` with the worktree path **before** `thread.turn.start` (`CodingSessionService.ts:378-404`), so the reactor resolves the worktree cwd and captures the `turn/0` baseline; worktrees pass the `isGitRepository` check (a linked worktree's `.git` file satisfies `existsSync`, `git/Utils.ts:5-7`).

**Revert is built end to end, with one honest gap.** Every user message with a downstream turn diff carries the Undo action (`RevertUserMessageButton`, `MessagesTimeline.tsx:1065-1088`), disabled while working; the handler confirm-gates with a destructive dialog ("This will discard newer messages and turn diffs… cannot be undone", `ChatView.tsx:4714-4724`) and refuses with "Interrupt the current turn before reverting checkpoints." while a turn runs (`:4710-4713`). Server-side, `handleRevertRequested` (`CheckpointReactor.ts:690-818`) restores the worktree (`git restore --source <checkpoint> --worktree --staged` + `clean -fd` — never a branch move, never a HEAD move), rolls the provider conversation back (`rollbackConversation`), deletes later checkpoint refs, and emits `thread.reverted`, which both projections and the client reducer apply by discarding later turns, messages, and diffs. **The gap: the decider's `thread.checkpoint.revert` case has no running-turn guard** (`decider.ts:1119-1138`) — the AC's "waits for a running turn to be interrupted first" holds only for the window that clicked. Section 3 closes this at the decider, M-114 D3's seam.

**"The leaf commit is never destroyed" is structural, and stays so.** The revert chain touches `state.sqlite` and git only; no Mercurian write path exists anywhere in it, `coding_sessions.branch` stays valid because checkpoints never touch `refs/heads`, and branch drift after a mid-session `git checkout` still flows through `followWorktreeBranchDrift` → `CodingSessionRecordReactor` unchanged.

**The two designed entry points don't exist yet, and each has a precise blocker.** The sidebar lists sessions only inside the plan card's hover tooltip (`SidebarCodingSessionRows`, `PlanListSidebar.tsx:690-701`), whose positioner is hard-coded `pointer-events-none` (`ui/tooltip.tsx:36`) — rows cannot be made clickable in place, though `PlanTreeRow.codingSessions` already carries `threadId`. The Checkpoint Graph's node popover shows a session leaf's structured facts (`PlanNodePopover.tsx:303-327`) but `offeredActs` short-circuits to `["continue"]` (`PlanNodePopover.logic.ts:185-201`) and `PlanNodeSessionFacts` deliberately drops `threadId` (`:28-34`) — there is no "Open session" act. Map clicks pick the leaf (`graphNodePopoverInteraction`, `DagExplorer.tsx:386-411`), moving the planning surface onto it with M-110's `SessionLeafBanner` — behavior this plan must leave untouched (AC 1's "planning space unchanged"). Navigating to `/sessions/$threadId` also leaves no sidebar row active (`resolveTreeSelection` knows only plans/repositories/settings, `planListing.logic.ts:33-41`).

**The screen still heads itself as a t3code thread.** `ChatHeader` renders project-favicon → thread-title breadcrumbs where the leading crumb **starts a new thread in the plumbing project** (`ChatHeader.tsx:215-243`) — an act with no Mercurian meaning that would create a leafless orphan thread — plus the thread action menu (pin/snooze/settle/**delete**; delete leaves a dangling `coding_sessions` record, M-114 D1's accepted interim exposure) and the git-actions/open-in/scripts cluster that 065 owns. The `BranchToolbar` needs no suppression: for a started session `envLocked` and the worktree lock (`BranchToolbar.tsx:351`) already make it a read-only branch/worktree indicator, which matches "once started, the branch and worktree are fixed."

**Findings carried to M-115/066 (teardown), not fixed here:** `refs/t3/checkpoints/<threadId>/…` refs are deleted only by revert — `ThreadDeletionReactor` and worktree removal never call `deleteCheckpointRefs`, so each session accumulates dangling full-tree commits in the shared git dir; and thread deletion outside the designed teardown still strands `coding_sessions` rows. Removing the thread action menu from the session screen (Section 1) closes the only UI path to the latter in the meantime.

## Design

### 1. The session screen heads itself as a session — one seam into `ChatView`

Add one optional prop to `ChatViewProps` (`ChatView.tsx:487-508`): `headerContent?: ReactNode`. In the `<header data-chat-header>` block (`:5993-6014`), render `headerContent ?? <ChatHeader …/>`. The wrapper `<header>` — Electron drag region, titlebar insets, `panelLayoutControls` — stays; only the inner content swaps. This is the smallest upstream edit that lets the session route own its header, and it is deliberately generic rather than Mercurian-shaped so weekly merges stay cheap. `ChatHeader` is not deleted: with the session route the only `ChatView` consumer, it becomes parked-in-place behind the default branch, per ADR 004's discipline (amend the §2 disposition table: t3code thread header superseded on the session screen at M-117; git actions/open-in/scripts return per 065's design; component parked, wire untouched).

Add `apps/web/src/components/mercurian/CodingSessionHeader.tsx` **(new)**, supplied by the route as `headerContent`. It renders:

- a **plan crumb** — the parent plan's title, a `<Link to="/plans/$planId">` — falling back to a bare "Plans" crumb linking `/` when the thread maps to no plan (the route's existing dangling-thread tolerance);
- the **session title** — `activeThread.title` (M-110 seeds it from the plan title), with inline rename reusing the exported `resolveRenameCommit` rule (`ChatHeader.tsx:77-86`) and dispatching `threadEnvironment.updateMetadata`, so the t3code temperament (a generated title never overwrites a rename) transfers whole.

Nothing else: no new-thread act, no thread action menu (pin/snooze/settle/delete are t3code sidebar concepts with no session meaning; delete's dangling-record exposure closes with the menu), no git actions/open-in/scripts (065). The route (`_chat.sessions.$threadId.tsx`) already computes `planId` from the tree snapshot; extend that lookup to also carry the plan's title and thread shell facts the header needs. `BranchToolbar`, the minimap, and the right-panel tabs all stay exactly as mounted — the toolbar is already locked read-only for a started session, and the vault's Coding Session View omitting the minimap is not read as removal (the guardrail is reuse, not redesign; stripping it would be a deliberate vault-cited act this issue doesn't have).

### 2. Two entry points open the session; picking a leaf still means picking

**Sidebar row (the "tree row").** Per the Left Sidebar resolution, the popover — not a third card line — is where a plan's session detail lives, so the popover itself becomes interactive. Replace the plan card's `Tooltip`/`SidebarPlanTooltip` pairing (`PlanListSidebar.tsx:660-686`) with a controlled `Popover` (`ui/popover`) driven by the linger pattern `usePlanNodePopover` proved (`PlanNodePopover.tsx:51-106`): open after a hover linger, close on a short delay so the pointer can travel into the popup, keep the glass styling and current content byte-for-byte. Extract the hover-control into `apps/web/src/components/mercurian/SidebarPlanHoverCard.{tsx,logic.ts}` **(new)** so the timing logic is pure and tested once. `SidebarCodingSessionRows` rows then become links: each row wraps its existing `Running/Ended · branch` label in `<Link to="/sessions/$threadId" params={{ threadId: session.threadId }}>` — the record already carries `threadId` (`packages/contracts/src/mercurian.ts:84`); no wire change.

**Checkpoint Graph leaf.** Two pure-logic edits plus one render case, all in Mercurian files: add `threadId` to `PlanNodeSessionFacts` (`PlanNodePopover.logic.ts:28-34`, populated from the record at `:143-156` — present only when the record exists); make `offeredActs` return `["continue", "open-session"]` for a coding-session node with a record; render the new act in the popover's acts row (`PlanNodePopover.tsx:356-375`) as a Button-rendered `<Link to="/sessions/$threadId">` — the `PlanTimeline.tsx:205-218` precedent — labeled **Open session**. This is the vault's leaf-record resolution made navigable: "the full turn-by-turn session inspectable from the leaf." **Click semantics do not change:** `graphNodePopoverInteraction` (`DagExplorer.tsx:386-411`) still picks on click because `"continue"` remains offered — clicking a session leaf keeps moving the planning surface onto it with the `SessionLeafBanner` and parent acting-head, exactly M-110's behavior, and the popover stays the hover's second stage per the Checkpoint Graph's resolved click reading. The act is reachable from every view: Graph via linger, Thread/Columns via linger and the info button.

**The screen knows its place in the sidebar.** Extend `resolveTreeSelection` (`planListing.logic.ts:33-41`) to recognize `sessions/<threadId>` and return the thread id; `PlanListSidebar` maps it to the owning plan via the tree rows' `codingSessions` (the same reverse lookup the route already does) so the parent plan's card reads active while its session screen is open.

The planning space, `PlanningSpace.tsx`, `PlanPosition.logic.ts`, and the timeline session card are untouched — AC 1's "unchanged by it" is satisfied by construction, and the timeline card's existing **Open session** link remains the third entry.

### 3. Revert refuses at the decider while a turn runs; everything else is verified, not rebuilt

Extend the decider's `thread.checkpoint.revert` case (`decider.ts:1119-1138`): after `requireThread`, refuse with an `OrchestrationCommandInvariantError` ("Interrupt the running turn before reverting checkpoints.") when `thread.latestTurn?.state === "running"` — the same read-model check M-114's cancel case uses (`:1073`). This makes "revert waits for a running turn to be interrupted first" hold for every client and every replay rather than only for the window whose button was disabled; the client's existing guard and error copy (`ChatView.tsx:4710-4713`) become the friendly fast path in front of a structural refusal. The shipped semantics stay t3code's built referent — the user interrupts, then reverts; no auto-interrupt-then-revert is added (the vault documents the built behavior, and an implicit interrupt would make a destructive act more automatic, not less).

Nothing else in the revert chain changes. The confirm gate, permanence copy, worktree restore, conversation rollback, later-diff discard, and client reducer rollback are upstream machinery already exercised; the leaf-never-destroyed clause is pinned by tests rather than code — the revert chain has no Mercurian write to remove. One fragile ordering invariant gets a pin: `CodingSessionService`'s birth must keep dispatching `thread.meta.update` (worktree path) before `thread.turn.start`, because the checkpoint baseline resolves the cwd from the thread row; assert the dispatch order in `CodingSessionService.test.ts` if M-110's tests don't already.

### 4. What this issue deliberately does not build

The composer's chips, pickers, and send/stop control (AC 5) and the timeline behaviors (AC 2, AC 3) ship as they stand — the walk demonstrates them; no code is written for them. Terminal-output and review-comment chips keep their upstream sources (the interim terminal/diff tabs) until 064 re-houses those panels. Starting a session from the draft sheet still lands you in the planning space (navigating into the newborn session is 064/065 polish, not an AC here). No contract, migration, RPC, or `ws.ts` change is made anywhere in this plan — the one server edit is the decider guard, which adds no new service calls and therefore no `server.test.ts` mock drift.

### 5. Documentation and surface accounting

- `docs/user/projects-and-plans.md`: the session screen — opening it from the plan card's popover, the Checkpoint Graph leaf's popover, or the timeline card; how the timeline reads (folded work log, turn folds, changed-files card); revert-to-this-message with its confirm and interrupt-first rule; the leaf staying put in plan history after a revert.
- `docs/internals/glossary.md`: Coding Session View (the screen), and cross-link checkpoint/turn diff/revert to the session vocabulary.
- `docs/architecture/fork-baseline.md`: the §2 disposition amendment (Section 1).
- Web and desktop apply identically (same served origin); mobile stays parked and untouched; the entry points and header are provider-agnostic.

## Decision Log

- **D1 (architectural) — Header seam: one generic `headerContent` override on `ChatView`, header composed by the route.** Alternatives: a Mercurian-shaped `sessionContext` prop (couples upstream ChatView to Mercurian types), forking a session variant of `ChatHeader` (rebuild, guardrail violation), or keeping upstream's header whole (M-114's interim — rejected now because its leading crumb creates leafless orphan threads and its menu deletes session threads outside the designed teardown). The generic ReactNode keeps the upstream diff one conditional.
- **D2 (design-conformant) — The sidebar entry is the popover made interactive, not a third card line or nested rows.** The Left Sidebar resolution names the popover as where session detail accrues "rather than growing the card back into multiple lines"; the third card line the note contemplates is future Left Sidebar work, not this AC. Cost accepted: the plan card's hover detail changes from an inert tooltip to a lingering hover-card.
- **D3 (design-conformant) — Opening from the leaf is a popover act; map clicks keep picking.** The Checkpoint Graph resolution (2026-08-19) is explicit that clicks pick and the popover is the hover's second stage; making a session-leaf click navigate would both fork that resolution and change M-110's planning-space behavior that AC 1 freezes. Per the vault-readings-stay-literal practice, the fork was not taken.
- **D4 (architectural) — "Waits for interrupt" becomes a decider refusal, not an auto-interrupt.** The decider is M-114 D3's proven seam for invariants that must hold for every client; auto-interrupting on revert would make a confirm-gated destructive act more automatic than the built t3code referent the vault documents. The client guard stays as the friendly path.
- **D5 (local) — Route stays `/sessions/$threadId`** (M-114 D5's allowance to re-address was examined and declined: the thread id is the session's runtime identity, zero translation at the mount, and no AC names the URL).
