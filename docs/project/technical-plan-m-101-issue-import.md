# Technical Plan — M-101: Issue Import

_Generated from the Goal/AC of Linear issue M-101 (see the issue for the full AC). Implements backlog 051 (Phase 5 — Trackers, import, revisions) on the fork as it stands after M-94 (multi-parent commit model), M-95 (projects/plans/tree), M-98 (tracker connections), M-100 (plan artifact), M-102 (plan lifecycle), and M-106 (DAG explorer) — all landed and verified in source. Under [ADR 001](../architecture/local-first-runtime.md) and [ADR 002](../architecture/event-streaming-model.md). Design sources are the almagest vault notes the issue cites: Issue Import, Issues, Publishing, Environments (the born-published carve-out, resolved 2026-07), Plans (the lifecycle resolution), Projects._

**Goal, in one sentence:** from a project's new-plan flow, browse the connected trackers' issues live — fetched, filtered, selected, never stored — and import one as a new plan whose root commit _is_ the issue's content: idempotent by origin (re-import navigates, or resurfaces an archived plan), ungrounded at birth, and born published (the plan and its root commit are shared truth; everything after the root defaults to a private draft).

**Scope fences, restated from the issue:** refresh and issue revisions are M-109's — this plan writes the _root_ issue-revision commit and nothing ever revises it here; no issue is stored or mirrored for browsing (the browse stays a live read of M-98's `listTrackerIssues`); no connector method is added (write-back stays resolved-deferred, and even `getIssue` waits for M-109's refresh). Born-blank plan creation is untouched and stays equally supported.

## Design

### The shape of the work: the seams are cut, this issue threads them

Every prior issue in this phase left a deliberate hook for import, verified in source: the commit model can mint a published root of kind `issue-revision`; the lifecycle rules already answer "what does re-import find" for both archive and delete; the tracker layer already serves the live browse (`listTrackerIssues`, paged and searchable, never stored); and the draft planning space is the new-plan flow the vault says import belongs to. What M-101 adds is one origin table, one `PlanningStore` write path, one RPC, one dialog, and the projection that makes the imported root visible.

### Data model: `008_PlanOrigins`, one narrow table

`mercurian/persistence/Migrations/008_PlanOrigins.ts` **(new)**, registered as `[8, "PlanOrigins"]`:

```sql
CREATE TABLE IF NOT EXISTS plan_origins (
  plan_id       TEXT PRIMARY KEY REFERENCES plans(plan_id),
  connection_id TEXT NOT NULL,
  issue_id      TEXT NOT NULL,
  issue_url     TEXT NOT NULL,
  imported_at   TEXT NOT NULL,
  UNIQUE (connection_id, issue_id)
)
```

- **A table, not columns on `plans`** — migration 005's header says it verbatim: "imported-issue and origin columns. Issue import owns those, and its **table** arrives with the feature that writes it." Most plans are born blank; their row carries no empty origin fields.
- **Origin = `(connection_id, issue_id)`**, the recorded intent ("it is connection identity — not kind — that an import's origin will name"): two Linear workspaces are two connections whose issue keys may collide, so kind+id would be ambiguous where connection+id is not. `connection_id` is **deliberately not a foreign key** into `tracker_connections` — origins are content, and disconnecting a tracker must never dangle or cascade into plans (M-98's `disconnect` rationale). Accepted cost, worth naming: disconnecting and re-connecting the _same_ tracker workspace mints a new `connection_id`, so a re-import through the new connection is a new origin and creates a new plan. That is the price of origins-as-content; if it ever hurts, the fix is a tracker-side workspace identity captured at probe time, not a foreign key.
- **`UNIQUE (connection_id, issue_id)`** is the idempotency rule made structural — the workspace-level "never duplicates" holds even against two windows importing in the same instant.
- `issue_url` is the canonical link back to the origin, captured at import so surfaces can offer "open in tracker" without a live fetch. **Deliberately absent:** the issue's `status` (a live fact about the tracker, derived when wanted, never stored — the standing rule) and any content columns (the content is the root commit; a copy here would be a second truth).
- `DELETE FROM plan_origins WHERE plan_id = …` joins `deletePlan`'s walk (alongside `plan_visits`), which is exactly M-102's contract: delete leaves no trace, so re-import after delete starts fresh.

### The root commit: kind `issue-revision`, published, human

The imported content lands as the history's root commit with `kind: "issue-revision"` — the kind the schema pre-declared for exactly this. The vault is explicit that "the root commit is the issue" and that upstream changes later land as more commits of the same species (M-109); starting the history with a `message` would force M-109 to retype the root. `authorKind: "human"` — import is a human act (and `CommitStore` refuses assistant roots: "opening a history is a human or import act").

`IssueRevisionCommitPayload` **(new, in `PlanningStore.ts`** beside `MessageCommitPayload`**)**: `{ title, description }` — the issue's content, nothing else. `url` is origin metadata (it lives in `plan_origins`); `status` is live tracker state and is not content.

`createHistory` is called with `rootPublished: true` — the one seam cut for this issue. Everything after the root goes through `append`, which hardcodes `published: false`; "commits after the root default to private drafts" therefore needs no code and one test.

Two derived rules then hold by construction, each pinned by an existing mechanism: `hasPublishedCommits` (an `EXISTS … published = 1` over the history) flips true at birth, so **delete is hidden and refused immediately** — `buildPlanRowMenuItems` already drops the verb and `deletePlan` already refuses with `PlanDeleteBlockedError`; and `derivePlanText` folds only `plan-revision` payloads, so the imported plan's **artifact is born empty** — the issue is what you plan _from_, not the plan text.

### `PlanningStore.importPlan`: the one write path

`importPlan(input: ImportPlanInput) → Effect<PlanImport, PlanningStoreError>` joins `PlanningStore` — import creates a plan, and the store already composes `CommitStore`; no new cross-store dependency arises because the issue's content arrives in the input rather than being re-fetched (rationale under "The wire" below). `ImportPlanInput`: `{ projectId, connectionId, issueId, issueUrl, title, description, createdAt }`. `PlanImport`: `{ detail: PlanDetail, outcome: "created" | "existing" | "resurfaced" }`.

One transaction:

1. Require the project (`MercurianProjectNotFoundError` otherwise).
2. Look up `plan_origins` by `(connection_id, issue_id)`.
   - **Found, active** → outcome `"existing"`, return the existing plan's detail. No write, no `announceChange`.
   - **Found, archived** → clear `archived_at` (the existing `unarchivePlanRow`; `updated_at` untouched, the M-102 rule — the plan returns to its old place, resurfacing is not activity), outcome `"resurfaced"`.
   - **Not found** → mint `planId`/`historyId`/`commitId`; `commits.createHistory` with the `issue-revision` root and `rootPublished: true`; insert the plan row with `title: derivePlanTitle(title)` (the issue's title, first-line-capped at 80 exactly like every other plan title — the AC's "carries its issue's title" with the store's one title discipline) and `archivedAt: null`; insert the origin row; outcome `"created"`.
3. A `UNIQUE` violation on the origin insert (two windows racing) is caught, re-read as case "found", and answered as `"existing"`/`"resurfaced"` — the loser of the race gets the winner's plan, which is what idempotent means.

`announceChange` fires for `"created"` and `"resurfaced"` (the tree changed) and not for `"existing"`.

**Ungrounded at birth is by construction, not by code:** plans have no repository columns anywhere in the schema (grounding is project-level, "derived, never assigned"), so the AC's "no repository associations" is the absence this plan preserves — the checklist's negative constraint is that `importPlan` touches nothing repository-shaped.

### The wire: one method, one projection gap closed

`mercurian.importPlan` joins `MERCURIAN_WS_METHODS` in `packages/contracts/src/mercurian.ts` (it creates a plan; the planning surface owns it). `MercurianImportPlanInput`: `{ projectId: MercurianProjectId, connectionId: TrackerConnectionId, issue: TrackerIssue }` — the browse's own five-field shape, passed back verbatim (`mercurian.ts` imports the two tracker types from `mercurianTrackers.ts`; same package, no cycle). `PlanImportResult`: `{ detail: PlanDetail, outcome: Schema.Literals(["created", "existing", "resurfaced"]) }`. `"importPlan"` joins `MercurianPlanningError`'s operation literals.

**The issue content is client-supplied, deliberately.** The client just fetched the issue live through `listTrackerIssues`; the connector has no by-id read to re-fetch with, and adding one is M-109's refresh seam, not this issue's. Trust is not the objection it sounds like: `importPlan` rides the same operate scope as `appendPlanMessage`, which already lets the same caller write arbitrary content into any plan — a tampered import buys nothing a message doesn't. The server takes `issue.id`/`issue.url`/`title`/`description` from the input and mints everything else (ids, time, published flag) itself. The `status` field of the passed `TrackerIssue` is ignored — nothing stores it.

**The timeline projection gains its third member.** `PlanTimelineItem` (contracts and store) grows `{ _tag: "issue-revision", …PlanCommitFields, title, description }`, and `toTimelineEvent` projects `kind === "issue-revision"` instead of skipping it — otherwise the imported plan opens on a space whose only commit is invisible. The item carries its content (unlike plan revisions, whose text is elided to avoid quadratic re-sends): the root is one commit, its payload is human-scale, and the planning space "literally begins with the issue" — the conversation must show what was imported without waiting for M-109's issue artifact. `planText` derivation is untouched (an issue revision is not a plan revision).

Then the four standard touchpoints, each mechanical: `WsMercurianImportPlanRpc` in `rpc.ts` + `WsRpcGroup`; `importPlan → AuthOrchestrationOperateScope` in `RpcAuthorization.ts`; the `ws.ts` handler under `observeRpcEffect` (aggregate `"mercurian"`, `DateTime.now`, `MercurianProjectNotFoundError` passed through, everything else wrapped as `MercurianPlanningError({ operation: "importPlan" })`); no new subscription, so `EnvironmentSubscriptionRpcTag` is untouched.

### Client plumbing

`packages/client-runtime/src/state/mercurianPlanning.ts`: `importPlan` joins `createMercurianPlanningAtoms` as a `createEnvironmentRpcCommand` on the existing write scheduler. `apps/web/src/state/mercurian.ts`: `useImportPlan()` in the `useCreatePlan` shape. The browse needs nothing new — `useListTrackerIssues` (`apps/web/src/state/mercurianTrackers.ts`) shipped with M-98 exactly for this consumer.

### UI: the Import affordance in the new-plan flow

The vault places import in "a project's new-plan flow", and the fork's new-plan flow is the draft planning space. So:

- **`PlanningSpaceDraft`** (`components/mercurian/PlanningSpace.tsx`): the empty state ("What are we planning?") gains a second line of affordance — an **Import from a tracker** button under the title, opening the dialog. The draft's typed text is _not_ discarded on a successful import: the text was never consumed, and the one-draft-per-project store keeps it for the next born-blank plan. On success the dialog navigates to `/plans/$planId` (`replace: true`, the born-blank pattern).
- **`ImportIssueDialog.tsx` + `ImportIssueDialog.logic.ts`** **(new, `components/mercurian/`)**: the browse. Reads `useTrackers()`; with **no connections**, the dialog states what trackers are for and points at Settings → Trackers (reverse state, not a dead button). With connections: a connection picker (auto-selected when there is exactly one), a search input passed to the tracker (debounced live `listTrackerIssues` calls — the tracker is the only thing that knows how to search its own backlog), a paged list of five-field issue rows (title, id, status word as the tracker says it; `nextCursor` drives a Load more row), each row's `url` reachable as an "open in tracker" affordance. Selecting an issue and confirming calls `importPlan`. Outcome handling: `"created"` navigates; `"existing"` and `"resurfaced"` navigate too, with the existing toast pattern saying what happened ("This issue already has a plan" / "This issue's plan was restored from the archive") — idempotency reads as navigation, never as an error. While the dialog is open nothing is stored: the issue list lives in component state and dies with the dialog, which is what "fetched live, not stored" means in the UI.
- **Rendering the imported root:** `PlanTimeline.tsx` gains the `issue-revision` arm — a card in the conversation flow (it has a body, unlike a plan-revision row): a small header ("Imported issue" + relative time, `TicketIcon` or similar from the existing lucide family), the issue title, the description as `MessageText`. `DagExplorer.tsx`'s two glyph sites (`:381`, `:471`) add the same icon for `_tag === "issue-revision"`. The published flag already rides every wire commit, so the explorer's shared-vs-draft rendering needs nothing.

Mobile untouched, per every Mercurian issue so far.

### Docs (AGENTS.md §Hit every surface)

`docs/user/trackers.md` gains the import walk (browse from a project's new plan, what re-import does, born published, the origin link) — or a cross-linked section in `docs/user/projects-and-plans.md` where plan creation is documented; implementation's call on which file leads. `docs/internals/glossary.md`: **Issue import**, **Origin (plan)** entries beside the existing Tracker family. `docs/internals/overview.md`: a sentence for `plan_origins` and the import path.

### Gaps and findings carried out of discovery

- `toTimelineEvent` skipping unknown kinds means the naive version of this feature ships an invisible root — the projection arm is load-bearing, not polish. Flagged above, checklisted below.
- The reconnect-mints-a-new-origin cost (accepted, per the origins-are-content rule) is recorded in the migration header so M-109 and any future "merge duplicate plans" work inherit the reasoning.
- The vault's Issue Import / Issues / Trackers notes all say "What exists today: not built" — true today, stale the day this lands; the almagest vault wants its "what exists today" sections refreshed with the PR (a vault commit, not a repo file).
- M-109 (refresh, revisions) inherits: the `issue-revision` kind already typed end to end, the origin row to refresh from, and the missing connector `getIssue` it will add.
