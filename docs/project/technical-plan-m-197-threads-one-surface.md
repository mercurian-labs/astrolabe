## Design

### 1. The line runtime: thread at open or fork, slot at turn

`line_runtimes` (migration 017, landed) keeps binding `(planId, lineRootCommitId) → threadId`. Two changes, in **migration `018_LineRuntimeBirth`** (new): `line_root_commit_id` becomes nullable and a `fork_parent_commit_id` column is added, so a line can exist with a thread and no commits yet; and `mercurian_projects` gains `orchestration_project_id`, filled for existing rows by the same home-path lookup the service does today, so the upstream draft flow has a project to create threads in.

`LineRuntimeService.ensure` splits into what it already does in two halves:

- **`ensureThread({planId, lineRootCommitId | forkParentCommitId})`** — find-or-create the orchestration project (now read from the project row), `thread.create {title: plan.title, modelSelection: last-used, runtimeMode: last-used, branch: null, worktreePath: null}`, `thread.meta.update {workspaceMembers}` when a slot is already known, record the row. Idempotent; no slot. Called when a line is _opened_ with no runtime (legacy plan-only lines) and when a line is _forked_ (§7). A thread born here before any commit is invisible in Checkpoints until its first message lands; the plan already exists, so "nothing exists until its first commit" holds at the unit the sidebar lists.
- **`ensureSlot({threadId, holder})`** — the landed claim/re-claim/rename/`workspaceMembers` path with `wait: true` and `awaitLineBranches`, called from `ws.ts acquireLineSlot` on `thread.turn.start`, exactly where session turns claim today. The waiting-for-slot phase publishes as it does now.

A **new thread** is the upstream draft flow: `useHandleNewThread` un-parked with the Mercurian project's orchestration project as the draft's project; on first send `ChatView` runs `thread.create` + `thread.turn.start` (`:6083-6110`) unchanged; the reactor (§2) sees `thread.created` in a project with a Mercurian owner and no line runtime for that thread, creates the plan row and the pending line runtime, and the first `turn-start-requested` lands the root commit. `mercurian.createPlan` and `PlanningSpaceDraft`/`planDraftStore` retire; existing plan drafts (`t3code:plan-drafts:v1`) are migrated once into `composerDraftStore` draft threads (text and project; the model choice maps to `modelSelection` where it resolves) so drafts stay intact.

### 2. The history is recorded from the turn

`PlanningAssistant` becomes **`LineTurnReactor`** (`mercurian/assistant/LineTurnReactor.ts`, replacing `startTurn`, `stopTurn`, `answerQuestion`, `measureReconstruction`; the fold, `settleTurn`, `appendAssistantMessage`, memory-amendment staging, and `PlanTurnRegistry` use port whole). It subscribes to `engine.streamDomainEvents` (the `LineRuntimeRecordReactor` pattern) and, for threads `resolveThreadLine` knows:

1. `thread.created` in a Mercurian-owned project with no runtime row → plan row (title from the thread, project from the owner map) + pending line runtime.
2. `thread.turn-start-requested` → `planningStore.appendMessage({planId, parentCommitId: lineTip ?? forkParentCommitId, commitId: messageId, text, attachments, ranUnder})`, with the commit id set to the message id (new optional `commitId` on `appendMessage`; today it generates one). The first message on a pending line sets `line_root_commit_id` and clears `fork_parent_commit_id`. `ranUnder` derives from the event's `modelSelection` through `Providers` (instance → provider kind + model). Then `registry.open` and the turn frame as today. A turn refused by the registry (chain busy) is not possible on a serial orchestration thread; `PlanTurnActiveError` on the append path retires.
3. Provider events fold as today, keyed by thread; `turn.completed`/`aborted`/`session.exited` settle the assistant commit with `parentCommitId = messageId`.
4. `thread.deleted` for a line thread → the landed teardown; `thread.archived` is ignored (archive is the plan's).

Stop and answer are the upstream composer's: `thread.turn.interrupt` and `thread.user-input.respond` reach the engine as for any thread; the reactor observes `turn-interrupt-requested` only to keep its 5 s force-settle watchdog. `mercurian.appendPlanMessage`, `stopPlanningTurn`, `answerPlanningQuestion`, and `measurePlanReconstruction` delete from `MERCURIAN_WS_METHODS`, `operation`, `RpcAuthorization`, and the `server.test.ts` mock. `visitPlan`, `savePlanRevision`, `saveSpecRevision`, `readLineUncommittedDiff`, `recreateLineBranch` stay (the two save doors stay for the assistant's MCP tools and for M-214's migration; the surfaces stop offering them).

**Runtime mode and model** are the thread's, set by the upstream composer through `thread.runtime-mode.set` and the turn's `modelSelection`; the landed "set the mode before a differing turn" fix becomes unnecessary and is removed with `startTurn`. Last-used stickiness for a new thread is upstream's own (project default → last thread) — `planComposerStore.runtimeMode` and `workspaceSettingsStore.planningModel` retire from the send path (the setting page keeps its provider gate copy until M-199 decides).

### 3. Seams: preparation resumes, approvals unchanged

`MercurianTurnPreparation` stops forcing a fresh session. `prepare` returns `skipResume: true` only when the turn is the **first turn of a line that has ancestry** (a pending line just rooted from `fork_parent_commit_id`, or a legacy line's first orchestration turn), building the appendix + transcript preamble from the ancestor path as today; every later turn on the line returns identity, so the provider session resumes as upstream's does and the context meter reads it. The preamble's "transcript" is the ancestor path _up to the fork point_ (the line's own turns are in the session). `MercurianApprovalAutoResponder` is unchanged.

### 4. Contracts

- Delete: `appendPlanMessage`, `createPlan`, `stopPlanningTurn`, `answerPlanningQuestion`, `measurePlanReconstruction` and their inputs/results; `PlanReconstructionMeasure`; `PlanTurnRefusalReason` loses nothing (refusals now surface as upstream thread errors through `ThreadErrorBanner`: `line-branch-missing` and `repository-not-git` become `ThreadError` codes raised by `acquireLineSlot`).
- `PlanLineRuntimeRecord.lineRootCommitId` becomes nullable and gains `forkParentCommitId?`; `MercurianProject.orchestrationProjectId`.
- New: `mercurian.forkLine({planId, parentCommitId}) → {threadId}` (§7) and `mercurian.openLine({planId, lineRootCommitId}) → {threadId}` (§5), both thin over `ensureThread`.
- Nothing on `OrchestrationThread` or any orchestration command changes.

### 5. The thread space is the upstream view

`routes/_chat.threads.$planId.tsx` keeps its address and becomes the upstream thread route with a Mercurian resolver in front: `usePlanDetail(planId)` → the **current line** (search `line=<threadId>` if given; else the line last visited, recorded by `visitPlan`; else the first line's runtime) → `openLine` when that line has no runtime → `<ChatView environmentId threadId routeKind="server" threadSyncPhase headerContent headerBanner planPanel>` inside `SidebarInset`, byte-for-byte the upstream route's gating (`resolveThreadRouteRenderState`, `finalizePromotedDraftThreadByRef`). `?at=<commitId>` sets the **viewing position** for the surfaces (Plan/Spec as of then; Checkpoints highlight) and nothing else — the conversation is the line's thread regardless. `routes/_chat.threads.draft.$draftId.tsx` becomes the upstream draft route verbatim (its promotion navigates to `/threads/$planId?line=` once the reactor's plan row exists — the draft route waits on `usePlanDetail` by thread id, a new `planForThread` selector over the tree snapshot). `_chat.plans.*` and `_chat.sessions.$threadId` redirects stay; the sessions redirect lands on `?line=<threadId>` instead of `?at=`.

**Deleted:** `PlanningSpace.tsx` (1,557 lines) and `PlanningSpaceDraft`, `PlanComposer*` (+ logic, tests, catalog), `CodeView*`, `SessionRightPanelTabs*`, `ComposerFooterModeControls.tsx` (folded back into `ChatComposer`, i.e. the phase-B lift reverts), `PlanReconstructionMeter*`, `planComposerStore`, `planDraftStore` (after the one-time migration), `PlanTimeline.tsx` (its session card and changed-files join are moot: the timeline is upstream's, and the changed-files card is upstream's own `ChangedFilesCard` on the turn), `PlanNodePopover`'s "Show code" act (picking a checkpoint navigates; the working surfaces follow the line). `coverage.ts` classifications and `coverage.test.ts` pins follow. `useHandleNewThread` un-parks: `navigateToParkedThreadRoute` deletes and the upstream navigation returns, targeting `/threads/draft/$draftId` and `/threads/$planId`.

### 6. The panel: Checkpoints pinned, Plan and Spec as surfaces

`rightPanelStore` gains two surface kinds beside the existing `plan`: `{id: "spec", kind: "spec"}` and `{id: "checkpoints", kind: "checkpoints"}` (singletons, like `diff`). **Pinning** is one rule in the store, `PINNED_SURFACE_IDS = ["checkpoints"]`: `closeSurface`/`closeOtherSurfaces`/`closeSurfacesToRight`/`closeAllSurfaces` skip pinned ids, and `selectThreadRightPanelState` prepends the pinned surfaces to `surfaces` when absent, so a thread's strip always reads Checkpoints first. `RightPanelTabs` renders a pinned tab without `PanelTabCloseButton` (icon plain, no context-menu close items) — the one visible modification to the upstream strip, gated on a new `pinnedSurfaceIds` prop that upstream callers never pass. The plus menu lists Plan and Spec (`onAddPlan` already exists; `onAddSpec` joins; `planAvailable`/`specAvailable` true for line threads) and Checkpoints never, since it is always there. **Mercurian's default panel state** for a line thread is `{isOpen: true, activeSurfaceId: "plan", surfaces: [checkpoints, plan]}`, applied by the route wrapper once per thread key when the store has no entry — the vault's "a newly born thread opens showing Plan" — and afterwards the store's per-thread memory is upstream's, width included (`t3code:preview-panel-width`). Keyboard toggles, maximize, the sheet under 980 px, and the drag bounds are inherited untouched; `mercurian:plan-right-pane*` storage keys are dropped.

**Rendering.** `ChatView`'s `planPanel` slot renders `PlanArtifact` read-only (no `Edit`, `readOnly` always, `readOnlyAction` = Back to now when viewing past); a new `specPanel` and `checkpointsPanel` slot pair (two optional `ReactNode` props beside `planPanel`, the only `ChatView.tsx` edit in this section) render `SpecArtifact` read-only and `DagExplorer`. All three take the plan's graph, position, and stale sets from a `PlanSurfacesContext` the route wrapper provides (`usePlanDetail`, `buildPlanGraph`, `staleSpecLeafIds`, `stalePlanLeafIds`, position from `?at=`/`?line=`), so `ChatView` passes nodes, not data. `DagExplorer` loses `cornerControl` and `onColumnsWidthCapChange` (the panel's width is the panel's); picking a checkpoint navigates to `/threads/$planId?line=<its line's thread>&at=<commit>`; `onEditAndBranch` becomes Fork here (§7). The Checkpoints surface belongs to the plan, so the wrapper keys its pinned entries by plan as well as by thread: when the current line changes, the new thread key is seeded with the same pinned set and the previous key's working surfaces stay with their thread.

### 7. The header, the switcher, Fork here, banners and overlays

**Header** = `headerContent={<ChatHeader …/>}` with one addition: `ChatHeader` gains an optional `leadingActions?: ReactNode` rendered first in `data-chat-header-actions`; the wrapper passes the repository switcher (`resolveCodingSessionMember` over `thread.workspaceMembers`, shown when members > 1) and the switcher's selection flows back through the wrapper into `openInCwd`/`gitCwd`/scripts `worktreePath` and into `diffPanelStore` + `PreviewPanel` cwd for the working surfaces. `NarrowedGroundingNotice` rides `headerBanner` beside `LineBranchMissingBanner`. Before the first turn (`workspaceMembers` undefined) the wrapper passes no switcher and `ChatHeader` shows no git actions (its own `activeProjectName` gate plus a `workspaceReady` prop that hides scripts/open-in/git until members exist). Thread title rename → `mercurian.renamePlan`; the project crumb's new-thread → `useHandleNewThread` for the Mercurian project.

**Fork here.** `MessagesTimeline`'s user row gains an optional `onForkHere?: (message) => void` rendered as a ghost icon button beside copy (`:1065-1068`; tooltip "Fork here"); `ChatView` threads it through from a new optional prop. The wrapper's handler calls `mercurian.forkLine({planId, parentCommitId: parentOf(messageId)})`, seeds the new thread's composer draft with the message text (`composerDraftStore.setText`), and navigates to `?line=<threadId>`. `PlanNodePopover`'s edit-and-branch does the same. The origin line is untouched; the new line's branch and slot are born on its first turn as §1 says.

**Overlays.** `MemoryAmendmentSheet`, `MemoryNoteReader` (with its stack), and the memory-failure notice wrap `ChatView` from the route wrapper exactly as `PlanningSpace` mounted them (`:1095-1110`, absolute over the space); memory-note mentions join the mention sources through `ChatComposer`'s existing mention provider (a `MentionSource` for `mercurian.searchMemoryNotes`, the phase-B `mentions.sources` moved). `SlotWaitNotice` renders from the turn frame's `waiting-for-slot` phase through `headerBanner`.

### 8. Navigation, vocabulary, docs

Sidebar cards navigate to `/threads/$planId` (line resolved by the wrapper); the palette and keybinding labels are as landed. Vocabulary census stands; new strings: "Fork here", "Checkpoints" (tab), "Plan"/"Spec" (tabs and plus-menu entries), "Waiting for a working slot…". Docs: `docs/user/projects-and-threads.md`'s "The thread space" section is rewritten around the upstream layout (panel, tabs, plus menu, Fork here, terminal drawer, context meter), the right-pane and code-view subsections go, and `permission-modes.md` drops the "before a differing turn" note; `docs/internals/glossary.md` marks **Planning assistant** historical (→ **Line turn reactor**), adds **Pinned surface**, **Fork here**, **Pending line**; `overview.md`'s thread paragraph says the thread space is the upstream view.
