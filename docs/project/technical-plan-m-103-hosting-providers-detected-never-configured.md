# Technical Plan — M-103: Hosting providers: detected, never configured

_Generated from the Goal/AC of Linear issue M-103 (see the issue for the full AC). Implements backlog 043 (Phase 4 — Assistant and providers) on the t3code fork as it stands after M-96, under [ADR 001](../architecture/local-first-runtime.md) and [ADR 004](../architecture/fork-baseline.md). Design sources are the almagest vault notes the issue cites: Repositories (resolved 2026-07: discovery lives on the Repositories page; Settings stays preferences-only), T3code Source Control, Providers (temperament), Coding Session View, Settings._

**Goal, in one sentence:** surface hosting providers the way the design demands — presence probed, identity asked, remedy named, never a login flow or an enable toggle — on the Repositories page; derive each repository's provider from its remotes and show it on the row; light up publish-repository where a ready provider meets a remote-less repository; land the background fetch interval in Mercurian's Settings; and leave named, tested seams for the session-side PR affordances that M-119 (blocked on this issue) mounts.

**The central discovery finding:** almost all of the _detection machinery_ this issue needs already exists in the fork and is upstream-owned, working code — `serverDiscoverSourceControl` probes presence and identity per provider (`apps/server/src/sourceControl/SourceControlProviderRegistry.ts` `discover`, `SourceControlProviderDiscovery.ts`), provider-from-remotes derivation exists twice over (`packages/shared/src/sourceControl.ts` `detectSourceControlProviderFromRemoteUrl`; `apps/server/src/project/RepositoryIdentityResolver.ts`), per-worktree PR status and create-PR gating exist end to end (`subscribeVcsStatus` → `VcsStatusRemoteShape.pr` in `packages/contracts/src/git.ts:222–228`; `apps/web/src/components/GitActionsControl.logic.ts`), publish-repository exists as an RPC and a dialog (`sourceControl.publishRepository`; `GitActionsControl.tsx`), and the zero-able fetch interval exists as a server setting enforced by `VcsStatusBroadcaster` (`automaticGitFetchInterval`, `packages/contracts/src/settings.ts:528,556`). M-103 is therefore a _surfacing and seam_ issue: give these facts their Mercurian wire shape and their designed home, per the fork's seam rules — not a rebuild of detection.

**Scope fences.** Coding sessions do not exist yet — the tree has no session rows (`packages/contracts/src/mercurian.ts:252`: rollups extend "when those rows arrive") and the session header is M-119's, which this issue _blocks_. So the AC's session-facing clauses (create-PR in a session's git actions, PR status on coding-session rows) land here as the wire facts, gating helpers, and named upstream seams those surfaces consume; M-119 and the session issues mount them. The leaf record's PR link (Coding Sessions resolution: structured facts) belongs to the issue that creates leaves. The publish-repository affordance, by contrast, has a live home today — the repository row — and lands whole.

## Design

### AC1 — Provider standing, on the Repositories page

A **Hosting providers** section on `RepositoriesPage` — the resolved home ("here, on the Repositories page"; Settings stays preferences-only). New `components/mercurian/HostingProvidersSection.tsx` + shared logic (below), mounted by `RepositoriesPage.tsx` above the repository list (standing is about the machine; the rows below are about what it serves).

- **Data**: the existing `sourceControlEnvironment.discovery` query atom — the same read the add dialog already gates on. One probe source for the whole app; no new server surface. The section renders `result.sourceControlProviders` only: hosting is this section's subject, and git-ness already lives per-row as `hasGit` (the VCS rows — git version, Jujutsu "coming soon" — are the inherited page's furniture, not this design's).
- **Presentation**, adapted from `SourceControlSettings.tsx`'s `DiscoveryItemRow` but Mercurian-owned: provider icon (`components/Icons` — `GitHubIcon` etc., the `SOURCE_CONTROL_PROVIDER_ICONS` mapping pattern) with status dot; the three standings in words — _authenticated as whom_ (account via `RedactedSensitiveText`, imported — it is a generic widget), _present but not signed in_ (the exact remedy: sign in with the provider's tool, named), _not installed_ (the `installHint` remedy verbatim). Bitbucket's CLI-less api-type discovery (`SourceControlProviderDiscovery.ts` `type: "api"`) renders the same way — its remedy is credential-shaped, in discovery's words.
- **Deliberate omissions**: **no Switch at all** — t3code renders a permanently disabled toggle; the vault's line is "there are no enable toggles," so Mercurian drops even the read-only control (the status dot and sentence _are_ the standing). No login flow, no per-provider actions. A **rescan** button (the t3code affordance) refreshes discovery _and_ the repository facts (`refreshRepositories`, below), so one click re-answers the whole page.
- **Shared vocabulary**: `AddRepositoryDialog.logic.ts`'s `buildProviderReadiness` / `providerLabel` / `REPOSITORY_PROVIDER_KINDS` move to a new `components/mercurian/hostingProviders.logic.ts` **(new)**, re-imported by the dialog (its tests move too). The section, the dialog's gated rows, the publish affordance, and — later — M-119's session git actions all speak readiness from this one helper, which is what keeps "the same remedy messages" true across surfaces (T3code Source Control: "gated by the same discovery readiness the settings page displays, with the same remedy messages"). New helpers land beside it: `providerStanding(discovery, kind)` (the three-way standing + remedy for the section) and `repositoryHostingStanding(hosting, discovery)` (the row join, AC2).

The inherited `/settings/source-control` page is **left untouched**, per the recorded SettingsNav rule for the Application group. Relocation here means the Mercurian surface is the Repositories page and nothing Mercurian-side links to the inherited page; retiring the fork page wholesale is the standing open decision on the inherited sections, not this issue's.

### AC2 — The provider a repository row shows is derived from its remotes

**Server.** `RepositoryStore` gains a second live probe beside `hasGit`, same pattern, same discipline (derived, never stored — the 003 migration header explicitly reserved this):

- `probeHosting(path)`: `git -C <path> remote -v` via `ProcessRunner` (no shell — the `RepositoryIdentityResolver` precedent), parse fetch remotes, pick the primary remote preferring `origin` (the `selectProviderContext` / `pickPrimaryRemote` rule), classify with the shared pure `detectSourceControlProviderFromRemoteUrl` (`@t3tools/shared/sourceControl` — already the registry's own classifier). Result: `{ provider, providerName, remoteName, remoteUrl } | null` — `null` when the directory has no git or no remote. A remote on an unrecognized host classifies as `kind: "unknown"` with the host as its name; it renders as a plain fact with no affordances (no tool serves it), and the registry's CLI-based `refineUnknownRemote` polish for self-hosted instances is deliberately not rebuilt here (carried as a finding).
- Cached in a store-owned `Cache` beside `gitProbeCache` (same short TTL and capacity), keyed by path, **with store-owned invalidation** — the reason this probe lives in the store rather than depending on `RepositoryIdentityResolver` (whose cache exposes no invalidation, and whose service belongs to upstream project machinery; M-96's gap note pointed at it as "the natural dependency," but the arrival of an explicit refresh act, below, makes owned invalidation the deciding requirement — the same derivation is reused via the same shared classifier, so nothing is duplicated but twenty lines of remote-parsing).
- `getSnapshot` joins it per repository exactly as `hasGit` joins today (`RepositoryStore.ts:619–643`); `RepositoryView` in `mercurian/repositories/schema.ts` gains the field.

**Wire.** `contracts/src/mercurianRepositories.ts`: new `MercurianRepositoryHosting = Schema.Struct({ provider: SourceControlProviderKind, providerName, remoteName, remoteUrl })` (kind imported from `sourceControl.ts` — the wire vocabulary both sides already share), and `MercurianRepository` gains `hosting: Schema.NullOr(MercurianRepositoryHosting)`. The module doc's "two facts are deliberately derived rather than stored" becomes three. `mercurian/repositories/wire.ts` maps it through.

**One new method** on the existing map: `refreshRepositories: "mercurian.refreshRepositories"` — invalidates both probe caches and publishes `changes`, so the snapshot re-emits with fresh facts. Input `{}`, output void. It exists because probed facts otherwise refresh only when a mutation re-emits the snapshot (fine for `hasGit`'s "flips on its own" story within a session, wrong for a page whose rescan button promises a re-answer, and needed the moment publish-repository changes a remote out from under a 30-second cache). Scope: `AuthOrchestrationReadScope` — it changes no state, same trust posture as `serverDiscoverSourceControl` (`RpcAuthorization.ts:81`). Touchpoints are the mechanical four: contracts map + schemas, `rpc.ts` const + group membership, `RpcAuthorization.ts` scope, `ws.ts` handler (`"rpc.aggregate": "mercurian"`).

**Client.** `client-runtime/state/mercurianRepositories.ts` adds the `refreshRepositories` command to `createMercurianRepositoryAtoms` (same write scheduler); `apps/web/src/state/mercurianRepositories.ts` exports `useRefreshRepositories()`.

**Row UI.** `RepositoryRow` gains a hosting line beside the environment badge: provider icon + name, and the account standing joined client-side by `repositoryHostingStanding` — the provider on the row meets the discovery result: _"GitHub · authenticated as venk"_, _"GitHub — gh is not signed in"_ (remedy words from the shared helper), _"github.com remote — no provider tool detected"_ for unknown kinds, and for a git repository with no remote, the publish line (AC3). Presentation helpers extend `RepositoriesPage.logic.ts`. **Nothing is assignable anywhere** — there is no control, no picker, no override; the line is a rendering of a probe, which is the AC's "never assignable" made true by construction (no wire input exists that could set it, no column exists that could hold it).

### AC3 — What an authenticated provider lights up

**Publish-repository — lands whole, now.** The repository row where `hasGit && hosting === null`:

- When at least one provider is ready (shared readiness helper): the no-remote line becomes an affordance — _"No remote yet — publish repository…"_ — plus a **Publish repository…** row-menu item. Opens `components/mercurian/PublishRepositoryDialog.tsx` **(new)**, adapted from the inner dialog in the fork's `GitActionsControl.tsx` (`:367–478`): provider picker over _ready_ providers only, `owner/repo` input prefilled from the discovery account + repository name (the fork's prefill move), private/public visibility, calling the existing `sourceControlEnvironment.publishRepository` command with `{ cwd: repository.path, provider, repository, visibility }`. On success: `refreshRepositories()` — the row flips to its provider standing without waiting out a cache TTL.
- When no provider is ready: **no affordance appears** — the row keeps a plain "No remote" fact. The AC's "without one, none of these appear" is the readiness helper returning nothing, not a disabled button (a disabled publish button would be a remedy surface for the _repository_, but the remedy belongs to the _provider_, which the standing section above already names).

**Create-PR and PR status on session rows — the seam, named.** These surfaces are M-119's and the session issues'; M-103 makes them a wiring job rather than a design job:

- _Create-PR gating_: `subscribeVcsStatus` on a session's worktree already carries `sourceControlProvider` (derived from remotes, per-cwd, live — `contracts/git.ts:204`), `hasPrimaryRemote`, and `pr`; `GitActionsControl.logic.ts` (`buildMenuItems`, `resolveQuickAction`) already gates create-PR on exactly these and degrades to publish/commit when hosting is absent — including provider-correct vocabulary ("merge request" for GitLab) via `sourceControlPresentation.ts`. M-119 adapts this control for the session header; what it inherits from M-103 is the readiness/remedy helper (`hostingProviders.logic.ts`) so a missing provider names its remedy with the same words the Repositories page shows.
- _PR status on coding-session rows_: the fork's row treatment is `ThreadStatusIndicators.tsx` (PR icon colored open/merged/closed, click-through) fed by the same `VcsStatusResult.pr`. Session rows arrive with the session issues; this is the recorded pattern they mount, and the tree contract's rollup vocabulary already anticipates the rows (`mercurian.ts:252`).
- _The leaf record's PR link_: Coding Sessions resolved the leaf to structured facts including "a PR link when one exists" — that lands with the leaf itself, out of scope here.

**The freshness rule is already right**: the PR fact rides `VcsStatusRemoteShape`, refreshed by `VcsStatusBroadcaster` on the `automaticGitFetchInterval` and by explicit git actions — which is exactly the AC4 wiring below, and why zeroing the interval leaves PR status moving only on explicit acts.

### AC4 — The fetch interval, in Mercurian's Settings

`routes/settings.preferences.tsx` trades its `SettingsEmptyPage` for `components/mercurian/PreferencesSettings.tsx` + `PreferencesSettings.logic.ts` **(new)** — the first real preferences content, deliberately one row so the page stays honest about what exists (the placeholder's other promises — worktree base, confirm-gates — belong to their issues):

- **Background refresh** — a seconds `NumberField` (the `ui/number-field` widget) over the _existing_ server setting: read via `usePrimarySettings` + `resolveServerBackgroundActivitySettings`, written via `useUpdatePrimarySettings` as a `backgroundActivity` override with `profile: "custom"` — the exact write shape of the fork's `GitFetchIntervalSettings`. The two small pure builders (`normalizeFetchIntervalSeconds`, the override-patch assembler) are reimplemented in the Mercurian `.logic.ts` with tests rather than exported from the fork's settings component — twenty lines against editing an upstream file (the seam rule), and the underlying storage is shared so the two surfaces cannot disagree.
- **Zero is a designed state and the copy says so**: "Set to 0 and remote status refreshes only when you act — credential prompts never fire in the background." The behavior is already enforced server-side: at zero, `VcsStatusBroadcaster` skips the background loop's work (`:397`) and even the subscription-time initial pass runs with `refreshUpstream: false` (`:418`) — no fetch, no credential prompt. Nothing server-side changes in this issue.
- A reset affordance when the value differs from the profile default (`getBackgroundActivityPresetSettings`), the fork's own settings temperament ("every row knows its own default").

The inherited `/settings/source-control` page keeps its copy of the same control; same setting underneath, so no divergence is possible.

`docs/user/` Repositories page: provider standing (the three standings and their remedies, no sign-in of the app's own), the derived provider on rows, publish-repository. `docs/user/` settings page: the background refresh preference and its zero semantics. `docs/internals/glossary.md`: **Hosting provider** entry (detected, never configured; derived from remotes) beside the Repository disambiguation family.

### Gaps and findings carried out of discovery

- Session surfaces don't exist; the tree contract already reserves their rollup vocabulary. AC3's session clauses are seams here and mounting work in M-119 — which is blocked on this issue, so the dependency arrow matches the design layering.
- `refineUnknownRemote` (CLI-refined self-hosted classification) exists upstream for the _operation_ path (`SourceControlProviderRegistry.resolveHandle`) but is not rebuilt for the row's display probe; a self-hosted GitHub Enterprise remote whose host string lacks "github" shows as an unknown-host fact until that polish is wanted.
- The vault's T3code Source Control note lists review-a-PR threads among what an authenticated provider lights up; Mercurian's design has no analog surface and the AC doesn't carry it — untouched, flagged for the vault's session-era reconciliation.
- `sourceControlPresentation.ts` (provider icons, PR/MR terminology) is web-level and fork-owned but import-safe; Mercurian components already import fork `ui/` freely — no extraction needed.
