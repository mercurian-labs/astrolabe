# Technical Plan — M-147: Mobile planning space

_Generated from the Goal/AC of Linear issue M-147 (see the issue for the full AC). **Stack context:** branch `venk/m-147-mobile-planning-space` stacks on `venk/m-146-mobile-plan-list`, whose plan establishes the mobile Mercurian state bridge (`apps/mobile/src/state/mercurian.ts` wrapping `createMercurianPlanningAtoms`), the plan-list home, and a stub planning-space route that this issue fills in — those are treated as present here, and file/route names attributed to M-146 below should be reconciled to what its branch actually lands. Downstream, M-148 adds the history Thread view and M-149 the Checkpoint Graph on touch; this plan leaves them room, not affordances. Design sources are the almagest vault notes: Plans (the planning space), Composer (suggested messages aside, the send/stop/gate/draft contract), Right Sidebar (the phone-width ruling: pane and conversation stack under one full-width header, pane above), and Assistant (per-branch provider/model choice derived from history)._

**Goal, in one sentence:** a plan opened on the phone shows its conversation for the path you stand on, keeps the current plan artifact one toggle away as a read-only standing view, and gives you a working composer — send-becomes-stop, one turn at a time, surviving drafts, the branch's model choice shown and switchable, and every can't-reply reason said out loud before send.

**Scope, stated plainly:** reading and replying only. No plan-artifact editing (desktop-first per the issue), no spec pane, no implement flow, no checkpoint picking or edit-and-branch (M-148/M-149), no @-mentions and no image attachments (no AC line; the draft shape stays extensible), no plan creation (M-146 already excludes it).

## What discovery found

- **The data layer is already shared and already reachable from mobile.** `packages/client-runtime/src/state/mercurianPlanning.ts` (`createMercurianPlanningAtoms`) exposes the `plan` subscription (`subscribePlan` folded through `Stream.scan(EMPTY_PLAN_STATE, applyPlanStreamItem)`) and every command this issue needs — `appendPlanMessage`, `stopPlanningTurn`, `answerPlanningQuestion`, `visitPlan`, `getPlanTextAt` — serialized per `[environmentId, planId]` so a stop pressed after a send lands after it. The fold in `packages/client-runtime/src/state/planReducer.ts` is documented "pure, so web and mobile share it": it already carries the streaming turn (`detail.inFlightTurn`, delta/grounding/question frames, replay guards) and the transient `turnRefusal`. `apps/mobile/package.json` depends on `@t3tools/client-runtime` (workspace), mobile imports ~40 of its subpaths, and the `./state/mercurian-planning` subpath resolves. Cross-client liveness (AC 8) is this one subscription — nothing new crosses the wire in this issue.
- **The web planning space is the behavior to mirror, and its pure half is portable.** `apps/web/src/components/mercurian/PlanningSpace.tsx` derives everything the phone needs from the subscription plus framework-free `.logic.ts` siblings: `PlanGraph.logic.ts` (`buildPlanGraph`, `ancestorClosure` — the only runtime import, `d3-dag`, is confined to the `dagLayout` half), `PlanPosition.logic.ts` (`LATEST`/`advance`/`resolveHead`/`resolveActingHead`, per-window and transient by design), `PlanModelChoice.logic.ts` (`standingModelChoice` walks first-parents for the nearest `ranUnder` record), `PlanComposer.logic.ts` (`resolveComposerControl` — one control, two faces, no queueing — plus `planningModelGateNotice`/`turnRefusalNotice`, the wording for every can't-reply reason), and `PlanArtifact.logic.ts` (`snapshotTextIsForPath`, zero imports — when the snapshot's `planText` answers for another path, `getPlanTextAt` is the read). The visible timeline is the ancestor closure of the resolved head; the in-flight turn renders only when its `parentCommitId` is on that path; a send places the position live at the sent commit and `advance` rides the branch forward. The one non-portable import in the gate wording is `providerLabel` (contracts' `PROVIDER_DISPLAY_NAMES` plus a six-line title-case fallback from web's `providerModels.ts`).
- **The model machinery.** `resolvePlanningModel` and `PlanningModelResolution` (`unset` / `resolved` / `unresolved: no-instance | not-signed-in | model-unavailable`) live in `packages/contracts/src/mercurianWorkspace.ts` — the AC's four reasons are exactly `unset`, `no-instance`, `not-signed-in`, `model-unavailable`. The last-used seed arrives via `createMercurianWorkspaceAtoms` (`@t3tools/client-runtime/state/mercurian-workspace`); provider snapshots are the server-config stream — client-runtime's `createServerEnvironmentAtoms` already exposes `providersValueAtom(environmentId)`, and mobile's `apps/mobile/src/state/server.ts` already instantiates it. Web additionally overlays local settings (`withProviderSettingsOverlay`) to hide probe lag after a same-machine instance toggle; mobile has no instance toggles, so the overlay's reason doesn't exist there. The effective choice chain in `PlanningSpace.tsx`: draft flip scoped to head (`modelChoiceForHead`) ?? `standingModelChoice` ?? the workspace's last-used pair; `appendPlanMessage` carries `modelChoice`, and the sent message's `ranUnder` makes it the branch's record.
- **Mobile's own conventions are mature and specific.** State: one thin module per domain in `apps/mobile/src/state/` calling a `create*Atoms(connectionAtomRuntime)` factory; reads via `useAtomValue`/`useEnvironmentQuery` (`state/query.ts`, tolerates a `null` atom); writes via `useAtomCommand` (`state/use-atom-command.ts`) with `environmentId` passed explicitly — mobile is multi-environment and has no primary-environment atom; thread routes carry `environmentId` in params (`Stack.tsx`, `THREAD_LINKING_PREFIX = "threads/:environmentId/:threadId"`). Navigation: react-navigation native-stack **static API**, flat routes with `linking` strings, `StaticScreenProps` params, per-screen options via the `NativeStackScreenOptions` component, iOS glass header items (`unstable_headerRightItems` + `withNativeGlassHeaderItem`) with an explicit `AndroidScreenHeader` fallback (`headerShown: Platform.OS !== "android"`). Markdown: the dual-renderer ternary — `hasNativeSelectableMarkdownText() ? <SelectableMarkdownText…> : <Markdown…>` (nitro-markdown fallback) — with `apps/mobile/src/features/files/FileMarkdownPreview.tsx` as the canonical read-only document recipe (`ScrollView` + `--color-md-*` token styles). Streaming is just a growing string; no streaming prop. Drafts: `apps/mobile/src/state/use-composer-drafts.ts` — an `Atom` of `Record<draftKey, draft>` keyed `"<environmentId>:<threadId>"`, persisted to a schema-versioned JSON file under `Paths.document`, debounced through a `SerializedAsyncQueue`, empty drafts deleted, pure reducers exported for tests. Composer primitives: `ComposerEditor` (`src/native/T3ComposerEditor.types.ts` — controlled `value`/`onChangeText`/`placeholder`/`onSubmit`), `ControlPill` (`icon="arrow.up"` primary ↔ `icon="stop.fill"` danger is exactly the thread composer's send↔stop swap), `ComposerToolbarTrigger`, and the `ThreadSettingsSheet` RN-`Modal` bottom-card pattern for model choice.
- **Mercurian does not exist on mobile yet** (zero grep hits) — M-146 opens the door; this plan walks through it. ADR 004 (`docs/architecture/fork-baseline.md`) parked `apps/mobile` because upstream churns there most; the M-146–149 series is its revival (vault design now exists), and the additive discipline matters most here: Mercurian mobile code lands in its own feature and state modules, upstream-owned mobile files (ThreadComposer, ThreadFeed, FileMarkdownPreview) are studied, not edited.
- **Gap the AC exposes:** the pure planning-surface logic mobile must share currently lives under `apps/web/`, which no package can import. The repo's stated home for client logic shared by web and mobile is `packages/client-runtime` (AGENTS.md; `planReducer.ts` is the in-domain precedent). The plan's one structural move addresses exactly this.

## Design

### Move the pure planning-surface logic to client-runtime; web keeps its paths via shims

The significant structural call. Mobile needs `buildPlanGraph`/`ancestorClosure`, the position model, `standingModelChoice`, the composer control/notice functions, and `snapshotTextIsForPath` — all framework-free today, all under `apps/web/`. Duplicating them on mobile forks the exact wording of the four gate notices and the exact follow/one-turn semantics the AC pins across surfaces; the repo's own precedent (`planReducer.ts`) and AGENTS.md name client-runtime as the home. So five files move, mirroring the web names:

- `packages/client-runtime/src/state/planGraph.ts` **(new)** — from `PlanGraph.logic.ts`: the types (`PlanGraph`, `PlanGraphNode`, `PlanCheckpoint`, `PlanCheckpointEffect`), `buildPlanGraph`, `ancestorClosure`, `descendantClosure`, `hasFork`, `planCommitSummary`, `planCommitDetail`. The `d3-dag` half (`dagLayout`, `Spatial*`, `PlanExplorerView`, `effectivePlanExplorerView`) **stays in the web file** — layout is the DAG explorer's concern and `d3-dag` must not become a client-runtime dependency.
- `packages/client-runtime/src/state/planPosition.ts` **(new)** — `PlanPosition.logic.ts` wholesale.
- `packages/client-runtime/src/state/planModelChoice.ts` **(new)** — `standingModelChoice`.
- `packages/client-runtime/src/state/planComposer.ts` **(new)** — from `PlanComposer.logic.ts`: `resolveComposerControl`, `planningModelGateNotice`, `turnRefusalNotice`, `implementFailureNotice`, `turnAwaitsInput`; plus `providerLabel` (contracts' `PROVIDER_DISPLAY_NAMES` with the title-case fallback inlined — a bounded six-line duplication of upstream `providerModels.ts` rather than an upstream edit); plus `modelChoiceForHead` and its `PlanDraftModelChoice` type lifted from web's `planComposerStore.ts` so both surfaces share the "a flip only applies where it was made" rule.
- `packages/client-runtime/src/state/planArtifact.ts` **(new)** — `PlanArtifact.logic.ts` wholesale (`snapshotTextIsForPath`, `lastPlanRevision`).

Each gets a `./state/plan-*` entry in the client-runtime `exports` map. The web `.logic.ts` files become one-line re-export shims (PlanGraph.logic keeps its layout half beside the re-exports; PlanningModel.logic's `providerLabel` becomes a re-export), so **no web component file changes at all** and the many existing web imports stay valid. The colocated web tests move with the logic into client-runtime (the PlanGraph test splits: graph-core cases move, layout cases stay). This is deliberately a move-plus-shim, not a refactor of consumers: while upstream tracking is live, the smallest diff that de-forks the logic is the right one.

### The state bridge grows two modules

- `apps/mobile/src/state/mercurian.ts` **(edit; established by M-146)** — alongside M-146's tree/list hooks, add the plan-detail read: `usePlanDetail(environmentId, planId)` flattening `mercurianPlanning.plan({ environmentId, input: { planId } })` to web's `PlanDetailState` shape (`detail`, `readyCommits`, `isPending`, `error`, `turnRefusal`, `implementFailure`) via `useEnvironmentQuery`'s null-atom idiom for the guard phase. Commands need no wrappers — screens call `useAtomCommand(mercurianPlanning.appendPlanMessage, …)` etc. directly, the mobile idiom.
- `apps/mobile/src/state/mercurianWorkspace.ts` **(new)** — `createMercurianWorkspaceAtoms(connectionAtomRuntime)` plus `usePlanningModel(environmentId)`: the last-used pair from the workspace-settings subscription, providers from `serverEnvironment.providersValueAtom(environmentId)`, `resolution` recomputed with contracts' `resolvePlanningModel`. **Deliberate divergence from web:** no settings overlay — the overlay masks probe lag after a _local_ instance toggle, and mobile has no instance toggles; a toggle made on desktop shows here after the next probe reconciliation, a transient cross-client lag we accept for the smaller model.

Environment identity: the route carries it. Mobile has no primary-environment atom and thread routes already spell `threads/:environmentId/:threadId`; the planning-space route follows as `plans/:environmentId/:planId` (this matches the stub M-146 lands — reconcile to its actual params if they differ).

### The screen: one full-width header, pane above conversation

`apps/mobile/src/features/plans/PlanRouteScreen.tsx` **(new; fills M-146's stub)** — guard/content split like `ThreadRouteScreen` (params normalized and branded before hooks run). The content component owns, mirroring `PlanningSpace.tsx`:

- **Position** — `useState<PlanPosition>(LATEST)`, reset on plan change; `advance(graph, position)` on every graph change; `resolveHead`/`resolveActingHead` for the standing and acting commits. No picker on this screen (M-148's), but the model is the full one: a send places the position live at its commit, so the surface follows the line _you_ extended even when another client forks — which is what "the path I'm standing on" costs.
- **Visible timeline and in-flight** — `ancestorClosure` filtering, and the in-flight turn shown only when its `parentCommitId` is on the path, exactly as web.
- **Visit** — the `visitPlan` effect keyed on `detail.plan.updatedAt`, unguarded (the server refuses no-op visits), which is what clears M-146's unread emphasis.
- **The pane toggle** — screen-local `useState<"conversation" | "artifact">("conversation")`. Opening always lands on the conversation (AC line 1); per the phone-width ruling, choosing the artifact stacks the read-only pane **above** the conversation under the one full-width header (both visible, flex-shared), and choosing it again closes it. The toggle rides the native header: an SF-symbol glass item on iOS (`NativeStackScreenOptions` + `unstable_headerRightItems`), an `AndroidScreenHeader` action on Android — the header also carries the plan's title from `detail.plan.title`. **Deliberate divergence from the desktop pane's "comes back the way you left it":** the AC's "opening a plan shows its conversation" is the phone ruling, so the pane state is per-visit and transient, not persisted. The state is a view union, not a boolean, so M-148's history view joins as a third member and its own header icon without reshaping — and no dead history button ships now.

### The conversation

`apps/mobile/src/features/plans/PlanTimelineList.tsx` **(new)** with pure row derivation in `planTimelineRows.ts` **(new, + test)**: `(visibleTimeline, inFlight, inFlightImplement) → rows` with stable keys and row types, so the list component stays a renderer. The list is `KeyboardAwareLegendList` (`@legendapp/list/keyboard`) with `alignItemsAtEnd` / `maintainScrollAtEnd` / `initialScrollAtEnd`, matching mobile's feed idiom — the phone needs its keyboard physics, and plan histories stay short so the estimated-size tuning is unfussy. Rows, restyled from web's `PlanTimeline.tsx` in mobile's grammar (uniwind tokens, `AppText`):

- **Human message** — right-aligned `--color-user-bubble` bubble (the thread feed's user-row language), text only.
- **Assistant message** — full-width markdown through the `SelectableMarkdownText` dual-renderer ternary; above it the grounding fold (collapsed count line, tap to expand — `Pressable` state) and the narrowed-grounding notice when `groundingScope` is present; below it a muted attribution line when `generatedBy` is recorded (`providerLabel(provider) · model`, the history explaining itself) and the interrupted mark when `interrupted` — a stopped reply is a commit, marked, not hidden.
- **Plan-revision / spec-revision rows** — the compact one-line effects ("You edited the plan", "The assistant revised the plan", split and cause variants), reusing the moved `planCommitSummary` ladders. This is AC line 1's "plan-revision effects visible".
- **Coding-session rows** — a compact, non-interactive record row (repository, branch, status); no "Open session" navigation — no session screen exists on mobile.
- **In-flight turn** — the assistant shape with the growing string (streaming is just re-render), a spinner/"replying…" status line, live grounding fold, and the **question card** when `questions` arrive: options as tappable rows (label + description, `multiSelect` honored), submit through `answerPlanningQuestion`. Included deliberately: the Goal's "answer it without returning to my desk" dies exactly at an awaiting-input turn otherwise — the composer is held (turn active) and only Stop would remain. Settled questions render as the read-only Q&A record.
- **In-flight implement** (started elsewhere) — a minimal "checking whether this plan is ready to implement…" row with Stop; it holds the composer like any turn. No proposal/split UI follows on mobile — the analysis lands as commits and rows.

Markdown styling: a Mercurian-local `apps/mobile/src/features/plans/markdownStyles.ts` **(new)** carrying the `FileMarkdownPreview` token recipe (`--color-md-*`, `useFontFamily`, appearance-scaled sizes) for both the assistant rows and the artifact pane — one Mercurian copy rather than editing the two upstream files that each hold their own (the M-123 mirror-not-extract stance, applied to mobile).

### The artifact pane

`apps/mobile/src/features/plans/PlanArtifactPane.tsx` **(new)** — the `FileMarkdownPreview` recipe: `ScrollView`, centered measure, dual-renderer markdown, no edit affordance at all (read-only by construction, not a disabled editor). Its text is `detail.planText` — live, because every revision folds into the subscription (AC line 2) — except when the standing path's last revision is not the last one anywhere: `snapshotTextIsForPath(timeline, visibleTimeline)` says so, and a `getPlanTextAt(planId, head)` read answers, with a quiet "Reading the plan as of then…" placeholder meanwhile (an empty artifact and an unread one must not look alike). A header line shows `lastRevisionLabel`-style attribution ("Edited by you · 2h ago") from the moved `lastPlanRevision`.

### The composer: send↔stop, gates first, drafts that stay

`apps/mobile/src/features/plans/PlanComposerBar.tsx` **(new)** — Mercurian-owned; the upstream `ThreadComposer` is studied, not reused (its thirty props carry runtime modes, worktrees, and an outbox that planning must not inherit). Built from the shared primitives: `ComposerEditor` (controlled, multiline, `onSubmit` for hardware Cmd-Return), the model trigger pill, and one `ControlPill` whose face comes from the shared `resolveComposerControl` — `arrow.up` primary when sendable, `stop.fill` danger while `turnActive` (`inFlightTurn ?? inFlightImplement`), held while a send is in flight. That derivation **is** the one-turn AC: no queueing exists because the control never offers send during a turn, on any client.

- **Send** — `appendPlanMessage({ planId, text, parentCommitId: actingHead, modelChoice })` via `useAtomCommand` with `reportFailure: false` (the composer speaks for itself); on success, position moves live to the sent commit and the draft clears. **No outbox for plan messages** (deliberate, unlike threads): the draft clears only on a non-null result, so a failed or offline send keeps your words in the composer — the honest smaller model for v1.
- **Stop** — `stopPlanningTurn(planId)`; the partial lands as an interrupted commit on the same subscription, and the timeline shows it marked.
- **The gate** — `planningModelGateNotice(choice, resolution)` renders as a quiet notice line docked above the editor; the send face is disabled while gated, typing stays live (drafts are drafts). The four reasons arrive worded exactly as on desktop because the wording moved, not forked. `turnRefusal` from the subscription renders as the transient backstop notice below it — the message that landed anyway, explained (`turnRefusalNotice`), covering the race the gate cannot.
- **The model trigger** — a `ComposerToolbarTrigger`-style pill showing the choice in effect where you stand: draft flip (`modelChoiceForHead`, scoped to `actingHead`) ?? `standingModelChoice(graph, itemsById, actingHead)` ?? the workspace's last-used pair; label via `providerLabel` plus the model's display name looked up in provider snapshots (raw slug when the machine doesn't list it — the record is never rewritten). Disabled while a turn runs: a change never retargets a reply in progress.

`apps/mobile/src/features/plans/PlanModelSheet.tsx` **(new)** with `planModelSheet.logic.ts` **(new, + test)** — the `ThreadSettingsSheet` presentation pattern (RN `Modal`, bottom-anchored card), listing **abstract pairs**: models grouped by provider, deduplicated by `(driver, slug)` across a driver's instances (choosing any instance of a provider records the same abstract pair — the vault's picker grammar), the standing pair injected as a row even when no instance offers it, signed-out models selectable (offering is capability; authentication gates sending). Picking writes the draft-local flip (`setPlanComposerDraftModelChoice` at `actingHead`) — nothing lands until the next message records it.

Drafts: `apps/mobile/src/state/use-plan-composer-drafts.ts` **(new, + test)** — a sibling of the thread draft store, same discipline (atom + schema-versioned `plan-composer-drafts/drafts.json` under `Paths.document`, 200 ms debounce through `SerializedAsyncQueue`, empty drafts deleted, pure reducers exported), keyed `"<environmentId>:<planId>"`, shape `{ text, modelChoice?: PlanDraftModelChoice }`. Leaving the plan and returning — or relaunching the app — restores it (AC line 5).

### What deliberately does not change

Contracts, the server, `packages/client-runtime`'s existing modules (`planReducer`, `mercurianPlanning`), every upstream-owned mobile file (`ThreadComposer.tsx`, `ThreadFeed.tsx`, `FileMarkdownPreview.tsx`, `Stack.tsx` — M-146 registered the route), and every web component. Web behavior is untouched by construction: its logic imports resolve to the same code through shims.
