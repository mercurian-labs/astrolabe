# Technical Plan — M-108: Composer: act from anywhere, forks, drafts, images

_Generated from the Goal/AC of Linear issue M-108 (see the issue for the full AC). Implements backlog 032 (Phase 3 — Planning space) on the planning space as M-106 left it (right pane, DAG explorer, anchored navigation — PR #11, merged), under ADR 001 (additive Mercurian server), ADR 002 (event/streaming model), and ADR 004 (fork baseline). Design sources are the almagest vault notes the issue cites: Composer, Commit Tree (fork guarantee resolved 2026-07), Plans ("transfers cleanly" list), DAG Explorer (navigate resolved), T3code Thread View (the machinery being reused)._

**Goal, in one sentence:** make the composer the single place a person acts in a planning space — from the tip of the conversation they're in or from any commit they've picked — so that sending from an earlier point lands a new fork whose first commit is their message, while the composer itself grows what the fork's thread composer already has: a per-plan draft that survives leaving, image attachments, mention chips, and one send/stop control.

**Scope, stated plainly (the issue's exclusions):** no suggested next messages (034 / M-112), no review-comment chips (035 / M-113), no assistant-side grounding (042 / M-104 — nothing streams in planning yet, so the Stop face of the send control and the no-queueing gate ship as a seam, exercised the day the assistant lands), and no concept mentions (Concepts is removed from the design — tombstone note). File mentions are **included but gated**: the chip mechanism lands whole; the _source_ of mentionable file names is the repository registry (040 / M-96), which does not exist yet, so the mention menu has nothing to offer until it does. The mechanism is verifiable with any candidate source, which is exactly how its tests feed it.

## Design

### Position generalizes: standing somewhere, live or looking back

M-106 built position as `now | anchored`, where `now` follows the globally-latest commit and `anchored` is a frozen look at the past with the composer disabled. Both halves stop being right the moment a send can fork: "now" as _globally_ latest would yank a window onto whichever branch last received a commit (two windows on two branches must be able to disagree about where they stand — ADR 002 §5's whole point), and "anchored disables the composer" contradicts the issue's core sentence — "the composer acts from wherever you stand."

The replacement, still per-window and transient (`PlanningSpace` state, reset on plan change, exactly as today):

```
type PlanPosition =
  | { readonly _tag: "latest" }                     // the landing default: the path through graph.latest
  | { readonly _tag: "at"; readonly commitId: MercurianCommitId; readonly live: boolean };
```

- **`latest`** is what opening a plan gives you — the path through the highest-sequence commit, which is always a leaf (a commit is born childless). Identical to today's `now` while history is linear.
- **`at` with `live: true`** — you stood somewhere deliberately and that somewhere was a branch tip when you stood there: you picked a leaf in the explorer, or you just sent a message. The conversation is live at _this branch's_ tip: the composer appends from here, the artifact is editable, and the surface **follows** this line as it grows — when a commit lands whose parent set includes your head, your position advances to it (chained, along the lowest-sequence child, until it rests on a leaf again). It never advances across branches: a commit landing elsewhere in the DAG moves nothing in this window.
- **`at` with `live: false`** — you picked an interior commit: you are looking back. The surface shows `ancestorClosure` through it (M-106's projection, unchanged), the artifact is read-only showing `getPlanTextAt` text (unchanged), and — the change — **the composer stays active**: sending continues from here, landing a new fork whose first commit is your message. A banner above the composer says where you stand and offers "Back to now" (→ `latest`).

`live` is stamped when position is set — `graph.byId.get(commitId).childrenIds.length === 0` at pick time, always `true` after an own send — and the follow rule only ever runs for live positions, so looking back is stable under arrivals, exactly as M-106 promised ("the projection through an earlier commit cannot change").

All of this is pure and lives in **`PlanPosition.logic.ts` (new)**, the `.logic.ts` convention applied: `resolveHead(graph, position)` (the commit the composer acts from; `graph.latest` for `latest`), `positionAfterPick(graph, commitId)` (leaf → live, interior → looking back, `graph.latest` → `latest`), `advance(graph, position)` (the follow step: live + children → lowest-sequence child, iterated to a leaf; everything else → unchanged), and `isViewingPast(graph, position)`. `PlanningSpace` runs `advance` in an effect over timeline growth and keeps the rest of its M-106 shape — the explorer's `onSelect` now routes through `positionAfterPick`, and its highlight input becomes `resolveHead` so it tracks the followed tip. The transient race where a subscription echo arrives before the send RPC resolves settles correctly: the RPC result sets position explicitly to the sent commit, and `advance` is idempotent from there.

One deliberate asymmetry: a _fork race_ — two windows live at the same head, both send — lands two siblings, a true fork. Each window follows its own commit (own send sets position; the follow rule prefers the first-born only when a window sat passively). Nothing is destroyed, both lines are real, and the explorer shows the branch point — this is the honest rendering of what happened, not an error to prevent. The store already serializes the writes; the client already serializes per plan (`serialPerPlan`).

### Send says where it stands: explicit parents on the write path

The M-106 plan recorded the finding this issue resolves: `PlanningStore.readTip` picks the _globally latest_ commit as append target — "fine while the UI cannot create forks, but wrong-shaped the day M-108 lands (a send should extend the _viewed_ path)." So the write path becomes explicit:

- **Contracts** (`packages/contracts/src/mercurian.ts`): `MercurianAppendPlanMessageInput` and `MercurianSavePlanRevisionInput` each gain `parentCommitId: Schema.optional(MercurianCommitId)` — _the commit this act continues from_. Absent means "the space's tip", which keeps the input honest for the one client that has no position yet (nothing else changes for callers that always pass it, which the web client now does). No new RPC methods, no new scopes — `RpcAuthorization` is untouched because the type-checked map keys on methods, not inputs.
- **Server** (`PlanningStore.ts`): `appendAtTip` generalizes to `appendAt`. Given `parentCommitId`, it resolves the parent through `CommitStore.getCommit` (visibility `all`) and refuses `CommitNotFoundError` when the commit is absent **or belongs to another plan's history** — the exact rule and phrasing `getPlanTextAt` established ("a commit of some other plan's history does not exist for this plan"). Given none, it reads the tip as today. Append stays inside one transaction; parents become `[parent]`; `authorKind` stays hardcoded `"human"`. The fork case needs no code of its own: appending onto a commit that already has a child _is_ the fork, and `CommitStore.writeCommit` already permits it for humans while refusing it for assistants — the resolved Commit Tree guarantee ("the product refuses assistant-created forks and merges as a hard rule") is already the store's law and this issue inherits it rather than restating it.
- **Error surface** (`ws.ts`): unchanged shape — `PlanNotFoundError` passes; `CommitNotFoundError` and everything else wrap into `MercurianPlanningError({ operation: "appendPlanMessage" | "savePlanRevision" })`. The client only names commits it received from this plan's own subscription, so a missing parent is a planning bug, not a refusal the surface renders (the M-106 rule, applied again).

**Plan revisions ride the same explicit parent** — an edit saved while live at a fork's tip must land on _that_ branch, not the global tip — but the UI offers Edit only when live. A revision that _opens_ a fork is thereby impossible to author from the product, keeping the vault's "a fork opens with a message" true where authoring happens. Deliberately, the store does **not** refuse a human revision-fork: the vault's hard rule (resolved 2026-07) is scoped to assistant forks and merges, and a store refusal here would turn a benign two-window race (edit saved just after a sibling send landed) into a failed save. Significant choice, flagged.

### The viewing-the-past composer replaces the disabled one

`BackToNowBar` (M-106) is superseded. When `isViewingPast`: the composer renders with a slim banner docked above it — `ClockIcon`, "Viewing an earlier point — sending starts a new branch from here", and the "Back to now" button (the reverse state, kept). The artifact keeps its M-106 read-only treatment with the same affordance. When live at a non-`latest` leaf (you followed a fork tip), no banner — you are simply _in_ that conversation; the explorer's highlight is what says which one. M-106's AC line "anchored disables composer and Edit behind Back to now" is amended by this issue's AC — worth recording in the M-106 issue as an addendum note at review time, the way M-106 itself amended its explorer AC.

### Attachments: the fork's pipeline, pointed at a plan

The issue's frame — "standing the existing composer machinery in the planning space, not building one" — meets the repo's additive-fork rule (thread machinery stays unimported by Mercurian code) cleanly here, because the attachment pipeline is _not_ thread machinery: `attachmentStore` resolves paths from an id alone, the assets door (`AssetResource` `"attachment"`) authorizes by id alone, and `ChatAttachment`/`UploadChatAttachment` are contracts-package schemas. All of it is reused as-is:

- **Payload and wire.** `MessageCommitPayload` gains `attachments: Schema.optional(Schema.Array(ChatAttachment))` — metadata only (id, name, mimeType, sizeBytes), so a commit's payload stays constant-size and the snapshot payload rule holds; bytes never ride the subscription. `Contracts.PlanMessage` gains the same optional field (imported from `orchestration.ts` — reusing the schema rather than minting a Mercurian twin keeps the byte caps, the id brand, and `attachmentStore`'s signatures in one place; significant choice, flagged). Optionality keeps decoding of every pre-M-108 commit total. `MercurianAppendPlanMessageInput` and `MercurianCreatePlanInput` gain `attachments: Schema.optional(Schema.Array(UploadChatAttachment))` — the birth message is a message, so the draft space composes with the same powers as every later one.
- **Server** — `apps/server/src/mercurian/planning/attachments.ts` (new): `normalizePlanAttachments(planId, uploads)` mirroring `Normalizer.ts`'s steps — cap count at `PROVIDER_SEND_TURN_MAX_ATTACHMENTS`, `parseBase64DataUrl`, byte bounds against `PROVIDER_SEND_TURN_MAX_IMAGE_BYTES`, `createAttachmentId(planId)` (the plan id is the store's UUID and passes the safe-segment rules the same way thread ids do), `resolveAttachmentPath`, mkdir + write via `FileSystem`. Called from the `ws.ts` handlers (`appendPlanMessage`, `createPlan`) before the store call — normalization is a boundary concern in this repo (`Normalizer.ts` precedent), and `PlanningStore` stays a sqlite-and-commits module. A refusal after files are written orphans them; that is the fork's existing failure shape (`Normalizer` has the same property) and is recorded, not solved, here.
- **Client.** The composer collects images by paste, drop, and file pick; `compressImageForStash` (`lib/imageCompression.ts`) bounds what persists in the draft; send maps them to `UploadChatAttachment` data URLs. `PlanTimeline` renders a message's attachments as a thumbnail grid above the text (the `MessagesTimeline` idiom, restated small on `ui/` primitives — not imported from it) with `useAssetUrl(environmentId, { _tag: "attachment", attachmentId })` resolving each image; `usePrimaryEnvironmentId` is already the web layer's one environment answer.

### Drafts: a plan keeps its unsent message

ADR 002 §5 names drafts client-local, and the vault agrees ("leave the planning space and come back, and it's still in the composer"). **`planComposerStore.ts` (new, `apps/web/src/`)**, beside `planDraftStore.ts` and in its idiom (zustand, hand-rolled schema validation on read, versioned key): per-plan `{ text, attachments }` keyed by `planId`, persisted to `mercurian:plan-composer-drafts:v1` through `createDebouncedStorage` (`lib/storage`, the `composerDraftStore` precedent, flushed on `beforeunload`). Text always persists; attachments persist as compressed data URLs with the fork's degradation rule — an image too large to persist stays session-only rather than blocking composing. Sending clears the plan's entry. `planDraftStore` (unborn plans, keyed by project) is untouched — different lifecycle, and its draft already survives leaving; the draft space simply gains attachments through the same composer component.

### The editor: chips stand ready, sources arrive with the registry

`PlanComposer`'s raw `<textarea>` is replaced by **`ComposerPromptEditor`** (`components/ComposerPromptEditor.tsx`) — the fork's Lexical editor, self-contained (it mounts its own `LexicalComposer`), taking `skills={[]}` and `terminalContexts={[]}`; it is the one piece of composer machinery this issue stands in the planning space, and it lives in `components/` root, not `components/chat/`, precisely because it is the shared editor rather than thread furniture. What it buys:

- **Mention chips.** A mention is an inline token in the message _text_ (`@t3tools/shared/composerInlineTokens`) rendered as a chip in the editor — so "the mention becomes a chip in the message and travels with it" is true with **zero wire change**: the token rides in `MessageCommitPayload.text` like any other characters. `PlanTimeline` renders sent messages through a small pure pass over `collectComposerInlineTokens`, showing mention tokens as chip spans (semantic tokens only). The mention _menu_ needs a candidate source — the plan's repositories, which arrive with the registry (M-96) — so in planning it has no provider and never opens; the mechanism (token parse, chip render, editor behavior) is complete and tested against synthetic sources. When M-96 lands, it plugs a file-name source in; nothing here changes shape.
- **Paste behavior** (image paste lands in attachments, not as text) comes with the editor's `onPaste` seam and the attachment collection above.

`PlanComposer` keeps its own shell — Mercurian-owned, on `ui/` primitives: the draft binding, the attachment chip row (thumbnails with remove), the banner slot, and **one send control**. Send and stop are one control by construction: the button's face derives from a composer state that today is only ever `idle | sending` (send disabled while a send is in flight — no queueing at the only concurrency that exists yet). The `streaming → Stop` face is the assistant's to light (M-104); this issue leaves the control's state derivation as the single seam that issue extends, and builds no dead stop plumbing. Ships-dark, recorded as a finding like M-106's `published`.

`PlanningSpaceDraft` swaps to the same `PlanComposer` capabilities (its send path is `createPlan`, now with attachments); `PlanComposer`'s `value/onChangeValue` controlled mode stays for it, backed by `planDraftStore` exactly as today.

### AC criteria that resolve by construction

- _"Sending from the tip continues the current conversation"_: live position's head is the branch tip; explicit parent = head; the follow rule keeps the window on the line it extends.
- _"Every fork begins with my message"_: the only fork-creating act in the product is a composer send from a picked commit; assistant forks are already store-refused (`AssistantForkError`), and artifact edits are only offered live.
- _"No second history"_: no new subscription, no reducer change — the sent commit arrives back through the one plan stream and folds in with the replay guard untouched (`parents`/`published`/`attachments` ride the existing item shape).
- _"Nothing is destroyed"_: navigation and sending write nothing but appends; there is still no rewind anywhere on the surface.

### Gaps and findings carried out of discovery

- **Stop ships dark.** Nothing streams in planning until M-104; the send control's `streaming` face and the awaiting-turn queue gate belong to that issue. The seam is the composer-state derivation in `PlanComposer`.
- **Mentions ship gated.** No mentionable source exists until M-96 (repository registry); the menu never offers. Token mechanics are complete and pinned by tests against synthetic sources.
- **Attachment orphaning on refused sends** mirrors the fork's `Normalizer` behavior — files written, then the append refused, leaves unreferenced files in `attachmentsDir`. Same blast radius as t3code today; a sweep is nobody's job yet. Recorded.
- **Mobile renders none of this** (`apps/mobile` has no planning surface; unchanged, per M-106's "do not touch" precedent).
- **`published` on sent commits is still uniformly false** (Publishing unbuilt, M-92 pending) — fork tips in the explorer all render as private work; unchanged from M-106.
- **Merge selection is still absent** (M-111): positions and parents are single-commit everywhere in this issue; the input shape (`parentCommitId`, singular) is deliberately not an array — M-111's merge is its own human act with its own confirmation, not an overload of send. Significant choice, flagged.
