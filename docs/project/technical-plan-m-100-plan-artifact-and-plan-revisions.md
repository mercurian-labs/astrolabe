# Technical Plan — M-100: Plan artifact and plan revisions

_Generated from the Goal/AC of Linear issue M-100 (see the issue for the full AC). Implements backlog 030 (Phase 3 — Planning space) on the commit store 010 landed (`docs/project/technical-plan-m-94-multi-parent-commit-model.md`) and the planning surface 020 landed (`docs/project/technical-plan-m-95-projects-plans-tree.md`), under [ADR 001](../architecture/local-first-runtime.md), [ADR 002](../architecture/event-streaming-model.md), and [ADR 004](../architecture/fork-baseline.md). Design sources are the almagest vault notes the issue cites: Plans, Commit Tree, Issue Planning Flow, Issue Revisions, T3code Thread View (inverted)._

**Goal, in one sentence:** make the plan itself exist — a first-class editable artifact rendered beside its conversation in the planning space, where a human's direct edit lands as a `plan-revision` commit interleaved with message commits in the plan's one history, attributable, at the same standing as a message, with the current text derived from the revision history along the current path — and, per ADR 002 §2, put the planning space on its live stream: `mercurian.subscribePlan` supersedes M-95's `getPlan`-then-refresh placeholder in this same issue.

**Scope, stated plainly (the issue's exclusions):** no Open Decision suggestions, no review comments, no merges, no issue revisions, no technical-plan derivation — and no assistant-authored revisions yet ("assistant-authored revisions become real with the real assistant; human direct edits ship here"). The substrate for assistant revisions already exists and stays open: `CommitStore` accepts `kind: "plan-revision", authorKind: "assistant"` at a tip today (`apps/server/src/mercurian/commitTree/CommitStore.ts`, invariant 3 refuses only assistant forks/merges/roots), so nothing in this plan needs to change when the real assistant arrives — it will write through the same append path, and its output will reach every window through the same subscription. The _transient_ frame shapes for in-flight turns (ADR 002 §3) are explicitly M-104 contract design; this issue ships the durable-commit events only, on a stream shape those frames extend. Also out of scope: the [[Right Sidebar]]/DAG Explorer (its own backlog entry; the vault's planning-space walk mentions it as a toggle, but the AC here asks only for plan-beside-conversation-with-composer).

## Design

### The artifact is a projection, not a table

The vault pins the model: "a plan edit is a commit, interleaved with message commits in one branching history" and "there is no separate 'chat log', 'edit history', or issue-change log" (Commit Tree). So the plan artifact gets **no new table and no text column on `plans`** — its current text is derived from the history, which is what the AC's "the plan's current text is the result of its revision history along the current path" literally asks for. `mercurian.sqlite` needs **no migration**: `commits.kind` already admits `'plan-revision'` (`001_CommitGraph.ts` CHECK constraint), and M-94 wrote it there precisely so "landing plan revisions … later is new rows, not schema surgery." ADR 002 §2 sharpens this into the streaming answer too: **the commit DAG is the durable log** — the artifact and the event stream are the same rows read two ways.

**Revision payloads are full-text snapshots, not diffs** (significant choice; rationale):

- Derivation becomes O(1) at any commit: the plan's text _at_ a commit is the payload of the nearest content-bearing commit at or above it on the path — no patch replay, no corruptible chain.
- Forks come free: each branch's text is its own path's latest snapshot, which is exactly the Commit Tree's branching semantics. Merges (later) get a reconciled snapshot as the merge's plan revision — the vault already says "a merge's output _is_ a plan revision."
- Plans are small human-scale documents; snapshot rows in a local SQLite are cheap. Diff-sized payloads would optimize storage nobody is short of, at the cost of making every read a fold. (What a revision _changed_ — a rendered diff — is a display question a later surface can answer by diffing two snapshots.) This is also ADR 002 §3's temperament applied to edits: the record is the settled snapshot, one commit per edit, never a finer-grained log.

The payload schema follows the `MessageCommitPayload` precedent and lives beside it in `PlanningStore.ts`:

```ts
/** What a plan-revision commit carries: the plan's full text after the edit. */
export const PlanRevisionCommitPayload = Schema.Struct({ text: Schema.String });
```

**The derivation rule, written to survive import** (the AC's "must not assume a blank root"): walking the current path tip-ward from the root, the plan's text is the payload text of the **last `plan-revision` commit on the path; if none exists, the empty string**. The rule is a total function over any path of any commit kinds — a born-blank plan (message root, no revisions yet) derives `""`, which is the AC's "empty artifact"; when Issue Import lands a non-message root, the same walk simply starts from that root and nothing here changes. Nothing anywhere assumes revision #1 is the artifact's birth, and nothing caches text outside the history.

### `CommitStore` grows the read surface the cursor needs (additive only)

ADR 002 §2 keys planning-space events by `commits.sequence` — which the migration has carried since M-94 (`001_CommitGraph.ts:27`) but the read model never exposed (`CommitRow`/`Commit` in `commitTree/schema.ts` omit it). Two additive edits, no behavior change to writes or invariants:

- `commitTree/schema.ts`: `Commit` gains `sequence: Schema.Number`; `CommitStore.ts`'s `commitColumns` selects it. Every existing read now returns it (append order was already the sort key — `ORDER BY commits.sequence ASC` throughout).
- `CommitStore.ts`: one new read, `listCommitsSince({historyId, afterSequence, visibility})` — `listCommitRows` with an `AND commits.sequence > ?` guard, same `withParents` join. This is the event query: "what happened in this history after my cursor," served by the log the store already is. (PlanningStore keeps composing `CommitStore` rather than touching `commits` tables itself — the store's stated boundary.)

### `PlanningStore`: one new write, one reshaped read, one live read

`apps/server/src/mercurian/planning/PlanningStore.ts` (edit — same service, canonical order preserved):

- **`savePlanRevision({planId, text, createdAt}) → PlanRevision`** — the human direct edit. Mirrors `appendMessage`'s shape: require the plan, then in **one `sql.withTransaction`**: read the history's tip, `CommitStore.append({kind: "plan-revision", authorKind: "human", parents: [tip], payload: {text}})`, `touchPlanRow`. Then `announceChange` (an edit is activity; the tree's `updated_at` ordering should reflect it, and the tree stream re-emits off this signal unchanged). Tip computation moves **inside** the transaction here — and `appendMessage`'s tip read (currently outside its transaction, `PlanningStore.ts:426–431`) is aligned to match in the same edit: two write paths onto the tip now exist, so the read-tip-then-append must be atomic in both. SQLite's single writer plus the client's serial-per-plan scheduling makes the race unlikely, but the invariant should hold by construction, not by scheduling.
  - `authorKind` is hardcoded `"human"` server-side, like every write this surface owns — the RPC carries no author field, so there is no way to spoof an assistant revision through this method. The assistant's own write path arrives with the assistant.
- **`getPlanSnapshot` (was `getPlan`) reshapes**: returns `{ plan, planText, timeline, snapshotSequence }` where `timeline` is the ordered projection of the path — the current `listPlanMessages` generalized:

  ```ts
  export type PlanTimelineItem =
    | { readonly _tag: "message"; commitId; sequence; authorKind; text; createdAt }
    | { readonly _tag: "plan-revision"; commitId; sequence; authorKind; createdAt };
  ```

  One list, in commit order — messages and plan revisions interleaved at the same standing, which is the AC's history requirement made literal. **Revision timeline items deliberately carry no text**: the current artifact crosses once as `planText`, and shipping every historical snapshot would grow the payload with the square of editing activity (AGENTS.md's performance temperament). Attribution (who, when) rides on every item via `authorKind`/`createdAt` — commit facts the store already returns. Unknown kinds are skipped, as `listPlanMessages` does today, so future kinds don't break this surface. `snapshotSequence` = the max `sequence` in the projection (`0` for an impossible empty history) — the stream cursor.
  - `planText` is computed from the same `listCommits` result the timeline projects — last `plan-revision` in path order, else `""` — one query, no second walk.

- **`listTimelineSince({planId, afterSequence}) → ReadonlyArray<PlanTimelineEvent>`** — the event read for the subscription: `CommitStore.listCommitsSince` projected to `{item, planText?}` pairs, where `planText` is present iff the commit is a `plan-revision` (its payload _is_ the new current text — no recomputation). This is what the `ws.ts` handler replays per change signal and per resume.
- `createPlan` and `appendMessage` keep their shapes (`createPlan`'s returned detail gains the new fields: `planText: ""`, one-message timeline, `snapshotSequence` — the AC's born-blank-starts-empty, by construction; `appendMessage`/`savePlanRevision` return their appended item with `sequence`).

No new refusals: `savePlanRevision` reuses `PlanNotFoundError`; commit-store refusals keep passing through untranslated per the store's stated convention.

### The wire: `subscribePlan` in, `getPlan` out, `PlanDetail` reshaped in place

ADR 002 §2, applied concretely: **`mercurian.subscribePlan`** is the planning space's read path — "the `subscribeThread` shape over the commit store: snapshot, then commit-appended events keyed by `commits.sequence`, a resume cursor with the same bounded-gap-else-snapshot guard, and a synchronized marker. The subscription supersedes M-95's `getPlan`-then-refresh seam." So `mercurian.getPlan` is **removed, not kept beside the stream** (significant choice): its only consumer is the planning space this issue rewrites, a second read path would be a maintained placeholder ADR 002 already ruled dead, and M-95 shipped it expecting exactly this replacement.

`packages/contracts/src/mercurian.ts` (edit):

- `MERCURIAN_WS_METHODS`: `getPlan` replaced by `subscribePlan: "mercurian.subscribePlan"`; `savePlanRevision: "mercurian.savePlanRevision"` added.
- New schemas: `PlanRevision` (`{commitId: MercurianCommitId, sequence: Schema.Number, authorKind: PlanAuthorKind, createdAt: IsoDateTime}` — the mutation's return), `PlanTimelineItem` (tagged union above, wire form), `MercurianSavePlanRevisionInput` (`{planId, text: Schema.String}` — empty string is a legal artifact state, so no `TrimmedNonEmptyString`), `MercurianSubscribePlanInput` (`{planId, afterSequence: Schema.optional(Schema.Number)}`), and the stream items:

  ```ts
  export const PlanStreamItem = Schema.Union([
    Schema.Struct({ kind: Schema.Literal("snapshot"), snapshot: PlanDetail }),
    Schema.Struct({
      kind: Schema.Literal("commit"),
      sequence: Schema.Number,
      item: PlanTimelineItem,
      /** Present iff this commit changed the artifact — the new current text. */
      planText: Schema.optional(Schema.String),
    }),
    Schema.Struct({ kind: Schema.Literal("synchronized") }),
  ]);
  ```

- `PlanDetail` is **reshaped, not extended**: `{ plan: PlanShell, planText: Schema.String, timeline: Schema.Array(PlanTimelineItem), snapshotSequence: Schema.Number }`. The old `messages` field goes away — its consumers are `PlanningSpace.tsx` and `wire.ts`, both edited here; contracts are internal to this repo, mobile is parked (ADR 004 §2), so there is no compatibility window to honor. `MercurianPlanningError.operation`: `"getPlan"` → `"subscribePlan"`, plus `"savePlanRevision"`.
- Name check done in discovery: `PlanRevision`/`PlanTimelineItem`/`PlanStreamItem` are free across every `contracts/src` module (grep of all barrel-exported files; the only plan-adjacent upstream name is `OrchestrationProposedPlanId`).

Then the standard touchpoints:

- `contracts/src/rpc.ts`: `WsMercurianSavePlanRevisionRpc` (payload `MercurianSavePlanRevisionInput`, success `PlanRevision`, error `Schema.Union([PlanNotFoundError, MercurianPlanningError, EnvironmentAuthorizationError])`) and `WsMercurianSubscribePlanRpc` (`stream: true`, success `PlanStreamItem`, same error union) **replace** `WsMercurianGetPlanRpc`; `WsRpcGroup` membership updated (~line 919).
- `apps/server/src/auth/RpcAuthorization.ts`: `subscribePlan` → `AuthOrchestrationReadScope` (replacing the `getPlan` entry), `savePlanRevision` → `AuthOrchestrationOperateScope`. The scope-coverage test enforces both moves.
- `apps/server/src/ws.ts`, Mercurian block:
  - `savePlanRevision` handler: `DateTime.now` → `planningStore.savePlanRevision` → `toWirePlanRevision`; `PlanNotFoundError` passes through, everything else wraps as `MercurianPlanningError({operation: "savePlanRevision"})`; aggregate `"mercurian"`.
  - `subscribePlan` handler replaces `getPlan`, built exactly like the tree handler's queue-before-snapshot shape (`ws.ts:1397–1423` — attach the `PlanningStore.changes` signal _before_ the snapshot query so a commit landing mid-query still emits): on subscribe, if `afterSequence` is present and the gap to the current tip is within **`PLAN_RESUME_MAX_GAP`** (a Mercurian constant mirroring `SHELL_RESUME_MAX_GAP`/`THREAD_RESUME_MAX_GAP`), emit the missed commits via `listTimelineSince` then `synchronized`; otherwise emit `{kind:"snapshot"}` from `getPlanSnapshot` then `synchronized`. After that, each `changes` signal drives `listTimelineSince` from the connection's advancing cursor, emitting `{kind:"commit"}` items in sequence order. The `changes` signal is `void`, so per-plan filtering is the cursor query itself — a signal for some _other_ plan reads zero new rows for this history and emits nothing; with mutations being discrete human acts (M-95's measured temperament, restated in ADR 002 §7), the wasted query is negligible and the alternative (a keyed PubSub) is machinery the load doesn't justify (significant choice, flagged).
- `apps/server/src/mercurian/planning/wire.ts`: `toWirePlanRevision`, `toWirePlanTimelineItem`, `toWirePlanStreamItem`; `toWirePlanDetail` reshaped to emit `planText` + `timeline` + `snapshotSequence`.

The tree subscription is untouched — `PlanShell` doesn't change; `savePlanRevision`'s `announceChange` rides the existing snapshot-re-emit, and ADR 002 §7 explicitly keeps the tree on snapshot-re-emit until measurement says otherwise.

### Client plumbing: the subscription replaces the query, one pure reducer

- `packages/client-runtime/src/rpc/client.ts`: `MERCURIAN_WS_METHODS.subscribePlan` joins `EnvironmentSubscriptionRpcTag` (lines 42–45), replacing nothing (`getPlan` was unary).
- `packages/client-runtime/src/state/planReducer.ts` **(new)** — the pure fold, per the `shellReducer.ts`/`threadReducer.ts` precedent: `applyPlanStreamItem(state, item)` over `{detail: PlanDetail | null, synchronized: boolean}` — `snapshot` replaces `detail`; `commit` appends `item` to the timeline and, when `planText` is present, replaces `detail.planText`, guarded by `item.sequence > detail.snapshotSequence` (the shell's monotonic guard, `shell.ts:149–158`) and advancing `snapshotSequence` — which also makes the reducer idempotent against the command-response echo (a commit the mutation already returned arrives again on the stream and is dropped by the guard or by commitId identity). Co-located `planReducer.test.ts` (pure-function tests, the reducer-precedent style).
- `packages/client-runtime/src/state/mercurianPlanning.ts`: the `plan` **query family becomes a subscription family** — `createEnvironmentRpcSubscriptionAtomFamily(runtime, {tag: subscribePlan, transform: Stream.scan(EMPTY_PLAN_STATE, applyPlanStreamItem)})` (`transform` exists for exactly this, `runtime.ts:614–644`); `savePlanRevision` command added via `createEnvironmentRpcCommand`, same `writeScheduler`, and **the same serial-per-plan concurrency key as `appendPlanMessage`** — an edit and a message racing from one client would both target the tip; serializing per plan keeps the local history linear, which is this surface's contract until the DAG Explorer gives forks a deliberate UI. Reconnect resume (passing `afterSequence` from the current reducer state via `subscribeDynamic`-style input, as `shell.ts:180–214` does) is deliberately **not** built here: the subscription atom re-subscribes from scratch on reconnect and a fresh snapshot of a human-scale plan is small; the cursor is in the contract so the upgrade is server-compatible when plans grow or M-104's turns raise the stakes (significant choice, flagged — ADR 002's open question on reconnect-mid-turn buffers points the same way).
- `apps/web/src/state/mercurian.ts`: `usePlanDetail(planId)` keeps its name and return shape (`{detail, isPending, error}` — `refresh` is **removed**: with a live stream there is nothing to poll, and ADR 002 §1 names polling loops as the anti-pattern); `useSavePlanRevision()` added via the existing `useEnvironmentBoundCommand`. `PlanningSpace`'s send/save handlers drop their `refresh()` calls — the stream delivers the echo.

### The planning space grows its second pane

`apps/web/src/components/mercurian/PlanningSpace.tsx` (edit) plus two new Mercurian-owned components:

- **`apps/web/src/components/mercurian/PlanArtifact.tsx` (new)** — the artifact pane: a header row (the label "Plan", last-revision attribution — "Edited by you/Assistant · ‹relative time›" via the existing `formatRelativeTimeLabel`, derived client-side from the last `plan-revision` in the timeline — and an **Edit** button), and a body that is either the rendered plan or the editor.
  - **View state:** `planText` rendered as markdown. **Not** via `ChatMarkdown` (significant choice): that component is thread-entangled — `ScopedThreadRef`, `rightPanelStore`, workspace file links, thread toasts (`ChatMarkdown.tsx:11,78`) — and mounting it here would drag t3code's thread machinery into the Mercurian surface ADR 004 keeps additive. Instead a small local renderer on the same already-present dependencies: `react-markdown` + `remark-gfm` + `rehype-sanitize`, prose-styled with semantic tokens. The team's manual practice writes plans as markdown documents (Plans §What exists today), so markdown is the artifact's native register. Empty text renders the empty-artifact state: a quiet `ui/empty`-style placeholder ("No plan yet — edit to start one") that still shows the Edit affordance — born blank starts with an _empty artifact_, not with no artifact.
  - **Edit state:** a plain textarea seeded with `planText` (the `PlanComposer` textarea pattern, grown to fill the pane), **Save** and **Cancel**. Save → `useSavePlanRevision` → on success return to view state (the stream updates the artifact); Cancel discards. The buffer is deliberately ephemeral `useState` — an unsaved artifact edit is not a commit and not a draft store's business; the vault's per-plan _composer_ drafts are a different, already-designed thing. While editing, an update arriving on the stream (own echo aside, impossible today with one writer) does not clobber the buffer — the editor works on its seed until saved or cancelled. One guard: Save is disabled while the buffer equals `planText` — a no-op edit should not mint a no-op revision commit.
- **`apps/web/src/components/mercurian/PlanTimeline.tsx` (new)** — `MessageList` moves here and generalizes to `timeline: PlanTimelineItem[]`: message items keep today's card rendering; `plan-revision` items render as a compact interleaved row — icon, "You edited the plan" / "The assistant revised the plan", relative timestamp — sitting in the same `<ol>` flow as messages, _not_ a system-message ghetto: same list, same standing, which is the AC's visibility criterion. (Extracted rather than grown in place so `PlanningSpace.tsx` stays the layout shell; `ProjectTreeSidebar` + `.logic.ts` set the precedent for splitting Mercurian components as they grow.)
- **`PlanningSpace.tsx` layout:** inside the existing `PlanningSurface` below the header, a two-pane row — **artifact left, conversation right** (the conversation column keeps `PlanTimeline` + `PlanComposer`). Left-not-right because the vault's walk reads "the plan beside the conversation that evolves it" with the plan as the standing object the space orbits, and because the right edge is spoken for: the [[Right Sidebar]]/DAG Explorer docks there in the design this surface is growing toward. The divider is a drag handle on the artifact pane's right edge via `useResizableWidth` (`storageKey: "mercurian:plan-artifact-width:v1"`, `edge: "right"`, sensible min/max against viewport) — the discovered one-off-preference tier, persisted per the existing hook's drag-end discipline, and correctly _client-local_ under ADR 002 §5's line ("anything a status, ranking, or another window derives from must be server-owned" — a pane width is none of those). Below the `sm` breakpoint the panes stack (artifact above conversation) — same content, no separate mobile surface (mobile app is parked; narrow web still has to render something sane).
- **The draft space is untouched**: `PlanningSpaceDraft` stays composer-only. No plan exists before the first send ("nothing exists until its first commit"), so there is no artifact to show and nothing to subscribe to — the artifact pane appears with the plan, empty.

**AC "exactly one plan per planning space / nowhere a second artifact can appear":** already structural below (`plans.history_id TEXT UNIQUE` in `002_ProjectsPlans.ts`; `PlanningStore`'s header states it), and preserved above by construction — the route mounts one `PlanningSpace`, which renders one `PlanArtifact` bound to the subscription's `planText`; no component, route, or store offers a second artifact slot. The plan asserts this by citation rather than new code, and the test plan pins the store half. A bonus ADR 002 §6 makes explicit: with the read path now a subscription over the one commit log, two windows on the same plan agree — both see the same artifact and the same interleaved history, fan-out by construction.
