# Technical Plan — M-194: Memory branches: a line's amendments stay its own until merged home

_Generated 2026-09-02 from M-194's Goal/AC as re-scoped on 2026-09-01 plus the three clarifications applied to Linear the same day (the write-path commit is the one commit the product makes on a line's branch, only ever at the agent's request; an unmarked change is one the line's latest snapshot holds beyond its branch, and reverting it needs no slot; a note edited outside the product on main is current on the browse surface at once and reaches a line only through git). **Re-grounded 2026-09-03 on `main` at `78c759c3d0`**, which now carries M-206 builds 1 and 2 (the snapshot chain; built read from the chain; refs are the truth), M-196 (coding sessions span the project's repositories from a home repository), and the upstream sync. **Goal, in one sentence:** a thread's amendments land on the line's own branch of the memory repository, each line reads the memory its ancestry left it, and nothing reaches the memory's main line except through the human merge home.

**Scope fences.** Staleness stamps at landing are M-203. The deterministic utilities are M-193. Pruning memory branches and chains rides M-115. The unified thread space (M-197, vault-amended 2026-09-03: the adopted thread view whole, corner icons retired) is not built; this plan grounds the two turn kinds that exist today, planning turns and coding-session turns, and mounts the memory list where the planning space has room today (decision 6). Mobile has no memory surface and is untouched. Nothing here reads a note's meaning (M-202).

## What discovery found: the seams this plan moves

- **There is one memory root and it is the human's checkout.** `MemorySourceStore.getResolvedSource` → `rootPath` under the registered repository's own path; every read and every write (`commitPaths`, `commit --only` on whatever branch that checkout is on) targets it; reads take `{ projectId }` only. This is exactly the main line the browse surface should keep reading, and exactly the wrong place for a line's writes.
- **Designation and membership do not meet.** `designate` accepts any registered repository with no `projectRepositories` check; line branches and slot members come only from those links. A standalone memory repository therefore has no line branch and no slot member today.
- **The proposal is per-plan and in-memory** (`memoryAmendmentProposals: Map<PlanId, …>`), lost on restart, not keyed by line. Under this plan the proposal disappears: the tool call lands the commit.
- **The drift guard exists at the right shape.** `applyAmendment` re-reads each path and refuses with `ConfirmMemoryAmendmentBlockedError { reason: "memory-changed" }` when it differs from the proposal's `before`. It compares against the designated working tree; it needs to compare against the line.
- **Nothing lists what a line changed.** No path-scoped `git log`, no per-commit review state. `PlanTimeline.tsx` renders a landed amendment as one muted line and ignores the recorded SHA.
- **Nothing says "shipped."** `PlanCodingSessionRecord.prUrl` is written once at PR creation and never updated; PR state lives in the git layer's status keyed by branch and is refreshed only through `VcsStatusBroadcaster.refreshStatus` (from `ws.ts`) or `refreshLocalStatus` on turn completion.
- **The chain already gives a line's memory state a name.** `lineSnapshotRef(lineRoot)` is the tree of everything the line holds, marked or not; `refs/heads/<line branch>` is what it committed. "Unmarked" is the difference between the two restricted to the memory root — the same reading `getLineUncommittedDiff` already computes for code.
- **M-196 already snapshots every member and hands every member to a session.** Once the memory repository is a slot member, a coding session's turns snapshot it, its branch movement is derived per repository, and its worktree path is among the session's roots, with no reactor change.
- **A planning turn's slot claim has a holder shape ready.** `SlotLeaseHolder` is `{ kind: "turn", threadId }` (`worktreeSlots/schema.ts:31`), and the provider thread id a planning rebuild mints (`materials.threadId`) is exactly one such key.

## Design

### The load-bearing idea: the memory is a member, and a line's memory is a tree, not a folder

Two moves. First, the memory repository becomes a member of every slot and gets a line branch per line, through the same reactor and the same claim path as code, so nothing about memory needs its own worktree machinery — and, since the vault's rule is that every turn claims a slot, planning turns claim one too, standing where a session's turns stand. Second, every product read of a line's memory is a **tree read** from refs — the chain head when the line has a snapshot, else the branch tip — restricted to the memory root, so reads never depend on which slot the line holds or whether it holds one. Only a running turn touches files by path, and it does so in the slot it holds. The main line keeps being read from the designated checkout exactly as today.

### Membership: one repository set for lines, slots, and branches

**(new)** `apps/server/src/mercurian/worktreeSlots/projectWorkingRepositories.ts`, a pure function over `RepositoriesSnapshot` + `MemorySource`: the project's linked repositories, plus the memory source's repository when it is not among them. `LineBranchReactor.reconcile` and `SlotService.projectMembers` both call it instead of filtering `projectRepositories` themselves. Consequences that fall out: a standalone memory repository gets `mercurian/…` line branches minted at fork time, a slot member at its relative on-disk position, chained snapshots of every kind, the rename adoption and re-point guards of M-206 build 2, and fork inheritance. A memory inside a linked code repository is already a member and needs nothing. `CodingSessionService.start` keeps requiring the session's home repository to be linked; the memory member rides along in `workspaceMembers` without being offered as a home.

**Nested-repository refusal.** `MemorySourceStore.resolveRoot` gains one check through `GitVcsDriver`: `rev-parse --show-toplevel` of the candidate must equal the repository's own toplevel, else `MemorySourceInvalidError { reason: "nested-repository" }`; the contract's reason union grows the literal and `ManageProjectRepositoriesDialog` names the two accepted shapes.

### Reads: a `MemoryTreeSource` beside the working-tree root

`MemoryIndex` gains a second notion of where memory is, **(new)** in `memory/schema.ts`:

```
MemoryTreeSource = { kind: "worktree", rootPath } | { kind: "ref", repositoryPath, ref, subpath }
```

- `listFiles` for a `ref` source runs `git ls-tree -r --name-only <ref> -- <subpath>`; `readIfExists` runs `git show <ref>:<subpath>/<path>`; both through `GitVcsDriver.execute` in `repositoryPath`. The cache key becomes `(kind, rootPath | repositoryPath + resolved oid + subpath)`, so a moved ref is a new entry and the per-`rootPath` fingerprint path is untouched for the main line.
- **(new)** `MemoryIndex.resolveLineSource({ projectId, threadId })` → the line for the thread (a coding session's line from `CodingSessionStore.getByThreadId` and `lineRootCommitIdFor(detail, commitId)`; a planning thread's from the plan's head commit the same way), the memory repository's line-branch row from `LineBranchStore.get`, then `ref = lineSnapshotRef(lineRoot)` when it resolves in the memory repository, else `refs/heads/<line branch>`.
- Contracts: `MercurianReadMemoryIndexInput` and `MercurianReadMemoryNoteInput` gain optional `threadId`; absent means the main line. `ws.ts` handlers pass it through; the standalone Memory page sends none, the in-thread reader and mentions send the thread's.

### Standing: every turn claims the slot

**Planning turns claim the project slot** (decision 3B). `buildRebuildMaterials` claims through `SlotService.claim({ projectId, lineRootCommitId: lineRootCommitIdFor(detail, parentCommitId), holder: { kind: "turn", threadId: materials.threadId } })` and grounds the turn in the slot: `cwd` is the home member's path (the project's first linked repository, as M-196's `primaryRepository` resolves it), `additionalDirectories` are the other members' paths, and the memory root handed to the appendix is the memory member's path joined with the subpath, `kind: "memory"`. The lease is released when the turn settles (`settleTurn`) and on every failure path out of `runRebuild`; `SlotPoolAtCapacityError` becomes a `turn-refused` frame with a new `PlanTurnRefusalReason` literal `pool-at-capacity` (and `turnRefusalNotice` copy on the web), so a send at capacity says so instead of failing silently. The provider session stays `approvalPolicy: "never"` in the read-only sandbox: the agent reads the slot, and only the server writes to it, below. `LineBranchMissingError` at a planning claim maps to the same frame with reason `line-branch-missing`, and the recreate offer M-206 build 2 gives coding sessions is reachable from the plan's Implement door already; the planning space shows the refusal copy and points there.

**Layering.** `PlanningAssistant.layer` moves out of `RuntimeCoreDependenciesLive` to a `PlanningAssistantLayerLive` built on `SlotServiceLayerLive` and merged into `RuntimeDependenciesLive`; nothing in the orchestration or checkpoint reactors consumes the assistant, and `ws.ts` and the MCP toolkit are built above. `server.test.ts` is the proof.

**Coding sessions** already stand in the slot; the memory member is among `workspaceMembers` and therefore among the session's roots. The prompt appendix that names the memory root for planning (`PlanningPrompt.ts` `memoryRoot`) is extracted into a shared `memoryAppendix(...)` and the session's first-turn text carries it, so both turn kinds are told where memory is and that amendments land as commits.

### Writes: the tool lands the commit, on the line's branch, in the slot

The proposal round-trip retires. `propose_memory_amendment` keeps its input shape and its description changes to "lands an amendment on this line's memory branch". The handler calls **(new)** `MemoryIndex.landAmendment({ projectId, threadId, turnId, amendment })`:

1. `prepareAmendment` as today, with `before` read from the memory member in the slot the turn holds (the line's tree as checked out, chain head restored over the branch). A mismatch between the amendment's `before` and that file is the drift guard: `MemoryAmendmentValidationError { reason: "memory-changed" }` returned to the tool, in the turn, so the agent re-reads and retries.
2. Write the amended files into the member and commit them with the existing `commitPaths` (`commit --only` of exactly those paths, on the member's checked-out line branch). The message is the title, then trailers `Astrolabe-Amendment: <turnId>` and the existing `Amended-from-plan: <plan> (<planId>)`; `commitPaths` gains a `trailers` input. The trailer is the **mark**. The working tree and HEAD agree by construction, so the next snapshot's pinned HEAD is the new tip and M-206 reports the movement as "added"; no plumbing, no refresh step.
3. Record the landing in the plan history as today: `PlanningStore.appendMemoryAmendment` with `memoryCommitSha`, plus the branch name.

This is the one place the product commits to a line's branch, always inside a turn the agent is running, which is what keeps M-206's "the runtime never commits" true in spirit: the runtime's own bookkeeping still never touches it.

`confirmMemoryAmendment` / `cancelMemoryAmendment`, the `memory-amendment-proposed` and `-cancelled` stream items, `PlanDetail.memoryAmendmentProposal`, and `MemoryAmendmentSheet` as a modal retire with the gate; the sheet's diff rendering moves into the memory list. The prompt stanza becomes "an amendment lands on this line's memory branch as its own commit; one amendment per call, nothing else in it," which is the base teaching's rule stated where the agent reads it (M-192 carries the full teaching).

### The memory list, then the memory tab: marked commits, the unmarked delta, review state, revert

**Server.** **(new)** `MemoryIndex.readLineChanges({ projectId, threadId })`:

- **Marked**: `git log --first-parent --format=<oid>%x00<subject>%x00<trailers>%x00<author date> <base>..refs/heads/<line branch> -- <subpath>` from the repository path, `<base>` the line-branch row's `baseOid`; entries carrying the `Astrolabe-Amendment` trailer are amendments (turn attribution from the trailer), the rest are commits a person or the agent made by hand and show as such.
- **Unmarked**: `diff <line branch tip> <lineSnapshotRef> -- <subpath>` via `CheckpointStore.diffCheckpoints`; non-empty means one unmarked entry with that diff.
- Phase 2 adds review state from **(new)** table `memory_amendment_reviews(line_root_commit_id, repository_id, commit_oid, reviewed_at)` (migration `017_MemoryAmendmentReviews.ts` + `MemoryReviewStore.ts`); `unreviewedCount` = marked entries without a row, plus one when the unmarked entry exists.
- RPCs in `mercurianMemory.ts`: `readLineMemoryChanges` (phase 1), `markMemoryChangeReviewed` and `revertMemoryChange` (phase 2).

**Revert** (phase 2), one act, no slot:

- A marked commit: new commit on the line branch whose tree is the current tip's tree with the amended paths restored from the commit's parent (temp index `read-tree <tip>`; per path `update-index --cacheinfo` from `<commit>^:<path>` or `--remove` when the commit added it; `write-tree`; `commit-tree -p <tip>`; compare-and-swap `update-ref`). Message "Reverted: <title>" with the amendment trailer, so the revert lists as marked and reviewed. When a slot member has the line branch checked out, refresh the reverted paths there (`git checkout <branch> -- <paths>`), the one refresh this plan keeps.
- The unmarked entry: a new snapshot on the chain whose tree is the chain head's tree with the memory paths restored from the branch tip, parents `(chain head, HEAD)`, kind **`curated`** — one new literal on `SnapshotKind` — through **(new)** `SnapshotChain.captureTree({ treeOid, … })` beside `capture`. The next claim on the line restores it over the branch as it restores any snapshot; a slot already on the line refreshes the memory paths as above.

**Web.** `RightPaneState.view` gains `"memory"` (storage key bumped to `v3` with a tolerant decode of `v2`), a third corner `Toggle` in `PlanPaneToggle`, and **(new)** `apps/web/src/components/mercurian/MemoryTab.tsx` + `.logic.ts` + `.logic.test.ts` + `.catalog.tsx`: the list (marked with attribution, hand commits, the unmarked entry), each entry expanding to the diff through the viewer `MemoryAmendmentSheet.tsx` uses today; phase 2 adds the unreviewed badge on the toggle and the **Reviewed** and **Revert** actions. State module `apps/web/src/state/mercurianMemory.ts` and `packages/client-runtime/src/state/mercurianMemory.ts` gain the requests. The timeline row for a landed amendment links to the tab. Interim placement, recorded: under the vault's 2026-09-03 amendment the memory list is a surface in the adopted panel's strip, scoped to the memory repository by the header's switcher; until M-197 lands it is mounted as the third corner toggle the planning space has today.

### The browse surface reads main; what a line changed is visible from the thread

Unchanged for the Memory page: `readMemoryIndex` without `threadId` reads the designated checkout. Nothing on that page shows a line's changes, per the AC's placement; the tab is the thread-side reading. A note opened in the transient reader inside a thread reads the line's tree, so a mention of a note the line amended shows the amended text.

### The merge home (phase 3)

**The signal.** No shipped state exists, so the plan defines it narrowly and keeps the act always reachable:

- **(new)** `CodingSessionStore.recordPullRequestState(threadId, state)` and a `pr_state TEXT` column in migration 017; the PR status refresh writes it when the branch matches a session, and **opening the memory tab refreshes PR status** (`VcsStatusBroadcaster.refreshStatus`) so the one place the suggestion shows is also a place that asks. A session whose `pr_state` becomes `merged` is "shipped".
- `planSuggestions.logic.ts` gains `memoryMergeHomeSuggestion(detail, lineChanges)` → one row, "Merge this line's memory home", when the line has any marked or unmarked memory change and (a session's `pr_state` is `merged`, or the plan is archived). The memory tab carries a **Merge home** action too, ungated.

**The walk and the act.** The message opens a turn whose responding step is the product's, not the agent's: **(new)** stream item `memory-merge-home-review { entries, unreviewed }` renders in the memory tab as a walk through every unreviewed entry, ending in **Merge home** / **Not now**. Confirming calls **(new)** RPC `mergeMemoryHome({ threadId })`:

1. If the unmarked entry exists, land it first as a marked commit titled "Unmarked memory changes" with trailer `Astrolabe-Amendment: unmarked`, so nothing crosses uncommitted.
2. **Memory inside a code repository:** nothing to merge locally; the walk is the pre-push review and the pull request is the merge. The act records `memory_merged_home_at` on the session (migration 017) and returns; the exit's existing offer to commit and push ships it.
3. **Standalone memory repository:** `git merge-tree --write-tree <main tip> <line tip>` in the repository path, behind an explicit floor: `GitVcsDriver` probes `git --version` once and a git below 2.38 refuses with `MergeMemoryHomeBlockedError { reason: "git-too-old" }` (documented in the user guide). Clean → `commit-tree <tree> -p <main tip> -p <line tip>` with message "Merge memory from <plan title>", CAS `update-ref refs/heads/<main>`; if the designated checkout has `<main>` checked out and its memory paths are clean, `git checkout <main> -- <subpath>` there; dirty memory paths in that checkout refuse with reason `checkout-dirty`. Conflicts → the RPC returns `{ conflicts }` and dispatches a `memory-merge-home-conflict` stream item; the assistant's next turn is seeded with a message proposing a reconciled amendment against current main, which lands through the ordinary write path; the human re-runs the merge home. Nothing merges on its own.
4. Declining leaves both branches standing: no state changes.

`<main>` is the repository's default branch as `LineBranchReactor.repositoryDefaultOid` resolves it.
