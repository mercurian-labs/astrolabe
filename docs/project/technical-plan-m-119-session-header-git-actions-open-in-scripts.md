# Technical Plan — M-119: Session header: git actions, open-in, repository scripts

_Generated from the Goal/AC on Linear issue M-119 (2026-08-20). Grounded against `main` at `d1731ae88`, after M-117 removed the t3code header from the session screen (deferring exactly this issue's three controls) and M-118 re-housed the right panel. Product sources consulted in the almagest vault: **Coding Session View** (the header's three controls), **Repositories** (resolved 2026-07: app-owned scripts, declared and edited on the repository; hosting detected, never configured), **T3code Worktree Lifecycle** ("the system never merges on its own"), **T3code Thread View** (the built header referent), **T3code Source Control** (what an authenticated provider lights up), **Coding Sessions** (leaf-record resolution: structured facts including "a PR link when one exists"). Governing ADRs: 001 (`docs/architecture/local-first-runtime.md`), 002, 004 (`docs/architecture/fork-baseline.md`)._

**Goal, in one sentence:** give the session header the three controls the vault designs — the fork's own git actions (commit with generated message, per-file inclusion, commit-on-new-branch, push, pull, open-a-PR with generated title and body, the combined moves), the fork's open-in picker, and the repository's scripts as a primary action plus a menu — every one pointed at the session's worktree and branch, with create-PR gated on an authenticated hosting provider serving the repository, a created PR's link recorded on the session's leaf, script output landing in the terminal tab, a declared preview address opening the browser preview on run, and the setup-on-worktree-creation behavior (already built by M-110) verified.

**The central discovery finding:** the two adapted controls are already fully portable. `GitActionsControl` takes only `{ gitCwd, activeThreadRef, draftId? }` (`GitActionsControl.tsx:94-98`) and derives everything else itself — status via `subscribeVcsStatus`, actions via `git.runStackedAction` with server-side commit-message and PR title/body generation (`GitManager.ts:1495,1660-1745`), per-file inclusion as an exclusion set in its commit dialog (`:1819-1971`), commit-on-new-branch (`runDialogActionOnNewBranch`, `:1509-1525`). `OpenInPicker` takes `{ environmentId, openInCwd, availableEditors, keybindings }` (`chat/OpenInPicker.tsx`), backed by `shell.openInEditor` and PATH-probed editor discovery (`process/externalLauncher.ts:318-330`). `ProjectScriptsControl` is purely presentational — all behavior lives in caller-supplied callbacks (`ProjectScriptsControl.tsx`). Mounting them in `CodingSessionHeader` is prop-threading, not adaptation. The genuinely new work is three seams: the **create-PR hosting gate** (upstream gates create-PR on `hasPrimaryRemote`, not on provider auth — the 043 gate must join repository hosting with discovery readiness), the **PR-link write** (`CodingSessionStore.attachPullRequest` exists end to end — schema, table `pr_url`, wire, and UI reads in `PlanNodePopover`/`PlanTimeline` — but has **no production caller**), and the **preview-on-run behavior** (`previewUrl` is declared, edited, and persisted upstream but has _no runtime consumer anywhere in the tree_).

**Scope fences:** M-110 owns birth — including setup scripts, which it already runs (`CodingSessionService.ts:389-393` loops `repository.scripts` where `isSetup`, launching each in a `setup-<scriptId>` terminal in the worktree before the first turn); AC6's setup half is verified and walked here, not built. M-118 owns the right panel; its terminal tab and preview surfaces are consumed, not changed. Script _declaration and editing_ stay on the Repositories page (M-96; the contracts file's own words: "Execution is the session view's — this surface only declares"). Hosting-provider _detection_ is M-103's, consumed whole. Teardown is M-115/066. PR links arriving from outside the app (a PR opened on github.com, or via `vcs` status polling) are not recorded — the AC's act is "opening a PR" from the session. Review-a-PR threads, upstream's t3.json script import, and `apps/mobile` (including its `client-runtime/state/gitActions.ts` twin) stay untouched.

## Discovery Summary

**What already works, verified:** commit with generated message (server-side `textGeneration.generateCommitMessage`), per-file inclusion, commit-on-new-branch, push, pull (offered contextually as the quick action when behind — the built referent's shape), open-a-PR with generated title and body (`generatePrContent`, GitHub PR-template detection, `provider.createChangeRequest`), the combined `commit_push` / `commit_push_pr` moves, publish-repository for a remote-less repo, provider-correct vocabulary ("merge request" for GitLab) — all in `GitActionsControl` + `GitManager`, driven by the quick-action state machine in `GitActionsControl.logic.ts` (`buildMenuItems`, `resolveQuickAction`). Branch write-back after commit-on-new-branch already reaches the leaf: `followWorktreeBranchDrift` → `CodingSessionRecordReactor` updates `coding_sessions.branch` (M-110). Editor discovery, launch, and the preferred-editor split button all exist. Setup scripts run at birth in the worktree with output in a `setup-<scriptId>` terminal that surfaces in the session's terminal tab.

**The gaps this issue closes:** (1) `CodingSessionHeader` renders no actions cluster and receives no worktree/repository context (`{environmentId, threadId, threadTitle, planId, planTitle}` only). (2) Upstream's create-PR gating is `hasPrimaryRemote`-shaped, not auth-shaped — a remote on an unauthenticated machine still offers create-PR, which 043 forbids. (3) `attachPullRequest` is a dangling write door: `prUrl` is read by `PlanNodePopover.logic.ts:34,155` and `PlanTimeline.tsx:202-204` but never written. (4) No script-run affordance exists on the session screen, and `previewUrl` has no consumer — "opens the browser preview when run" is new behavior on both the t3 and Mercurian sides.

## Design

### 1. The header grows its actions cluster — context threaded, controls mounted whole

`CodingSessionHeader.tsx` gains a right-hand actions container (the `ChatHeader:301-335` layout: scripts → open-in → git actions, before the existing `SessionPreviewOffer`). New props threaded from the route (`_chat.sessions.$threadId.tsx` already holds every source): `threadRef` (a `ScopedThreadRef` for the session's thread), `worktreePath` (from the server thread shell — stamped at birth before the first turn), and `repositoryId` (from `owningSession`). The header resolves the repository row itself via `useRepositories()` (scripts + `hosting`) and discovery via the existing `sourceControlEnvironment.discovery` atom.

- **Git actions:** mount the fork's `GitActionsControl` with `gitCwd = worktreePath` and `activeThreadRef = threadRef`, rendered only when `worktreePath` is present. AC2 is true by construction: `gitCwd` is the worktree path itself, never `repository.path`, so status, commit, push, pull, and PR all run `-C <worktree>` on the session's branch — no other checkout is reachable from the control. AC1's "every action is human-invoked" is likewise structural: the control acts only on click, and nothing in this plan adds an automatic invocation path (the never-merges invariant stays what M-110 left it).
- **Open-in picker:** mount `OpenInPicker` with `openInCwd = worktreePath`, `environmentId`, and `availableEditors`/`keybindings` read from the same primary-server atoms `ChatView` uses (`state/server.ts:90` and the keybindings atom) — read in the header rather than threaded through the route, since they are environment facts, not session facts. Render under the same condition `shouldShowOpenInPicker` encodes: thread environment is the primary environment.
- **Scripts:** the new `SessionScriptsControl` (Section 3).

The header test's absence pin flips: keep asserting no delete/new-thread affordance; assert the three controls render for a session with a worktree.

### 2. The create-PR hosting gate, and the PR link on the leaf

**Gate (client).** Add one generic, default-open optional parameter through the pure logic: `buildMenuItems` and `resolveQuickAction` (`GitActionsControl.logic.ts`) accept `changeRequestsAllowed?: boolean` (default `true`). When `false`: the create-PR menu item is **absent** (not disabled), and the quick-action machine never yields `create_pr` or `commit_push_pr` — `commit_push_pr` degrades to `commit_push`, exactly the existing `!hasPrimaryRemote` degradation shape. Viewing an already-open PR (`open_pr`) stays ungated — the AC gates the creation moves only. `GitActionsControl.tsx` gains the matching optional prop and threads it through; upstream behavior with the prop omitted is byte-identical (ADR 004's minimal-additive discipline; the mobile twin `client-runtime/state/gitActions.ts` is not touched — mobile is parked).

Mercurian computes the gate in `hostingProviders.logic.ts` — a small pure `changeRequestsAllowed(hosting, discovery)` that is true exactly when `repositoryHostingStanding` resolves to _authenticated_ — so the decision speaks the same readiness vocabulary as the Repositories page (M-103's named seam). The header joins the session's repository row (`hosting`) with the discovery result and passes the boolean down. When the gate fails, the remedy lives where M-103 put it: the provider standing on the Repositories page — the header shows no PR ghost.

**PR link (server).** In the `ws.ts` `git.runStackedAction` handler (`:2996-3019`), after the workflow succeeds having **created** a change request, resolve the coding session and record the link: `CodingSessionStore.attachPullRequest`. Keying: prefer the thread identity if the action input already carries it; otherwise resolve by the session's unique `worktreePath` matching the action's `cwd` (adding a `getByWorktreePath` lookup to the store if needed — the `thread_id` unique-index pattern). A non-session thread resolves to nothing and the handler behaves exactly as today. `attachPullRequest` already announces through the store's change signal, so the tree/plan snapshots re-emit and `PlanNodePopover`/`PlanTimeline` render the link with code that already exists. **`server.test.ts`'s mock must gain the same store method** (the recorded mock-drift lesson). Only the in-app creation act records; combined `commit_push_pr` flows through the same result and records identically.

### 3. Repository scripts: run in the session, output in the terminal tab, preview on run

`apps/web/src/components/mercurian/SessionScriptsControl.{tsx,logic.ts}` **(new)** — a thin Mercurian wrapper that _renders the upstream `ProjectScriptsControl`_ (primary action + menu, split-button shape) and supplies what upstream got from `ChatView`:

- **Data:** the session repository's `MercurianRepositoryScript[]` mapped to the `ProjectScript` shape the control renders (`scriptId → id`, `isSetup → runOnWorktreeCreate`, `previewUrl` through; default icon). Pure mapping in the logic file.
- **Run:** open-or-reuse a terminal `script-<scriptId>` (the `setup-<scriptId>` naming precedent) via the terminal atoms with `{ threadId, terminalId, cwd: worktreePath, worktreePath, env: projectScriptRuntimeEnv({ project: { cwd: repository.path }, worktreePath }) }`, write `` `${script.command}\r` ``, and activate the right panel's **terminal** surface on that terminal (the `rightPanelStore` terminal surface M-118 left live) — "output in the terminal tab" literally.
- **Run-only:** no edit gear, no add-script affordance, no t3.json import group — declaration and editing stay on the Repositories page per the resolved vault decision. If `ProjectScriptsControl`'s props don't already make those affordances optional, make them optional with a minimal additive upstream edit (callbacks absent ⇒ affordance absent); the t3 thread surfaces pass everything and render unchanged. When the repository declares **no scripts, the control does not render** — an empty menu would advertise an editing surface the session deliberately doesn't have.
- **Preview on run (new behavior):** when the run script declares `previewUrl` and the runtime supports previews (`isPreviewSupportedInRuntime()` — desktop only), open the browser preview surface on that address after issuing the command, through the same preview machinery the panel's empty state uses for configured script URLs. On the web client the script still runs; the disabled Browser tab with its existing "desktop only" message is the designed explanation (M-118's verified state) — no toast, no second message.

Setup scripts (AC6, second half) are **verified, not built**: M-110's birth launches every `isSetup` script in the fresh worktree before the first turn, with activity events in the timeline and the `setup-<scriptId>` terminal reconciled into the terminal tab. The walk demonstrates it; `CodingSessionService.test.ts` already covers launch-before-turn.

### 4. Documentation and surface accounting

- `docs/user/projects-and-plans.md`: the session header's three controls — how finished work leaves the session (commit/push/pull/PR, all human-invoked; the generated message and PR text as offers), when create-PR appears (authenticated provider serving the repository) and where the PR link lands (the leaf's record), the open-in picker, and repository scripts (run here, declared on the Repositories page; preview address; setup-at-birth).
- `docs/internals/glossary.md`: cross-link the session header entry to hosting-provider standing and repository scripts.
- Web and desktop apply identically (same served origin; preview-on-run is runtime-gated, not surface-forked). Mobile stays parked.

### Gaps and findings carried out of discovery

- Upstream's `autoOpenPreview` flag remains without a consumer on t3 surfaces; Mercurian's preview-on-run reads only the Mercurian script's `previewUrl` (the vault names no per-script toggle — a declared address opens on run).
- Pull is offered contextually (quick action when behind), matching the built referent; the walk makes the branch behind to demonstrate it.
- t3 enforces one setup script per project client-side while the Mercurian birth path loops all `isSetup` scripts — divergence noted, harmless, not reconciled here.
- A PR opened outside the session (or found by status polling) never back-fills `prUrl`; if wanted later, `VcsStatusRemoteShape.pr` is the seam.
