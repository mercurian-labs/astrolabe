# ADR 002: Event and streaming model

**Status:** Proposed — drafted 2026-08-03, executing the M-91 charge against the fork as it stands after backlog 020 (M-95); review and acceptance tracked on M-91. Decides the question [ADR 001](./local-first-runtime.md) delegated ("whether planning-space events ride upstream's `orchestration_events` or a Mercurian log"), over the storage seam ADR 001 fixed and the commit store M-94 landed.

## Context

The vault demands more consumers of the same live facts than any one surface: the project tree's status pills — one status per row, "the most urgent thing true of it right now" ("Issue Status"); the palette's needing-you ranking ("Search Palette"); streaming turns in planning spaces ("Assistant": "Responses stream… you can stop it mid-response") as well as coding sessions; approval requests and structured questions that pause work on you ("Coding Sessions"); and unseen-updates that clear on visit and re-arm on mark-unread ("Issue Status"). This ADR's job, per M-91, is not to invent a mechanism but to decide how those consumers ride — or extend — the one the fork already has, and to name what genuinely doesn't fit it.

Facts on the fork that shape the decision:

- **The existing mechanism is one pattern applied twice.** Server-owned state changes as typed events in an append-only log with a global monotonic `sequence` (`orchestration_events`; append and read-model projection in one transaction, PubSub publish only after commit — `orchestration/Layers/OrchestrationEngine.ts`). Clients consume per-aggregate `stream: true` RPCs shaped _snapshot → sequenced events → synchronized marker_, with cursor-based resume capped at a 1,000-event gap before falling back to a fresh snapshot (`SHELL_RESUME_MAX_GAP`/`THREAD_RESUME_MAX_GAP`, `apps/server/src/ws.ts`). The shell stream re-reads whole rows and coalesces; the thread stream forwards raw events (filtered by `isThreadDetailEvent`) that a pure client reducer folds (`packages/client-runtime/src/state/threadReducer.ts`).
- **Fan-out to N windows is provided, by construction.** Every subscription access creates a fresh PubSub subscription over the shared log ("Each access creates a fresh PubSub subscription so that multiple subscribers can consume independently" — `OrchestrationEngine.ts`), and each WebSocket upgrade builds its own RPC layer over shared singletons (`ws.ts`, `websocketRpcRouteLayer`). N windows are N independent cursors over one totally-ordered log; commands serialize through one queue with `commandId` receipts, so ordering is identical for every observer. This is the built form of the pattern the vault recorded on "T3code Thread": "Session state is server-owned and fans out."
- **Token streaming is delta events on the same log.** Assistant text streams as `thread.message-sent` events with `streaming: true` carrying delta fragments, folded identically by the server projector and the client reducer; delivery mode (`streaming`/`buffered`) is a server setting, so all windows see the same behavior. Cost worth naming: every delta is a persisted event row, and the log has no pruning — sequence grows for the lifetime of the database.
- **Mid-turn pauses are activities plus server-derived flags.** Approvals and structured questions are `thread.activity-appended` events; the projection derives `pending_approval_count` / `pending_user_input_count` onto the thread row (`refreshThreadShellSummary`, `orchestration/Layers/ProjectionPipeline.ts`), so `hasPendingApprovals` / `hasPendingUserInput` fan out server-computed on the shell stream. Responses return as commands on the single `orchestration.dispatchCommand` RPC.
- **Unseen tracking is the one signal that does not fan out.** "Completed-unseen" derives from `threadLastVisitedAtById` in `apps/web/src/uiStateStore.ts` — zustand over `window.localStorage`, never server-side (verified: no read/seen model anywhere in `apps/server` or contracts). The desktop shell loads a custom scheme (`t3code://app`, `apps/desktop/src/electron/ElectronProtocol.ts`) while a browser loads `http://host:port` — different origins, different localStorage — so two windows on one machine _already disagree_ about what's unseen.
- **What M-95 landed on the Mercurian side.** The planning store (`apps/server/src/mercurian/planning/PlanningStore.ts`) is plain relational over `mercurian.sqlite` (M-94's decision) with a `changes: Stream<void>` PubSub signal; the tree subscription (`mercurian.subscribeTree`) re-emits small whole snapshots on change; plan conversations are read by unary `mercurian.getPlan` with client-side refresh after each send; planning mutations are plain RPCs, not commands. The commit store itself already carries a global append order: `commits.sequence INTEGER PRIMARY KEY AUTOINCREMENT` (`mercurian/persistence/Migrations/001_CommitGraph.ts`).
- **Coding sessions will be t3code threads.** ADR 001 §3: the leaf commit is Mercurian-side; the session it names — timeline, runtime, worktree, checkpoints — stays t3code-side, referenced by thread id.

## Decision

### 1. One mechanism: the fork's protocol pattern, extended — never a parallel invention

The event/streaming mechanism is the fork's existing shape, stated as a rule new surfaces must follow: **server-owned state, changed only by server-side writes, observed through `stream: true` RPCs that emit a snapshot, then totally-ordered events with a resume cursor, fanned out via per-connection PubSub subscriptions.** No new surface invents a channel: no polling loops, no client-to-client paths, no client-derived status a server row could carry. Which surface rides which stream:

| Consumer                                                      | Mechanism                                                                                                                               |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Turn streaming + approvals + questions in **coding sessions** | Upstream `orchestration.subscribeThread` / `subscribeShell` / `dispatchCommand`, unchanged — sessions _are_ t3code threads (ADR 001 §3) |
| Turn streaming in **planning spaces** (M-100/M-104)           | New `mercurian.subscribePlan` (§2, §3)                                                                                                  |
| **Status signals** on the tree (M-99)                         | Server-derived flags on `mercurian.subscribeTree` rows (§4)                                                                             |
| **Unseen updates**                                            | Server-owned visited state in the Mercurian store, on the tree stream (§5)                                                              |
| **Palette** needing-you ranking (M-105)                       | Pure read over tree-subscription data; no channel of its own                                                                            |

### 2. Planning-space events: the commit DAG is the durable log

ADR 001's delegated question — upstream's log or a Mercurian log — dissolves on inspection: **the commit store already is the append-only, totally-ordered record of everything durable that happens in a planning space.** Messages, plan revisions, issue revisions, session leaves — the vault defines them as commits in one history ("Commit Tree": "There is no separate 'chat log'"), and M-94 gave every commit a global `sequence`. So planning-space events ride a Mercurian stream whose cursor is the commit store's own sequence — no second event-sourced log is built, and M-94's plain-relational decision stands unamended.

Concretely, at M-100: **`mercurian.subscribePlan`** — the `subscribeThread` shape over the commit store: snapshot (plan row + commits, via the existing read surface), then commit-appended events keyed by `commits.sequence`, a resume cursor with the same bounded-gap-else-snapshot guard, and a synchronized marker. The subscription supersedes M-95's `getPlan`-then-refresh seam, which was built as a placeholder for exactly this decision. `PlanningStore.changes` (the tree's re-emit signal) stays for coarse invalidation; per-plan streams carry the fine-grained events.

**Riding upstream's `orchestration_events` is refused**, on a mechanical ground, not a stylistic one: the pattern's correctness comes from appending the event and updating the read model in _one transaction_, and Mercurian's rows live in a different database file (ADR 001 §2: "no atomic transaction spanning both stores"). A Mercurian aggregate's events in `state.sqlite` could never be transactionally consistent with its state in `mercurian.sqlite`. The same fact, run the other way, is why the commit-DAG-as-log works: the commit _is_ the state and the event, in one file, in one insert.

Planning **mutations stay plain RPCs** (`mercurian.createProject`, `createPlan`, `appendPlanMessage`, and successors) rather than adopting the command/decider/receipt bus: the store's invariants are transactional refusals at the insert (M-94's design), there is no command replay to deduplicate, and the bus exists to serialize a live session runtime planning doesn't have. `dispatchCommand`, the decider, and the projector remain t3code-only machinery.

### 3. In-flight turn output is transport, not record

Upstream persists every streaming delta as an event row; Mercurian does not copy this. A streaming assistant response in a planning space is **ephemeral runtime state**: it fans out live to every subscribed window as transient frames on `mercurian.subscribePlan` (with the current partial text included in the subscription snapshot, so a window opened mid-turn joins the stream coherently), and **only the settled message lands as a commit** — including a stopped response, which commits marked interrupted per the Assistant resolution ("a commit, marked as interrupted"). Two reasons, in order: the Commit Tree's model is one commit per message, not one per token — a history of delta rows would be a second, finer chat log inside the store that "no separate chat log" forbids; and upstream's persist-every-delta has a real cost this ADR declines to import — an unprunable log that grows with every token ever streamed. What is given up: replaying the keystroke-level past of a turn. The record is the commit; the stream is how you watched it happen.

The same frame carries turn lifecycle for planning (turn running / awaiting a structured question / settled), which is what §4's flags derive from. The exact frame shapes are M-104's contract design, inside this decision.

### 4. Status signals are server-derived, composed at the read layer

"Issue Status" is three signals — awaiting your input, assistant working, unseen updates — one winner per row, rolling up the tree. The decision: **every status input is a server-side fact, derived onto the tree subscription's rows** the way `refreshThreadShellSummary` derives `hasPendingApprovals` today; clients rank and render, never originate.

Because a plan's signals come from two stores — planning-side (a structured question pending, an assistant turn streaming) from the Mercurian runtime and store, session-side (approval pending, turn running) from t3code's projections looked up by the leaf's referenced thread id — **composition happens at the subscription's read layer** (the `ws.ts` tree handler and the services it queries), never by cross-database transaction: the tree stream re-emits when _either_ store's change signal fires — `PlanningStore.changes`, or upstream's domain-event stream filtered to referenced thread ids. This is the id-reference seam of ADR 001 §3 doing its intended work at the surface.

### 5. Unseen-updates state moves server-side

The fork's client-local visited tracking is the one piece of the pattern that fails the design: "Issue Status" makes unseen a status like any other — tree-rolled, palette-ranked — and the resolved decision extends it to teammates' publishes; but localStorage-per-origin means the desktop shell and a browser window disagree today, and a signal M-99 must rank server-side can't live in one window's storage at all. Decision: **per-plan visited state becomes a Mercurian-store fact** — a visited-at per plan, written by a plain RPC on visit, with mark-unread as the upstream trick (visited-at set just before the latest activity) — flowing back out on the tree stream like any other row change, so every window agrees. In the local-first phase this is workspace-local (one user, no identity — ADR 001 §4); when identity arrives it becomes per-user state, and the teammate-publish extension of unseen rides whatever transport [ADR 003](./publish-as-act.md) decides. Client-local UI state that is genuinely preference (sidebar width, expansion, drafts) stays client-local; the line is: _anything a status, ranking, or another window derives from must be server-owned._

### 6. Two windows on one machine: verified, with the gap now closed

The AC's multi-window question, answered against the code: the desktop shell and a browser tab open the same locally-served origin (ADR 001 §1) over independent WebSocket connections; each gets its own RPC layer and its own PubSub cursors over the same post-commit event log, so **all server-owned state agrees between windows** — threads, streaming text, approvals, settled/snoozed/archived, server settings — verified in the machinery above. What diverged was exactly the client-local state: unseen/visited (closed by §5, the one substantive gap) and per-window preferences (correctly divergent). No new mechanism is needed for multi-window; the fork's fan-out was already the answer, minus one misplaced piece of state.

### 7. What is reused, what is added — the contract inventory

Reused as-is: the upstream protocol whole (log, decider, projector, shell/thread subscriptions, `dispatchCommand`, receipts, resume guards) for everything t3code-shaped, including coding sessions when they arrive. Reused as pattern: snapshot→events→synchronized, cursor resume, server-derived row flags — applied to Mercurian streams. Added, all on the Mercurian side of the contracts seam (`packages/contracts/src/mercurian.ts`, `MERCURIAN_WS_METHODS`): `subscribePlan` with its event/frame shapes (M-100/M-104), visited/mark-unread RPCs and tree-row status fields (M-99), each an additive extension of the file M-95 created. The tree keeps M-95's snapshot-re-emit rather than sequenced deltas — the payload is small shells and mutations are discrete human acts; the named trigger to revisit is the first measurement showing tree re-emits costing meaningful frame or wire time at real plan counts (the AGENTS.md performance bar), at which point the upgrade path is the same cursoring §2 gives plans.
