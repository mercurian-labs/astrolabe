# Visual replies

Agents can answer with a page instead of only text: a chart, table, image collage, or mockup. Diagrams of boxes and arrows are drawn as [canvases](#canvases). Ask for one ("show this as a chart", "make a collage of these screenshots") and the agent builds a self-contained HTML page, which appears in the thread above its written reply. It works with every provider, on web, desktop, and mobile.

Pages use your current theme, including custom themes, and follow light and dark mode as you switch. Scripts run inside the page, but it is sandboxed away from T3 Code and your session. Links you click in a page open in your browser. Use the expand button to open a page full screen. On web and desktop, use the zoom controls to see more detail.

Agents can place local images in a page by file path. T3 Code embeds them when the page is published, so the page keeps working after the original files move or are deleted. Deleting the thread deletes its pages.

Before publishing, agents check their work with screenshots from a small headless browser that T3 Code keeps for itself; it never uses a browser you installed. The first preview on a machine downloads it once (about 120 MB) into T3 Code's data folder, so that preview can take a minute. Browser tabs on a remote environment use the same browser, so whichever comes first downloads it. Some Linux hosts need [setup](remote-access.md#browser-host-setup) before it can start. Pages publish without it.

Previews can load public resources such as CDN scripts, but nothing on your local network. The machine running the environment looks up each name, and previews block names that resolve to private or reserved addresses. Clash or Mihomo in fake-IP DNS mode can return these addresses, so external resources can fail there. The preview's console messages can identify affected hostnames. Inline the resource, add its host to `fake-ip-filter`, or switch that machine's proxy DNS to `redir-host`.

## Canvases

When a flow, an architecture, or a set of dependencies is easier to see than to read, an agent draws it as a canvas in the thread, with or without being asked: cards, arrows and sections, laid out for it. A card can hold text, a link, or a place in your code. Click a code card to open the file at that line.

The agent shows a canvas inside its reply, beside the text that explains it: the whole board, or one named section of it with the rest dimmed, written `![[Name.canvas]]` or `![[Name.canvas#Section]]`, the way a note embeds a canvas. A `[[Name.canvas#Section]]` link does the same as a chip. Click either to open the board in the right panel, on that section, where you can drag and scroll to pan, pinch or Ctrl-scroll to zoom, and click the zoom percentage to see the whole board. Every canvas a turn drew is also listed at the foot of the reply, beside its changed files, even when the reply shows none of it: expand one to use the board in place, or open it in the right panel. On the phone, tap a canvas to do the same.

**Edit board** in the board's menu (☰ at its top right), or E with the board focused, opens the canvas in the right panel ready to change: move and add cards as on any [canvas](project-docs.md#edit-a-canvas). The copy in the chat stays read-only and shows your edits as you make them. Your edits save into the thread, and the composer shows an **Edited** pill for each board you changed: with your next message the agent sees those boards as you left them. Click a pill to open its board, or remove it (×) to keep that board's edits from the agent; editing the board again brings the pill back. **Read-only** in the same menu turns it back off. The menu also jumps to a labelled section, asks the agent about the board, and keeps it in the project.

A canvas stays in its thread and is deleted with it, unless you keep it. **Keep in the project…** in the board's menu or at the foot of the reply, or **Keep** on the phone's board, lets you add a comment, then **Add to chat** puts the canvas in the composer as a chip. Say what you want done with it, invoke any skill you like, and send: the agent can save it into the project as it looks in the thread, on the thread's branch. On a computer, ⌘Enter or Ctrl+Enter adds it and sends. **Place in the project** does the saving yourself: it asks for a name, with a folder before the name if you want it in one, and which of the project's repositories when it has several. In a thread with its own worktree, the canvas is written there for you to commit with the thread's other changes. In a hosted repository's main checkout it goes to your draft, which reaches the host when you open a pull request from it; anywhere else it is written on disk (see [Where your edits go](project-docs.md#where-your-edits-go)). Either way the thread's canvas stays as it was. Code cards link to the code in their own repository.

A kept code card is a link to that file at a commit your remote has, so it works outside Astrolabe too. If the thread's commit isn't pushed, the link goes to the nearest commit that is, and Keep tells you the code there may differ. A card becomes plain text, naming the file and commit, if the file isn't in a pushed commit or the repository has no remote, or on a server such as Bitbucket Data Center that has no such link.

Canvases use the open JSON Canvas format.

## MCP apps

Some MCP servers return an interactive app with their tool results, following the [MCP Apps](https://github.com/modelcontextprotocol/ext-apps) standard. When an agent calls one of those tools, the app appears in the thread below the tool call, on web, desktop, and mobile. The tool call keeps its input and result, so you can still read them when an app shows nothing. Codex and Claude support this today, for any MCP server you have configured for them. Claude needs Claude Code 2.1.301 or newer; older versions and other providers show these calls as ordinary tool calls.

Apps follow your theme. An app can call tools on its own server and post a message to the thread; Astrolabe asks first unless the server marks the tool as read-only, and it asks before every message. On mobile, an app also asks before opening a link, and Astrolabe asks before saving a file an app offers. An app stays viewable after its agent stops, but using it needs the agent of the thread that created it running, so send a message in that thread first if the app says it is unavailable. An app that navigates away from its own page is stopped. Apps run only on an environment whose Astrolabe server is current: on an older server, the thread shows a line asking you to update it in place of the app.

An app can open full screen right after you tap or click in it. On web and desktop, a tap in the app within five seconds of a click or key press elsewhere in T3 Code doesn't count, so tap it again after that. Use the button in its top corner, or press Escape outside the app, to return it to the thread. Anything else that needs your attention, such as an approval, also returns it to the thread. On mobile, full screen opens the app again in its own screen, so anything the app does not save itself starts over. An app can also keep the agent informed of what you did in it, such as a filter you picked; T3 Code sends the latest note from each app with your next message.
